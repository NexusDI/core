# bridge-api

A server team that adopts NexusDI wants to see one module graph serve real HTTP routes, with a scope per request, before it picks a framework. This app is that demo: the Starship Meridian's bridge API, one graph behind Hono, Express, Fastify and Cloudflare Workers, tested the same way on each.

## What the Demo Shows

The graph lives in `src/ship/`, and each framework entry wires it to routes with that framework's adapter.

- `src/ship/meridian.module.ts` composes the root the routes read: `Simulation.forRoot(setup.sim)`, `MeridianSystems`, the system modules whose tokens the routes read (`Tactical` for `/course`, `Safety`, `ShipLifeSupport` for the compartment route, `Telemetry` for the stream), then `MissionScope`, which reads the request's mission into a scoped `MissionFlightLog`, `AuditTrail`, `AlarmPanel` and `SimDriver.forRoot({ mode: setup.mode })`. The root exports `driver` and `AuditTrail`, so a test that imports it reads the driver and the audit log. The private `bridgeShip(name, setup, link)` builds both roots. `Meridian` adds `SubspaceLink.forRoot({ relayUrl })`, a global module, so the library's `Tactical` downloads the star charts over the link with an async factory. `OfflineMeridian` leaves the link out, so the phased array reads no link and `Tactical` serves the charts the library bundles, with no I/O. `AlarmPanel` is not global: it exports `ALARM_SINKS`, and `MasterAlarm` in the library's `Safety` collects every published sink. The charts, the comms module, the phased array and the `comms hail` command live in `@nexusdi/meridian-systems`. `src/ship/contracts.ts` holds the bridge's tokens, `AUDIT_LOG` among them, and re-exports `NAV_CHARTS`, `SUBSPACE_LINK`, `SUBSPACE_LINK_OPTIONS` and the types `Course`, `INavCharts`, `ISubspaceLink` and `SubspaceLinkOptions` from the library. The package has no `./offline` export. The move adds no route: `comms hail` goes through `POST /commands`.
- `src/ship/sim-driver.module.ts` binds `SIM_DRIVER` to `WallClockDriver`. In live mode the driver advances the loop one tick every `dt` seconds with `setInterval`, the one timer in the demo, and the container clears it when it disposes the ship. In manual mode it starts no timer, and `POST /sim/advance` moves the ship. `Meridian` and `OfflineMeridian` run manual, so a test or a Worker that builds them starts no timer.
- `src/ship/plugins.ts` holds `bridgePlugins({ dev?, trace?, tools?, scopes? })`. It always registers the interceptors plugin and the phase check (`MERIDIAN_SYSTEM_PHASE`): an audit interceptor on `NAV_CHARTS` that records each call in `AUDIT_LOG`. On `BLAST_DOORS` it binds `FlightRecorder` to `open` and `close` and `PressureInterlock` to `open`, imported from `@nexusdi/meridian-systems/interlock`. In development it adds `errors({ text: SHIP_TEXT })` only. `trace` needs `tools`, the devtools module. `devtools({ annotate: [shipNotes] })` and the black box recorder come from `introspect().plugins`, which a Node entry passes as `extra` when `SHIP_INTROSPECTION` is on. `shipNotes` from `@nexusdi/meridian-systems` labels each simulation provider in the graph with its system, such as `system: Telemetry`.
- `src/ship/alarm-panel.module.ts` holds `AlarmPanel`, which contributes `AuditAlarmSink` to the ship's `ALARM_SINKS`. The sink writes each alarm the master alarm raises or clears as one audit line, such as `raised DECOMPRESSION habitat at tick 2` and `cleared DECOMPRESSION habitat at tick 3`. The module exports `ALARM_SINKS`, so `all(ALARM_SINKS)` in Safety reads the sink although Safety imports nothing from the bridge.
- `src/entries/hono.ts`, `src/entries/express.ts` and `src/entries/fastify.ts` each export `createBridge(ship, options)`, which serves the same twelve routes through `@nexusdi/hono`, `@nexusdi/express` or `@nexusdi/fastify`. The `mount` option adds routes right after the adapter middleware: `e2e/fixtures/mission-routes.ts` uses it for `GET /mission`, `GET /log/stream` and the `missing-provider` mission of the e2e cases, which the entries do not serve. Express, like Hono and Fastify, matches routes case-sensitively and strictly: `createBridge` sets its `case sensitive routing` and `strict routing`, so `/Compartments/habitat/atmosphere` and `/compartments/habitat/atmosphere/` match no route on any framework. Every framework answers an unmatched path with an empty 404, so no answer repeats the path. Each entry reads a JSON body through `readJson` in `src/bridge/json-body.ts`, so the three answer a malformed or non-JSON body alike:

- The `/sim/advance` guard resolves `SIM_DRIVER` through each adapter's gate form: `di.inject` with `next` on Express, `di.injectMiddleware` on Hono and `di.injectHook` in Fastify's `onRequest`. Each framework then answers a live ship with 404 before it reads the body, and the startup check covers the guard's tokens as it covers a route's.
- `src/bridge/commands.ts` holds `answerCommand(desk, body, log)`, which the three entries share. It adds the entries of `log` to a 202 when the log holds any. It names no ship system: `COMMAND_DESK` finds the handler, and the route maps the error class to a status. A throw that is not a `NexusError` is a bug, and the framework answers it with an empty 500.
- The railgun needs no route and no bridge code. A crew member fires with `{ "system": "weapons", "action": "fire", "range": 10000 }` through `POST /commands`, and `answerCommand` hands it to `WeaponsCommands` like any other command. A fire answers 202 `{ "tick" }`, the tick that applies the shot. The first fire arms the mount, so on a cold reactor it answers 409 `MERIDIAN_POWER_BUDGET` with "The railgun load needs 300 MW, and the router has 0 MW free beside the loads above it." and the fix "raise the reactor throttle and wait for the output to climb, or lower a load of higher priority." A fire on an armed mount never answers 409 for power. A `range` that is not a number from 0 to 100,000 answers 400 `MERIDIAN_BAD_COMMAND` with "weapons fire cannot use the range argument. It takes fire with a range from 0 to 100,000 m." and the fix "send the arguments in the ranges above." `weapons reload` answers 400 with "weapons has no action 'reload'. It takes fire with a range from 0 to 100,000 m."
- `src/bridge/refusal.ts` holds `refusedReply(error)`, which `answerCommand` uses: 400 for a `BadCommandError` and 409 for any other `NexusError`. Anything else is rethrown. It also holds `refusalOf(error)`, which builds the body, and `SHIP_TEXT`, the list `[shipText, interceptorsText]`. The refusal's `message` and `fix` come from `explain(error, { text: SHIP_TEXT })`, with `shipText` from `@nexusdi/meridian-systems/text`, and a code no pack words keeps its one-line message. Core's `formatError` hook never formats an error user code threw, so `errors()` words only core's and the interceptors' own errors, and no refusal body depends on the plugin.
- `src/bridge/ftl.ts` holds `answerFtlSection(drive)`, the 200 body of `POST /sections/ftl`, and `ftlRating(scope)`, which is described under the FTL drive below.
- `src/bridge/compartment-of.ts` holds `compartmentOf(path)`, which reads the id of a `/compartments/<id>/...` path and keeps it percent-encoded. Each entry's request mapper sets `compartment` on the request from it, so the scope's `COMPARTMENT` names the room. The mapper runs before the router matches `:id`, so it reads the path itself: Hono the raw pathname of `c.req.url`, since `c.req.path` decodes it, Express `req.path` and Fastify `req.url`.
- `src/bridge/atmosphere.ts` holds `answerAtmosphere(scope)`. `COMPARTMENT` throws `UnknownCompartmentError` while the analyzer builds, and core rethrows it as it is, so the helper matches it with `instanceof` and answers 404 with its refusal. The refusal shows the room name decoded, so `reactor%20bay` reads `reactor bay`. It rethrows any other error.
- `src/bridge/mission.ts` holds `missionOf(header)` and `requestOf(header, compartment)`, which build the request each entry hands `nexus()`, and the `MISSION_HEADER` name. The console reads `missionOf` through the `@nexusdi/bridge-api/mission` export. `src/bridge/options.ts` holds `BridgeOptions`, which the three entries take.
- `src/bridge/json-body.ts` also holds `fieldOf(body, key)`, which `parseTicks` uses to read one field of a JSON body.
- `src/entries/worker.ts` builds the container on the first request of each isolate (the function form of `nexus()`), because Workers refuse I/O at module scope. It passes no `graph` option, so `GET /graph` answers 404 on a Worker. It passes no scopes either, so a door command answers `{ tick }` alone.

The telemetry stream holds only the latest frame the client has not read, and sends it when the client reads. So a `POST /sim/advance` of 600 ticks queues one frame per open stream, and a slow client skips the frames between its reads. The stream sends no heartbeat. A client that disconnects cancels the stream, and the cancel unsubscribes it from the feed. Express and Fastify send the stream through `telemetryReadable` (`src/bridge/telemetry-readable.ts`), a Node `Readable` with a high-water mark of 0, so the `Readable` reads no frame ahead of the client.

The bridge console in `examples/bridge-console`, the Meridian's React Router app, calls the Hono entry. The Express and Fastify entries run every case of `e2e/cases.ts` except one Hono-only check of the execution context, so each framework serves the same graph with the same results.

### The Flight Log of a Door Command

A crew member who opens a door reads the entry the command wrote in the request's flight log, beside the tick. `FlightRecorder`, a private class in `src/ship/plugins.ts`, is a singleton interceptor on `open` and `close` of `BLAST_DOORS`, so it serves every request and finds the request's log through the current scope. It takes `REQUEST_SCOPES` (`IScopeSource` in `src/ship/contracts.ts`), calls `next()`, then records `opened <door>` or `closed <door>` in the `FLIGHT_LOG` of the scope `current()` answers. The log prefixes the mission, so the entry reads `survey-7: opened habitat-airlock`. The recorder records after `next()` returns, so an `open` the interlock refuses records nothing. The other commands record nothing and answer `{ tick }` alone.

Each Node server entry and `src/entries/worker.offline.ts` create `const scopes = nodeScopes()` once and pass it to the ship, through `shipFromEnv(scopes)` or `bridgePlugins({ scopes })`, and to `createBridge(ship, { scopes })`. The bridge then runs each request in its scope, so the recorder reads that scope with no argument. Without `scopes`, `bridgePlugins` binds a source whose `current()` answers `undefined`, and the recorder records nothing. `src/entries/worker.ts` and the edge entry pass none.

### Loading the FTL Drive on Request

The ship starts without a jump drive, and `FtlDrive` joins it on `POST /sections/ftl`. Each `createBridge` calls `di.load(FtlDrive)` once, and the adapter returns a section. Hono and Express register the section before the handler: `bridge.post('/sections/ftl', ftl, ftl.inject({ drive: FTL_DRIVE }, ...))`. Fastify passes `{ onRequest: ftl }` in the route options. The bridge code never calls `ship.load` itself.

The section runs `ship.load(FtlDrive)` once per module and container, so every later `POST /sections/ftl` awaits the same settled promise. It then calls `scope.extend()` on the request's scope when that scope has started. The Node entries pass `nodeScopes()`, which opens the request's scope before the handler runs. A plain handler that awaited `ship.load()` and then read `FTL_DRIVE` from that scope would throw `NEXUS_LOADED_AFTER_SCOPE` on the first load. The `inject` inside the section finds a loaded drive and a no-op extend.

Until `POST /sections/ftl` loads the drive, `POST /commands` refuses an `ftl` command with 400 `MERIDIAN_BAD_COMMAND`, since the desk serves no `ftl` system. The loaded drive registers its commands with the desk, so the spool and the jump go through `POST /commands` like every other crew command. A spool the router cannot fit answers 409 `MERIDIAN_POWER_BUDGET`. A second spool on an armed drive answers 202 with the next tick and queues nothing, so `GET /commands` gains no entry. A second `POST /sections/ftl` answers the same 200 and builds nothing.

The telemetry stream opens its request scope before `POST /sections/ftl` loads the drive. Each `/telemetry` route passes `ftlRating(await di.scope(c))` on Hono or `ftlRating(await di.scope(req))` on Express and Fastify to `telemetryStream`, whose third argument is optional. `ftlRating` answers `undefined` while a frame's `ftl.status` reads `offline`. On the first other status it calls `await scope.extend()` and reads `FTL_DRIVE` once, then keeps the promise. Without the extend, the read throws `NEXUS_LOADED_AFTER_SCOPE`. From that frame on, each `snapshot` frame carries `ftlRating` after the reading's keys: `{ energy: 90000000000, power: 900000000, pulseShare: 0.1, reactorLevel: 0.9, coolantLimit: 1300 }`. The events stay `snapshot` and `offline`, and the console reads `/sim` and ignores `ftlRating`. The stream reads the drive bound to `FTL_DRIVE`, so a test that overrides the module gets its rating. A rating that rejects errors the stream.

## Running a Server

Each Node entry builds the container from the environment and listens on `PORT`, or 3000. Set `RELAY_URL` to download the charts from a relay; without it the server uses `OfflineMeridian`. The `dev-relay` target (`scripts/dev-relay.mjs`) starts a local relay that serves `/charts`, `/handshake` and `/signoff` as the e2e suites do, on `RELAY_PORT` or 3100. A hail on the offline ship answers 202 with a `notice` of code `MERIDIAN_NO_SUBSPACE_LINK`, its message, and a fix that names `RELAY_URL`, `dev-relay` and `dev`.

Two more variables set up the simulation, and a tick is always 0.5 ship seconds. `SIM_MODE` is `live`, the default, or `manual`. `SIM_SEED` is a whole number from 0 to 4294967295, and defaults to 7. An empty variable counts as unset, and any other value stops the server with an error that names the variable and the values it takes.

The Node servers read the ship's files from disk. `shipFromEnv` passes `files: new NodeShipFiles(shipFilesDir())` (`src/env/ship-files.ts`) to `Simulation.forRoot`, so the life-support calibration comes from `deck/sensors.calibration.json` in `@nexusdi/meridian-systems` through `node:fs/promises` when the ship starts. A missing or unreadable file stops the server with `NEXUS_PROVIDER_FAILED` for `LifeSupportOptions`, whose cause names the file. A Worker has no file system, so `src/entries/worker.ts` and `worker.offline.ts` pass no `files`, and the ship reads the copies the library bundles.

```sh
npx nx dev @nexusdi/bridge-api
npx nx run @nexusdi/bridge-api:build-deps
npx tsx examples/bridge-api/src/entries/server.express.ts
npx tsx examples/bridge-api/src/entries/server.fastify.ts
```

`nx dev` builds the workspace packages, starts the dev relay, waits until it answers `/charts`, and runs `tsx watch src/entries/server.hono.ts` with `RELAY_URL` set to the relay, so the ship is linked. The Express and Fastify entries read the same built packages, so `build-deps` builds them first. Each entry prints `Server is running on http://localhost:3000` once it listens.

A manual ship moves only when a client asks it to:

```sh
SIM_MODE=manual npx nx dev @nexusdi/bridge-api
curl -X POST http://localhost:3000/sim/advance -H 'content-type: application/json' -d '{ "ticks": 600 }'
curl http://localhost:3000/sim
curl -N http://localhost:3000/telemetry
```

A crew command queues for the next tick. With the reactor idle, a raise of the shields answers 409 with the power budget text, and a throttle answers 202:

```sh
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "engineering", "action": "shields", "raised": true }'
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "engineering", "action": "throttle", "level": 1 }'
curl http://localhost:3000/commands
```

Life support starts offline and runs on the reactor, so a client sets a throttle beside `online`. The analyzer then reads a compartment's air at the current tick, and an unknown compartment answers 404:

```sh
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "engineering", "action": "throttle", "level": 0.01 }'
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "life-support", "action": "online" }'
curl http://localhost:3000/compartments/habitat/atmosphere
curl http://localhost:3000/compartments/galley/atmosphere
```

A door command answers its flight log entry. The interlock refuses a door with more than 5,000 Pa across it, so on a manual ship at tick 0 the inner airlock door opens, and the outer door, with 101,300 Pa against space, answers 409:

```sh
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "safety", "action": "open", "door": "habitat-airlock" }'
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "safety", "action": "open", "door": "airlock-outer" }'
```

```text
{"tick":1,"flightLog":["survey-7: opened habitat-airlock"]}
{"code":"MERIDIAN_INTERLOCK","message":"The airlock-outer door holds 101,300 Pa of difference, above the 5,000 Pa interlock.","fix":"bring both sides within 5,000 Pa of each other with a pump or a vent, then open the door."}
```

The inner door stands open after the first command, so close it first. Then bring life support online and open the airlock's vent. Once the airlock holds under 5,000 Pa, the interlock lets the outer door open.

Each Node entry passes `graph: () => graph(ship)` unless `NODE_ENV` is `production` (`isDev` in `src/env/env.ts`), so `GET /graph` answers 404 in production. Each Node entry also passes `log: shipLog()` (`src/env/log.ts`), so an error that ends in a 500 or 503 writes one line with its `NEXUS_` code and message on the server, and the response body stays empty.

The federation shell reads the telemetry stream and posts crew commands from its own origin, so the Hono entry answers the origins in `SHELL_ORIGIN` with CORS headers through `hono/cors` (`shellOrigins` in `src/env/cors.ts`). `SHELL_ORIGIN` is a comma-separated list and defaults to `http://localhost:4300` and `http://127.0.0.1:4300`, the shell's dev server under both loopback names. The Hono entry trims each origin and ignores empty ones. In production the entry answers no origin, whatever `SHELL_ORIGIN` holds. The Express, Fastify and Workers entries send no CORS header.

The sources use parameter properties and extensionless imports, which plain `node` refuses, so `tsx` runs them.

Each Node entry stops on `SIGTERM` through `stopOnSigterm(server, shutdown, { close?, drain?, signals? })` from `src/env/drain.ts`. On the signal, it closes the server (`server.close()` by default, `bridge.close()` on Fastify), then aborts `shutdown`, the `AbortController` whose signal the entry passes to `createBridge` as `shutdown`. The abort ends every open telemetry stream with `event: offline` and `ship offline`. The server answers the requests in flight before it closes, and the ship disposes after that: Express and Hono through `await using` once the server emits `close`, Fastify in its `onClose` hook. After the signal, each response that finishes calls `server.closeIdleConnections()`, so a keep-alive connection closes once its response ends, and the process exits without waiting for a keep-alive timeout. After `drain` milliseconds (10 000 by default), `server.closeAllConnections()` ends the connections still open. A throw or a rejection from `close` goes to the console and sets exit code 1. Fastify listens on `::`, or on `HOST` when it is set, since on `localhost` it opens one server for 127.0.0.1 and one for ::1.

## Testing and Measuring

The app's checks run as Nx targets, each with the workspace packages built first.

- `npx nx test @nexusdi/bridge-api` runs the route tests over `@nexusdi/vitest` fixtures with fake charts, and a startup check that compiles both graphs. `test/check.test.ts` also compares the graph `inspect()` draws with the committed `graph.json`, so `main`'s test run and the release verify step catch a stale file. The driver, `setupFromEnv`, `parseTicks`, `readJson`, `answerCommand`, `compartmentOf`, `answerAtmosphere` and the simulation, command and atmosphere routes on each framework have their own cases. The atmosphere cases read the habitat and the airlock at tick 0, a 404 for `galley` and for the encoded `%68abitat`, and an empty 500 from a ship whose `ATMOSPHERE_SENSOR` is `FailingSensor` (`test/doubles.ts`). `check.test.ts` keys the graph's notes by token and module, since `ShipSystems` and `CommandHandlers` each have one provider per ship system. It reads `system: LifeSupport` and `phase: 4` on LifeSupport's physics and `system: Safety` and `phase: 5` on Safety's, and `system: Propulsion` and `system: Helm`, each with `phase: 2`, on theirs. It reads `system: Weapons` on the four providers of `Weapons`, with `phase: 3` on the physics. It finds no note on the interceptors plugin's providers or on `AlarmPanel`'s sink. It compiles `FtlDrive` as a load of both roots and draws the graph with that load. After `ship.load(FtlDrive)` it reads `system: FtlDrive` and no phase note on the development graph's `FtlDrive` provider. `test/shutdown.test.ts` disposes a live ship with `bridgePlugins({ trace })` and checks that the `dispose:instance` events name `SimDriver`, `MasterAlarm`, `TelemetryFeed` and `ReactorCore`, in that order, and that the reactor reads level 0 afterwards.

  The safety cases follow each door command and each alarm. `test/commands.test.ts` reads the interlock and interceptor text through `SHIP_TEXT`, and `answerCommand`'s 202 with and without `flightLog` and its 409 for `MERIDIAN_INTERLOCK`. `test/flight-recorder.test.ts` runs door commands inside `scopes.run(scope, ...)`: a refused `open airlock-outer` leaves the log empty, and `open bridge-habitat` leaves `survey-7: opened bridge-habitat`. `test/env/ship.test.ts` checks that `shipFromEnv(scopes)` hands its scopes to the recorder. On each framework, `test/routes/safety.test.ts` reads the flight log of an opened and a closed door, the entry under `x-mission-id: survey-9`, the tick alone without scopes, the 409 for the outer door at tick 0, a 400 for the door `galley` and for `flood` and `drill` of the airlock, a 202 `{ tick: 1 }` with no `flightLog` for a drill, the doors and drills at tick 0 from `GET /sim`, and an empty 404 for `GET /safety`.
