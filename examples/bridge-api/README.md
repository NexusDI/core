# bridge-api

A server team that adopts NexusDI wants to see one module graph serve real HTTP routes, with a scope per request, before it picks a framework. This app is that demo: the Starship Meridian's bridge API, one graph behind Hono, Express, Fastify and Cloudflare Workers, tested the same way on each.

## What the Demo Shows

The graph lives in `src/ship/`, and each framework entry wires it to routes with that framework's adapter.

- `src/ship/meridian.ts` composes the bridge's modules over the ship's systems: `BridgeApi`, which reads the request's mission into a scoped flight log, `AuditTrail`, `AlarmPanel`, `meridianSystems(...)` from `@nexusdi/meridian-systems` and `SimDriver.forRoot({ mode: setup.mode })`. The private `bridgeShip(name, systems, mode)` builds both roots. `Meridian` passes `{ ...setup.sim, relayUrl }`, so the library's `Comms` links the ship to the relay and its `Tactical` downloads the star charts with an async factory. `OfflineMeridian` passes `setup.sim` alone, so the library's `OfflineComms` binds no link and its `OfflineTactical` serves the charts the library bundles, with no I/O. The charts, the comms module, the phased array and the `comms hail` command live in `@nexusdi/meridian-systems`. `src/ship/contracts.ts` re-exports `NAV_CHARTS`, `SUBSPACE_LINK`, `COMMS_OPTIONS` and the types `Course`, `INavCharts`, `ISubspaceLink` and `CommsOptions` from the library, and `@nexusdi/bridge-api/ship` exports no `Comms`, `tactical` or `OfflineTactical`. The package has no `./offline` export. The move adds no route: `comms hail` goes through `POST /commands`.
- `src/ship/sim-driver.module.ts` binds `SIM_DRIVER` to `WallClockDriver`. In live mode the driver advances the loop one tick every `dt` seconds with `setInterval`, the one timer in the demo, and the container clears it when it disposes the ship. In manual mode it starts no timer, and `POST /sim/advance` moves the ship. `Meridian` and `OfflineMeridian` run manual, so a test or a Worker that builds them starts no timer.
- `src/ship/plugins.ts` holds `bridgePlugins({ dev?, trace?, scopes? })`. It always registers the interceptors plugin: an audit interceptor on `NAV_CHARTS` that records each call in `AUDIT_LOG`. On `BLAST_DOORS` it binds `FlightRecorder` to `open` and `close` and `PressureInterlock` to `open`, imported from `@nexusdi/meridian-systems/interlock`. In development it adds `errors({ text: SHIP_TEXT })` and `devtools({ annotate: [shipNotes] })`. `shipNotes` from `@nexusdi/meridian-systems` labels each simulation provider in the graph with its system, such as `system: Telemetry`.
- `src/ship/alarm-panel.module.ts` holds `AlarmPanel`, which contributes `AuditAlarmSink` to the ship's `ALARM_SINKS`. The sink writes each alarm the master alarm raises or clears as one audit line, such as `raised DECOMPRESSION habitat at tick 2` and `cleared DECOMPRESSION habitat at tick 3`. The module is global, since `all(ALARM_SINKS)` in Safety reads the sinks of Safety and its imports and the exports of every global module, and Safety imports nothing from the bridge.
- `src/hono.ts`, `src/express.ts` and `src/fastify.ts` each export `createBridge(ship, options)`, which serves the same eleven routes through `@nexusdi/hono`, `@nexusdi/express` or `@nexusdi/fastify`. Express, like Hono and Fastify, matches routes case-sensitively and strictly: `createBridge` sets its `case sensitive routing` and `strict routing`, so `/Compartments/habitat/atmosphere` and `/compartments/habitat/atmosphere/` match no route on any framework. Every framework answers an unmatched path with an empty 404, so no answer repeats the path. Each entry reads a JSON body through `readJson` in `src/bridge/json-body.ts`, so the three answer a malformed or non-JSON body alike:

- `src/bridge/commands.ts` holds `answerCommand(desk, body, log)`, which the three entries share. It adds the entries of `log` to a 202 when the log holds any. It names no ship system: `COMMAND_DESK` finds the handler, and the route maps the error class to a status. A throw that is not a `NexusError` is a bug, and the framework answers it with an empty 500.
- `src/bridge/refusal.ts` holds `refusalOf(error)`, which both routes that refuse use, and `SHIP_TEXT`, the list `[shipText, interceptorsText]`. The refusal's `message` and `fix` come from `explain(error, { text: SHIP_TEXT })`, with `shipText` from `@nexusdi/meridian-systems/text`, and a code no pack words keeps its one-line message. Core's `formatError` hook never formats an error user code threw, so `errors()` words only core's and the interceptors' own errors, and no refusal body depends on the plugin.
- `src/bridge/compartment-of.ts` holds `compartmentOf(path)`, which reads the id of a `/compartments/<id>/...` path and keeps it percent-encoded. Each entry's request mapper sets `compartment` on the request from it, so the scope's `COMPARTMENT` names the room. The mapper runs before the router matches `:id`, so it reads the path itself: Hono the raw pathname of `c.req.url`, since `c.req.path` decodes it, Express `req.path` and Fastify `req.url`.
- `src/bridge/atmosphere.ts` holds `answerAtmosphere(scope)`. `COMPARTMENT` throws `UnknownCompartmentError` while the analyzer builds, and core rethrows it as it is, so the helper matches it with `instanceof` and answers 404 with its refusal. It rethrows any other error.
- `src/worker.ts` builds the container on the first request of each isolate (the function form of `nexus()`), because Workers refuse I/O at module scope. It passes no `graph` option, so `GET /graph` answers 404 on a Worker. It passes no scopes either, so a door command answers `{ tick }` alone.

The telemetry stream holds only the latest frame the client has not read, and sends it when the client reads. So a `POST /sim/advance` of 600 ticks queues one frame per open stream, and a slow client skips the frames between its reads. The stream sends no heartbeat. A client that disconnects cancels the stream, and the cancel unsubscribes it from the feed. Express and Fastify send the stream through `telemetryReadable` (`src/bridge/telemetry-readable.ts`), a Node `Readable` with a high-water mark of 0, so the `Readable` reads no frame ahead of the client.

The bridge console in `examples/bridge-console`, the Meridian's React Router app, calls the Hono entry. The Express and Fastify entries run every case of `e2e/cases.ts` except one Hono-only check of the execution context, so each framework serves the same graph with the same results.

### The Flight Log of a Door Command

A crew member who opens a door reads the entry the command wrote in the request's flight log, beside the tick. `FlightRecorder`, a private class in `src/ship/plugins.ts`, is a singleton interceptor on `open` and `close` of `BLAST_DOORS`, so it serves every request and finds the request's log through the current scope. It takes `REQUEST_SCOPES` (`IScopeSource` in `src/ship/contracts.ts`), calls `next()`, then records `opened <door>` or `closed <door>` in the `FLIGHT_LOG` of the scope `current()` answers. The log prefixes the mission, so the entry reads `survey-7: opened habitat-airlock`. The recorder records after `next()` returns, so an `open` the interlock refuses records nothing. The other commands record nothing and answer `{ tick }` alone.

Each Node server entry and `src/worker.offline.ts` create `const scopes = nodeScopes()` once and pass it to the ship, through `shipFromEnv(scopes)` or `bridgePlugins({ scopes })`, and to `createBridge(ship, { scopes })`. The bridge then runs each request in its scope, so the recorder reads that scope with no argument. Without `scopes`, `bridgePlugins` binds a source whose `current()` answers `undefined`, and the recorder records nothing. `src/worker.ts` and the edge entry pass none.

## Running a Server

Each Node entry builds the container from the environment and listens on `PORT`, or 3000. Set `RELAY_URL` to download the charts from a relay; without it the server uses `OfflineMeridian`.

Two more variables set up the simulation, and a tick is always 0.5 ship seconds. `SIM_MODE` is `live`, the default, or `manual`. `SIM_SEED` is a whole number from 0 to 4294967295, and defaults to 7. An empty variable counts as unset, and any other value stops the server with an error that names the variable and the values it takes.

```sh
npx nx dev @nexusdi/bridge-api
npx nx run @nexusdi/bridge-api:build-deps
npx tsx examples/bridge-api/src/server.express.ts
npx tsx examples/bridge-api/src/server.fastify.ts
```

`nx dev` builds the workspace packages and runs `tsx watch src/server.hono.ts`, the app's `dev` script. The Express and Fastify entries read the same built packages, so `build-deps` builds them first. Each entry prints `Server is running on http://localhost:3000` once it listens.

A manual ship moves only when a client asks it to:

```sh
SIM_MODE=manual npx nx dev @nexusdi/bridge-api
curl -X POST http://localhost:3000/sim/advance -H 'content-type: application/json' -d '{ "ticks": 600 }'
curl http://localhost:3000/sim
curl -N http://localhost:3000/telemetry
```

A crew command queues for the next tick. With the reactor idle, a raise of the shields answers 409 with the power budget text, and a throttle answers 202:

```sh
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "engineering", "action": "shields", "raised": true }'
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "engineering", "action": "throttle", "level": 1 }'
curl http://localhost:3000/commands
```

Life support starts offline and runs on the reactor, so a client sets a throttle beside `online`. The analyzer then reads a compartment's air at the current tick, and an unknown compartment answers 404:

```sh
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "engineering", "action": "throttle", "level": 0.01 }'
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "life-support", "action": "online" }'
curl http://localhost:3000/compartments/habitat/atmosphere
curl http://localhost:3000/compartments/galley/atmosphere
```

A door command answers its flight log entry. The interlock refuses a door with more than 5,000 Pa across it, so on a manual ship at tick 0 the inner airlock door opens, and the outer door, with 101,300 Pa against space, answers 409:

```sh
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "safety", "action": "open", "door": "habitat-airlock" }'
curl -X POST http://localhost:3000/commands -H 'content-type: application/json' -d '{ "system": "safety", "action": "open", "door": "airlock-outer" }'
```

```text
{"tick":1,"flightLog":["survey-7: opened habitat-airlock"]}
{"code":"MERIDIAN_INTERLOCK","message":"The airlock-outer door holds 101,300 Pa of difference, above the 5,000 Pa interlock.","fix":"bring both sides within 5,000 Pa of each other with a pump or a vent, then open the door."}
```

The inner door stands open after the first command, so close it first. Then bring life support online and open the airlock's vent. Once the airlock holds under 5,000 Pa, the interlock lets the outer door open.

Each Node entry passes `graph: () => graph(ship)` unless `NODE_ENV` is `production` (`isDev` in `src/ship-from-env.ts`), so `GET /graph` answers 404 in production.

The sources use parameter properties and extensionless imports, which plain `node` refuses, so `tsx` runs them.

Each Node entry stops on `SIGTERM` through `stopOnSigterm(server, shutdown, { close?, drain?, signals? })` from `src/ship-from-env.ts`. On the signal, it closes the server (`server.close()` by default, `bridge.close()` on Fastify), then aborts `shutdown`, the `AbortController` whose signal the entry passes to `createBridge` as `shutdown`. The abort ends every open telemetry stream with `event: offline` and `ship offline`. The server answers the requests in flight before it closes, and the ship disposes after that: Express and Hono through `await using` once the server emits `close`, Fastify in its `onClose` hook. After the signal, each response that finishes calls `server.closeIdleConnections()`, so a keep-alive connection closes once its response ends, and the process exits without waiting for a keep-alive timeout. After `drain` milliseconds (10 000 by default), `server.closeAllConnections()` ends the connections still open. A throw or a rejection from `close` goes to the console and sets exit code 1. Fastify listens on `::`, or on `HOST` when it is set, since on `localhost` it opens one server for 127.0.0.1 and one for ::1.

## Testing and Measuring

The app's checks run as Nx targets, each with the workspace packages built first.

- `npx nx test @nexusdi/bridge-api` runs the route tests over `@nexusdi/vitest` fixtures with fake charts, and a startup check that compiles both graphs. `test/check.test.ts` also compares the graph `inspect()` draws with the committed `graph.json`, so `main`'s test run and the release verify step catch a stale file. The driver, `setupFromEnv`, `parseTicks`, `readJson`, `answerCommand`, `compartmentOf`, `answerAtmosphere` and the simulation, command and atmosphere routes on each framework have their own cases. The atmosphere cases read the habitat and the airlock at tick 0, a 404 for `galley` and for the encoded `%68abitat`, and an empty 500 from a ship whose `ATMOSPHERE_SENSOR` is `FailingSensor` (`test/doubles.ts`). `check.test.ts` keys the graph's notes by token and module, since `ShipSystems` and `CommandHandlers` each have one provider per ship system. It reads `system: LifeSupport` and `phase: 4` on LifeSupport's physics and `system: Safety` and `phase: 5` on Safety's, and `system: Propulsion` and `system: Helm`, each with `phase: 2`, on theirs. It finds no note on the interceptors plugin's providers or on `AlarmPanel`'s sink. `test/shutdown.test.ts` disposes a live ship with `bridgePlugins({ trace })` and checks that the `dispose:instance` events name `SimDriver`, `MasterAlarm`, `TelemetryFeed` and `ReactorCore`, in that order, and that the reactor reads level 0 afterwards.

  The safety cases follow each door command and each alarm. `test/commands.test.ts` reads the interlock and interceptor text through `SHIP_TEXT`, and `answerCommand`'s 202 with and without `flightLog` and its 409 for `MERIDIAN_INTERLOCK`. `test/flight-recorder.test.ts` runs door commands inside `scopes.run(scope, ...)`: a refused `open airlock-outer` leaves the log empty, and `open bridge-habitat` leaves `survey-7: opened bridge-habitat`. `test/ship-from-env.test.ts` checks that `shipFromEnv(scopes)` hands its scopes to the recorder. A `helm burn level 1` answers 202 `{ tick: 801 }`. At tick 1,200 the drive reads 14,400 N, 0.288 kg/s, 0.0036 m/s², 0.72 m/s and 72.18 m. The main drive asks and gets 600,000,000 W, and `GET /commands` holds the ticks 1, 11 and 801. Every read checks that no alarm is up. The burn waits for the settle, because a drive that pushes along an attitude equal to the course reads `cos(0)`, and `Math.cos` differs by one ulp between Node, Deno and Bun on about 3 % of other angles. The case is the sixth in `growthCases`, so workerd, Deno and Bun run it too.

  The other three run the six cases of `test/runtime/growth-cases.ts` on workerd (`test/worker/growth/`), Deno and Bun: `GET /sim` at tick 0, an advance of 600 ticks to 293 K and 101.3 kPa, a first telemetry frame at tick 0 before the client cancels, the airlock drill, the offline hail and the course and burn.
