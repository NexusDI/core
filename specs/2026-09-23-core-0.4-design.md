# @nexusdi/core 0.4: a compiled, sealed container

Status: revision 2, after the owner's pillar audit (section 0). Revision 1 was built on
`feat/core-0.4`; the plan tasks for revision 2 are not written yet.
Packages: `@nexusdi/core` (npm 0.3.1, which has users; `adjustSemverBumpsForZeroMajorVersion`
in `nx.json` makes the break a 0.4.0 bump). Adds `@nexusdi/decorators`, `@nexusdi/testing`,
`@nexusdi/node`, `@nexusdi/errors`, `@nexusdi/devtools`, `@nexusdi/federation` and
`@nexusdi/codemod`.
Depends on: `chore/tooling-upgrade` (Nx 23, TS 6.0.3, Vitest 4, nodenext ESM,
`scripts/verify-packaging.mjs`, `tools/repo-checks`; not yet on `main`),
`fix/core-export-map` (the 0.3.x source this spec mines; already contained in
`chore/tooling-upgrade`, also not yet on `main`).
Supersedes: `archive/async-container` (the abandoned async rewrite).
Out of scope, tracked elsewhere: an interceptor package (#17; its hook is in 0.4), the
graph CLI (#18; `inspect()` is in 0.4), a plugin registry page (#19; the plugin API is in
0.4), benchmarks (#21).
Prior art: Angular's `inject()` and `providers` shapes, NestJS module encapsulation and
`forRoot`, InversifyJS scopes, the TC39 Explicit Resource Management proposal, Standard
Schema.

## 0. Revision 2 (pillar audit)

Revision 1 is the spec the engine was built from (`feat/core-0.4`). On 2026-09-24 the owner
audited it against the NexusDI pillars and approved its 18 decisions. The owner changed
D9 from subpaths to packages, revised D18, and added D19, a public plugin system that
every optional package is built on. D20 follows from D19 and the owner's placement rule.
After the first draft of this revision, the owner replaced D5's size budget with a size
report and a consolidation workstream, and added D21, one error class.
This section lists each decision, then the feature placement and the package split. The
sections after it are revised to match, and where this section and a later section
disagree, the later section is wrong.

The pillars every entry is checked against:

- P1 modern
- P2 not complicated
- P3 a powerful module system
- P4 dynamic configuration through Nest-style static `forRoot`
- P5 a developer-friendly API
- P6 lightweight: a minimal bundle and few dependencies
- P7 flexible class and factory providers
- P8 an async core
- P9 TypeScript 7

"0.3 user" means code written against `@nexusdi/core@0.3.2`. "New user" means someone who
starts from the 0.4 docs. Sizes are gzip for the two-service app of section 17.2, bundled
as ESM with esbuild `--minify`. "Est." marks an estimate from the esbuild metafile; every
other size was measured.

### D1. `Nexus.create` accepts a provider list

- Before: `Nexus.create` took a module only, and every module needed a `name`. A hello
  world needed `defineModule({ name, providers })` before `Nexus.create`.
- After: `Nexus.create` takes a module, a provider array, or
  `{ providers, imports, exports }`. The last two compile as an anonymous root module
  named `root` in errors and in the graph. Every other module keeps its required
  `name`. The container stays sealed, and `set()` stays removed (section 3.5).
- Pillars: P2, P5. P3 is unchanged: the array is a root module under another name.
- 0.3 user: writes `const c = new Nexus(); c.set(Logger); c.set(UserService)`. After the
  codemod: `const c = await Nexus.create([Logger, UserService])`. The
  `container-bootstrap` transform writes the array for a flat container and
  `{ imports: [...] }` for one that registered modules.
- New user: `await Nexus.create([Logger, UserService])` and `get()`. Five lines, four
  concepts (`static deps`, `Nexus.create`, `await`, `get`).
- Size: est. under 0.1 KB.

### D2. One primary way to declare dependencies

- Before: four equal forms on the first pages: `provide(C, { deps })`, `static deps`,
  provider literals and `@Injectable`. The README and the docs' Getting started taught
  different forms.
- After: the primary form is a class that lists its constructor tokens in `static deps`,
  and a module that lists classes plus `provide(TOKEN, { useClass | useValue |
useFactory })` for interface tokens, values and factories. `@Injectable` moves to the
  decorators page and the `@nexusdi/decorators` package (see the package split),
  provider literals to the migration page, and `provide(C, { deps })` to the page for
  classes the user cannot edit. No form is removed (sections 2 and 3.2).
- Pillars: P2, P5, P7 (one form per job).
- 0.3 user: nothing to write by hand; the codemod output follows D3.
- New user: learns one form on the first pages and meets the others when a page needs
  them.
- Size: 0.

### D3. The codemod writes `static deps`

- Before: the `services` transform turned `@Service` and `@Inject` parameters into
  `@Injectable({ deps })`, and every Vite 8 project got the `vite-decorator-plugin` note,
  because Vite 8 does not lower standard decorators.
- After: `services` writes `static deps = [...] as const` by default, and
  `@Injectable({ deps })` only under `--style=decorators`, which also adds
  `@nexusdi/decorators` to `dependencies`. The `vite-decorator-plugin` note fires only
  for that style (section 13.2).
- Pillars: P1, P2, P5.
- 0.3 user: `@Service() class UserService { constructor(@Inject(LOGGER) l: ILogger) {} }`
  becomes `class UserService { static deps = [LOGGER] as const; constructor(l: ILogger) {} }`,
  and runs on every toolchain with no Babel plugin, Vite 8 included. The migrated class
  loses its decorators, so it looks less like the 0.3 code.
- New user: unaffected.
- Size: decorator users drop the `@nexusdi/decorators` package and its
  `Symbol.metadata` polyfill (est. 0.3 KB).

### D4. `forRoot` and `forRootAsync` replace `with()`

- Before: `Mod.with(value)` and `Mod.with({ deps, useFactory })`, one method that told a
  value from a factory by an own `useFactory` key, so an options object with a
  `useFactory` function was read as a factory.
- After: `Mod.forRoot(value)` and `Mod.forRootAsync({ deps?, useFactory })`. Each call
  returns a new module instance, as `with()` did, and options are still validated with
  Standard Schema during `create` (section 3.4).
- Pillars: P4 (a NestJS user finds the method by name), P5.
- 0.3 user: `Comms.config({ frequency: 1420 })` becomes `Comms.forRoot({ frequency: 1420 })`,
  and `Comms.configAsync(fn)` becomes `Comms.forRootAsync({ useFactory: fn })`. The
  codemod maps both one to one, which is closer to 0.3 than revision 1's mapping.
- New user: `defineModule({ name, options, schema, ... })`, then `forRoot` or
  `forRootAsync` at the import site.
- Size: 0. The rename is in before rc.0, so no RC user sees `with()`.

### D5. No bloat in core, reported on every pull request (revised by owner)

- Before: no size check. The built core measured 16.2 KB, 7.1 times 0.3.2's 2.28 KB, and
  the README said "lightweight". The audit proposed a 10 KB budget, and the first draft
  of this revision added a production build that skipped validation passes to reach it.
- After: no numeric budget and no build that skips checks. Every build runs every
  validation pass, and core is a complete, correct container with no plugin registered.
  The principle is "no unnecessary bloat in core", held three ways:
  - Placement: a feature core does not need moves into a plugin package, and nothing is
    cut for size alone (the feature placement table).
  - A size report on every pull request compares core's ESM gzip size with `main` and
    flags growth above 2%, which the pull request's author must justify in its
    description (section 12.4).
  - A consolidation workstream shrinks core without changing behaviour: one error class
    (D21), and merged compiler and runtime code pinned by the existing tests
    (section 12.5).
- Pillars: P6 as a standing check on growth, P5 (validation stays in every build, so
  production reports wiring errors at `create` as development does).
- 0.3 user: a browser bundle grows from 0.3.2's 2.28 KB to core's size, which the size
  report publishes on `main`.
- New user: installs one package with zero dependencies, and the README shows core's
  measured size from the report.
- Size: the placement table puts core at est. 13.5 to 14.5 KB before the consolidation
  workstream, which the plan measures step by step.

### D6. General positioning with a "when to skip" section

- Before: synthesis Decision 1 proposed narrowing the audience to several entry points
  or several teams, and telling single-team apps to skip NexusDI.
- After: NexusDI is a DI container for any TypeScript app. The README and the landing
  page feature the two strongest shapes as guides (one graph shared by an API, a worker
  and a CLI; a shell with sections from several teams) and end with a short "when you do
  not need a container" section (section 14.1).
- Pillars: P2, P5; the first pillar names a general-purpose container.
- 0.3 user and new user: the docs address the single app they are building.
- Size: 0.

### D7. Lead with modules and async startup

- Before: the launch claim led with "no reflect-metadata, any transpiler, TS 7 ready".
- After: the lead is "NestJS-style modules and async startup for any TypeScript app,
  checked before it runs, with no compiler flags". "No reflect-metadata" and TS 7
  support become supporting facts, because TS 7 and Vite 8 emit legacy decorator
  metadata and every legacy-decorator library also runs on TS 7 (section 14.1).
- Pillars: P3, P4, P8, P1.
- Users: no code change. Size: 0.

### D8. The first docs page uses classes as tokens

- Before: every example a user reads was interface-first, so the first page declared an
  interface, a token and a binding per service.
- After: the README hero and the docs' Getting started use classes as tokens (D1's
  five-line app). Interfaces, `Token<T>` and `provide(TOKEN, { useClass })` start on the
  second page, with one sentence on why a test or an environment swap wants them. Every
  later page, and every example in this spec, stays interface-first (section 3).
- Pillars: P2.
- Users: no code change. Size: 0.

### D9. Optional features ship as separate packages

Changed by the owner from the audit's subpath proposal. The package split below gives
the design.

- Before: one package, `@nexusdi/core`, with the `/testing` and `/node` subpaths and the
  decorators in its main entry.
- After: `@nexusdi/core` plus six optional packages: `@nexusdi/decorators`,
  `@nexusdi/testing`, `@nexusdi/node`, `@nexusdi/errors`, `@nexusdi/devtools` and
  `@nexusdi/federation`. Each has an exact peer dependency on `@nexusdi/core` and uses
  only core's public API: the plugin API of D19 and, for `@nexusdi/decorators`, the class
  metadata functions.
- Pillars: P6 (a feature the app does not install adds no bytes), P2 (the core API a new
  user sees shrinks), P3 and P8 unchanged.
- 0.3 user: a project that keeps decorators installs `@nexusdi/decorators`; test code
  installs `@nexusdi/testing`. The codemod adds both to `package.json` when the migrated
  code uses them and rewrites the imports.
- New user: `npm i @nexusdi/core`; the other packages when a page needs them.
- Size: the packages hold est. 3.1 to 3.9 KB that revision 1 put in every bundle (the
  feature placement table).

### D10. `scope.extend()` before rc.0

- Before: a scope was pinned to the blueprint current at its creation, and a token from a
  later `load()` threw `NEXUS_LOADED_AFTER_SCOPE` for the scope's whole life. Lazy routes
  with an ambient scope answered their first request with a designed 500.
- After: `await scope.extend()` re-pins the scope to the current blueprint and builds the
  scoped factories the new modules contribute (section 7.4). Pinning stays the default.
- Pillars: P3 (late loading works with scopes), P8.
- 0.3 user: nothing to change; 0.3 had no working scopes.
- New user: the framework adapters call `extend()` after `di.load()`; direct users call
  it when a request outlives a `load()`.
- Size: est. 0.3 KB.

### D11. `eager: false` for sync providers, in the RC window

- Before: every singleton was built at `create` and every scoped factory at
  `createScope`, needed or not. A scoped database client opened on `/health`.
- After: `provide(T, { ..., eager: false })` on a singleton or a scoped factory builds it
  at its first `get()`. The type rejects `eager: false` on an async factory and on a class
  with an async `onInit`; a JavaScript factory that returns a thenable at that first
  `get()` throws `NEXUS_LAZY_ASYNC` (sections 3.2 and 6.6). Eager stays the default, so
  wiring failures still show at boot. It ships in an RC, before 0.4.0 final.
- Pillars: P8 (async stays at `create`), P2 (opt-in), P5 (cold starts).
- 0.3 user: 0.3 built everything lazily; a user who relied on that adds `eager: false` to
  the providers with expensive or side-effecting constructors. The migration guide names
  this, and the codemod adds nothing.
- New user: meets it on the performance and serverless pages.
- Size: est. 0.2 KB.

### D12. One size method, gated in CI

- Before: the audit found two figures for one build (16.2 KB and 17.0 KB); the larger one
  came from a CommonJS-typed test project whose esbuild wrappers add about 0.9 KB.
- After: one method, an ESM consumer (`"type": "module"`), esbuild `--bundle --minify
--format=esm`, gzip level 9, and one fixture, the two-service app. The CI job, the
  README figure and the launch's size column all use it (section 17.2).
- Pillars: P6, P5 (honest numbers).
- Users: no code change. Size: 0.

### D13. Node 22.12 floor and ESM only, kept

- Before and after: `engines.node` is `>=22.12`, ESM only, no CommonJS build (section 12).
- Pillars: P1, P6.
- 0.3 user: 0.3.2 allowed Node 20. Node 20 and Node 22.0 to 22.11 users stay on 0.3.x,
  which gets security, crash and data-loss fixes (section 14), until they upgrade Node.
  The rc.0 announcement states the floor in its first lines.
- Size: 0.

### D14. Module encapsulation and strict root `get()`, kept

- Before and after: a module sees its own providers, its imports' exports and the global
  modules' exports; root `get()` sees what the root module sees (section 3.4).
- Pillars: P3, P5.
- 0.3 user: 0.3 read no `exports`, so code that relied on the flat map breaks with
  `NEXUS_MISSING_PROVIDER` or `NEXUS_NOT_VISIBLE`. The `module-exports` transform adds
  the `exports` and `imports` of a static graph.
- Size: 0.

### D15. Core errors carry codes and fields, and `@nexusdi/errors` adds the text

- Before: every error carried a full message with a `Fix:` line and near-miss
  suggestions, about 3.5 KB of every bundle.
- After: `@nexusdi/core` throws each error with its code, every structured field of
  section 9, and a one-line message: the code, the fields as `key=value` pairs, and the
  docs link for the code. The `errors()` plugin from `@nexusdi/errors` formats revision
  1's messages, fix lines, near-miss suggestions and `BlueprintError` text, character for
  character, through the `formatError` hook (section 9.1). `devtools()` includes it.
  Codes and fields stay the stable API.
- Pillars: P6; P5 holds, because a registered `errors()` keeps every message, and the
  one-line message links to the page that explains the code.
- 0.3 user: code that matched 0.3 message text already gets the `error-message-match`
  TODO. A project that wants full text registers `errors()` or `devtools()`.
- New user: the Getting started page registers `devtools()` in development, one line.
- Size: est. 2.4 to 3.2 KB saved, counted in the placement total.

### D16. Tokens, `@Injectable` and the modifiers, kept

- Before and after: typed `Token<T>` and `MultiToken<T>`; no symbol or string tokens;
  `@Injectable`, `@Inject(T) accessor` and `@Module` as optional standard decorators, now
  in `@nexusdi/decorators`; `optional()`, `lazy()` and `all()`.
- Pillars: P5, P1.
- 0.3 user: symbol tokens, `@Service`, `@Optional` and parameter `@Inject` go, and the
  codemod rewrites nearly all of it. `@Service(TOKEN)` loses its class-side binding;
  the module gains `provide(TOKEN, { useClass: C })`.
- Size: 0.

### D17. tsyringe and TypeDI migrations, after 0.4.0 final

- Before: no plan.
- After: `@nexusdi/codemod` gains `tsyringe` and `typedi` migrations beside `0.4` after
  0.4.0 final. The 0.4 plan does not include them (section 15).
- Pillars: P5, P1.
- Users: none in 0.4. Size: 0.

### D18. `@nexusdi/react` in 0.4, the Academy after 0.4.0 final: revised by owner

- Before: `@nexusdi/react` and the Academy missions both shipped in the RC window.
  The audit proposed moving both after 0.4.0 final, because the maintenance budget is
  5 to 10 hours a week.
- After: `@nexusdi/react` ships in 0.4, before 0.4.0 final. It gets its own spec after
  this revision and targets rc.0 with the other adapters. The Academy missions move to
  after 0.4.0 final, because they teach APIs that must be settled first. The docs site,
  with the Playground and the concept consoles, stays in the RC plan (section 14).
- Pillars: P5 (a React user gets the adapter at launch), P2 (the missions teach one
  stable API).
- 0.3 user and new user: no code change. The missions arrive after the APIs they teach
  stop moving.
- Size: 0 for core. The size report measures `@nexusdi/react` like the other packages.

### D19. A public plugin system (owner, after the audit)

- Before: no extension point. `/testing` reached the compiler through a package-private
  `internal.ts`. `trace` and `scopeContext` were `create` options, and issue #19 was out
  of scope.
- After: `Nexus.create(root, { plugins: [devtools(), myPlugin] })` registers plugins in
  order, and core validates each one at `create`. A plugin is a plain object with a
  `name`, an `apiVersion` and optional hooks: compile rewrites and checks, a token key
  mapping, a construct hook that may wrap an instance, event observation, error
  formatting, contributed modules, `setup`, an `onInit` switch and `dispose`
  (section 3.10). `@nexusdi/testing`, `@nexusdi/errors`, `@nexusdi/devtools`,
  `@nexusdi/federation` and the framework adapters use this API and nothing else. The
  `trace` and `scopeContext` options of `create` go: `trace(fn)` from `@nexusdi/devtools`
  replaces the first, and the ambient scope moves out of core (next entry).
- Pillars: P5 (one documented way to extend the container), P3 (a plugin contributes
  modules and never bypasses encapsulation), P6 (optional features are packages, and
  core runs one length test per hook site when no plugin is registered), P2 (an app with
  no plugin writes nothing new).
- 0.3 user: 0.3 had no plugins. Nothing to write.
- New user: the Getting started page adds `plugins: [devtools()]` in development. A
  plugin author reads section 3.10.
- Size: registration, validation, dispatch and the read-only views, est. 0.4 to 0.6 KB,
  counted in the placement table's total. With no plugin registered, the benchmark of
  section 17.3 asserts that `create`, `get` and `createScope` run no slower than a build
  without the hook sites, within its noise bound.

Section 3.10.8 maps every open feature issue to core or to a plugin, and names the hooks
each needs. Issue #19 was concept input only. Where this design departs from it:

- "DynamicModules as plugins": dropped. A module holds providers and cannot observe
  construction, format an error or rewrite the graph before validation, so modules stay
  the unit of providers, and a plugin is a container extension that may contribute
  modules.
- A plugin discovery registry in the docs or a CLI: dropped for 0.4. Runtime discovery,
  such as scanning `node_modules`, breaks explicit registration and every bundler. The
  docs list the first-party plugins, and third-party packages use the npm keyword
  `nexusdi-plugin`, which a later registry page can read.
- "Publish and document official and community plugins": kept. The first-party packages
  are the official set, and the plugin-author guide (section 3.10) is the contract a
  community plugin follows.

### D20. The ambient scope leaves core (follows from D19 and the placement rule)

- Before: `ship.runInScope(scope, fn)` and `ship.currentScope()` on `Nexus`, backed by a
  `ScopeContext` passed to `create`, and `NEXUS_NO_SCOPE_CONTEXT` when none was passed.
- After: core has no ambient scope. `@nexusdi/node` exports `nodeScopes()`, an object with
  `run(scope, fn)` and `current()` over one `AsyncLocalStorage` (section 7.3). It needs
  no core hook, because no core code reads the current scope: a lazy thunk resolves in
  the container that built its owner (section 3.3). `runInScope`, `currentScope`,
  `CreateOptions.scopeContext`, the `ScopeContext` type and `NEXUS_NO_SCOPE_CONTEXT`
  leave core. These are removals from revision 1's API, and no release has shipped them.
- Pillars: P6 (zero core bytes), P2 (a server that wants an ambient scope imports one
  function from the package that owns `AsyncLocalStorage`).
- 0.3 user: 0.3 had no ambient scope. Nothing to write.
- New user: `const scopes = nodeScopes()`, then `scopes.run(shuttle, () => dispatch(req))`
  and `scopes.current()?.get(T)`.
- Integrations: the adapters take the `nodeScopes()` object where they called
  `ship.runInScope`. The integrations spec needs that edit.
- Size: est. 0.1 KB out of core.

### D21. One error class (owner, after the audit)

- Before: `NexusError` was an abstract base with about 24 subclasses, one per code
  family (`MissingProviderError`, `ProviderError`, `BlueprintError` and the rest), each
  with its fields as own properties. Packages subclassed it for their codes.
- After: one concrete class. Every error core or a package raises is a `NexusError` with
  a `code` and a `fields` object typed by the code (section 9):

  ```ts
  try {
    await Nexus.create(Meridian);
  } catch (error) {
    if (isNexusError(error, 'NEXUS_MISSING_PROVIDER')) {
      error.fields.token; // string
    }
  }
  ```

  `isNexusError(value, code?)` narrows `fields` to the code's shape. `error.code ===
'NEXUS_MISSING_PROVIDER'` works for code that reads no field. A package declares its
  codes' fields by augmenting the `NexusErrorFields` interface, and no package
  subclasses `NexusError`. The subclasses and their names leave the public API, and the
  fields move from the error to `error.fields`. `cause` stays the standard
  `Error.cause`.

- Pillars: P6 (one class where 24 were), P2 (one way to test an error), P5 (the guard
  narrows the fields; it also works across two copies of core, where `instanceof` fails,
  because it checks the brand `Symbol.for('nexusdi.error')`).
- 0.3 user: `catch (e) { if (e instanceof NoProvider) ... }` becomes
  `isNexusError(e, 'NEXUS_MISSING_PROVIDER') || isNexusError(e, 'NEXUS_NOT_VISIBLE')`,
  and `InvalidToken`, `InvalidProvider` and `InvalidModule` become a guard with their
  code. `instanceof ContainerException` becomes `instanceof NexusError`, which still
  works. The codemod's `imports` transform rewrites each `instanceof` of a 0.3 error
  class into the guard and adds the import; any other use of a 0.3 error class, such as
  `new NoProvider()` or a subclass, gets the TODO `error-class-use`.
- New user: learns `isNexusError(error, code)` from the errors page. Code written against
  revision 1 needs no migration, because no release shipped it.
- Size: est. 0.4 to 0.8 KB saved, unmeasured; the size report shows the figure when the
  plan step merges.

### Feature placement

The owner's rule: core carries no unnecessary bloat, and teams that need more add
plugins and accept their weight. Every feature planned for 0.4 stays in 0.4. A
feature stays in core only when a pillar needs it there, and then the diagnostics still
move to a plugin. A plugin feature costs core nothing beyond the plugin dispatch counted
once, in the plugin API row.

| Whole-graph validation (the six passes)                     | core; its text in `@nexusdi/errors`                           | the D7 headline: every wiring error before any constructor runs                                                                                                                | baseline; the text 0                                 |
| Async startup, sync `get()`, levels, `onInit`               | core                                                          | P8                                                                                                                                                                             | baseline                                             |
| Scopes, `REQUEST`, `createScope`                            | core                                                          | P8 and P3: the compiler checks lifetimes across them                                                                                                                           | baseline                                             |
| `load()`                                                    | core                                                          | P3: validated late loading                                                                                                                                                     | baseline                                             |
| `scope.extend()` (D10)                                      | core                                                          | it re-pins scope state and runs the scope builder, both core internals, and `load()` is core                                                                                   | est. 0.3 KB                                          |
| Disposal                                                    | core                                                          | the runtime owns creation order                                                                                                                                                | baseline                                             |
| Multi providers and the modifiers                           | core                                                          | they are graph edges the compiler validates, and the deps types depend on them                                                                                                 | baseline                                             |

## 1. Problem

0.3.1 is the version on npm. It has four structural defects that no patch fixes.

The container is mutable at any time. `set()` works before and after the first `get()`,
so no code can validate the graph as a whole. The first `get()` that reaches a missing
provider throws, and in a server that `get()` runs in the first request down that path.

The container has no graph. `resolve()` reads `@Inject` metadata at call time. Cycles
are not detected at all on `fix/core-export-map`, and on `archive/async-container` a `Set`
of in-progress tokens reports a cycle whenever two concurrent `get()` calls reach the same
token.

Modules do not encapsulate. `processModuleConfig` in `libs/core/src/container.ts` copies
every provider of every imported module into one flat `Map`, and nothing reads `exports`.
A provider that `Engineering` keeps private is visible to `Tactical`.

The decorators depend on TypeScript's legacy decorator mode. `@Inject` is a parameter
decorator, which needs `experimentalDecorators: true`. Standard decorators have no
parameter decorators.

The async branch tried to fix the lifetimes and made `get()` return a promise. Every call
site became `await`, and the branch added defects of its own. Section 16 lists the
defects of both lines as regression tests. The branch is archived and nothing from it is
merged.

0.4 rebuilds the engine. The repo adopts the libraries repo's quality bar with it: type
tests, README doctests, a packed-consumer check, and a spec per change.

The owner judges every choice by what a DI container user expects. The container wires
classes without boilerplate. Lifetimes behave predictably. Tests override any provider
easily. Shutdown is clean. Errors say what to fix. A user never needs to know whether a
provider is sync or async.

## 2. Decisions

1. The engine has layers. The compiler turns definitions (pure, typed data) into a
   blueprint (an immutable, validated graph), and the runtime builds instances from the
   blueprint. Each layer imports only from the layers below it (section 12).
2. Packages: `@nexusdi/core` holds definitions, the compiler, the runtime and the plugin
   API. The optional features are separate packages built on that API (section 0,
   feature placement).
3. `await Nexus.create(root, options?)` compiles and builds the container, then seals it.
   `root` is a module, a provider array or `{ providers, imports, exports }`. There is no
   `set()`. `await ship.load(Module)` adds a lazily-loaded module after startup.
4. A token is a class or a `new Token<T>(description)`. `MultiToken<T>` collects many
   providers and resolves to `T[]`. Symbol and string tokens are removed.
5. The core is decorator-free. The primary form is a class with `static deps` and a
   module that binds tokens with `provide()` (section 0, D2), and TypeScript checks every
   deps tuple against the constructor that receives it. `@Injectable`, `@Inject` and
   `@Module` are optional sugar over the same definitions, written as standard (TC39)
   decorators, in `@nexusdi/decorators`.
6. `get()` and `has()` are synchronous everywhere. Async work happens only in
   `Nexus.create`, `load` and `createScope`.
7. Lifetimes are `singleton` (the default), `scoped` and `transient`. The compiler
   rejects a singleton that captures a scoped dependency.
8. `lazy(T)` is the only way to express a dependency cycle. There is no `forwardRef`.
9. Lifecycle is `onInit()` plus the standard `Symbol.asyncDispose` and `Symbol.dispose`.
   The container itself disposes only through `[Symbol.asyncDispose]()`. It has no
   `dispose()` method.
10. Every error extends `NexusError` and carries a stable `code` and structured fields.
    Compilation reports all of its errors at once, in one `BlueprintError`. Core's message
    is one line; `@nexusdi/errors` formats the full text (section 9).
11. `graph(ship)` from `@nexusdi/devtools` returns the compiled graph as plain JSON, and
    `trace(fn)` receives typed lifecycle events (section 10).
12. Migration from 0.3 is a full guide plus a published codemod, `@nexusdi/codemod`.
13. 0.4 is released as `0.4.0-rc.N` on the `next` dist-tag first (section 14).
14. The TypeScript floor is 5.4. The Node floor is 22.12, the first 22.x release that
    loads an ES module through `require()` without a flag (section 12).
15. `resolve(deps)` on a scope and the root, and `ship.validate(deps)`, resolve and check a
    deps map or tuple with the rules of a factory's deps (section 3.9).
16. `providers` accepts plain object literals in 0.3's `{ token, ... }` shape beside bare
    classes and `provide()` results. The compiler reads a literal as it reads the matching
    `provide()` call, and `defineModule` checks each literal with the rules `provide()`
    enforces (sections 3.2 and 4.6).
17. A plain class with constructor parameters declares its deps as
    `static deps = [TOKEN_A, TOKEN_B] as const`. Every class form without a `deps` option
    reads it, and an explicit `deps` option wins as a whole (section 3.2).
18. Core has no legacy `emitDecoratorMetadata` mode. Interface-first injection cannot use
    `design:paramtypes`, because TypeScript emits `Object` for a parameter typed with an
    interface, and core stays free of compiler flags. `static deps`, `@Injectable` and
    `provide()` cover every class (sections 3.2 and 15).
19. Plugins extend the container through one public, versioned API, registered at
    `create` (section 3.10). First-party packages use no other door into core.

### 2.1 Why the core has no decorators

At the May 2026 plenary, TC39 moved Decorators and Decorator Metadata back to Stage 2.7.
No engine implements either. `Symbol.metadata` is `undefined` on Node 22, 24 and 26. A
container whose only wiring mechanism is decorator metadata therefore depends on
TypeScript's or a bundler's downlevel emit plus a polyfill, on every runtime, for the
foreseeable future.

TypeScript 5.2 and later check a typed deps tuple against a constructor. The pattern
`Injectable<C>({ deps: Tokens<ConstructorParameters<C>> })` was verified on TS 5.2, 6
and 7: a deps entry of the wrong type, or a missing entry, is a compile error at the
call site. So a plain function call gives the safety that `emitDecoratorMetadata`
promised, with no metadata and no compiler flag.

`provide()` is that function. The decorators remain because users of NestJS and Angular
expect them, and they write exactly the definition `provide()` writes. `NoInfer` (TS
5.4) keeps `useValue` from widening `T`, which sets the floor at 5.4.

The decorators live in `@nexusdi/decorators`. Its README says in its first section that
they need the standard decorator mode. A project that keeps `experimentalDecorators` for
TypeORM or NestJS uses `static deps`, `provide()` and `defineModule()`.

### 2.2 Why `get()` is synchronous

With a synchronous `get()`, the user awaits only `Nexus.create`, `load` and
`createScope`. The async branch showed the alternative. Once `get()` returned a promise,
every constructor that wanted a dependency lazily had to become async, and a user had to
know which providers were async to know where to put `await`.

The runtime therefore builds every singleton at `create`, awaiting async factories.
`createScope` builds every scoped factory before it returns (section 7.2). After that,
every value `get()` can return already exists or can be built synchronously. A transient
cannot have an async factory, because `get()` would have nothing to await; the type of
`provide()` rejects it (section 4.3).

### 2.3 Why the container is sealed

A sealed container has a whole graph to validate. `create` reports every missing
provider, dependency cycle, lifetime violation and module import cycle before any
constructor runs. `set()` after startup makes that impossible, and 0.3's `set()` also
silently replaced providers that other singletons already held.

Other APIs cover what `set()` was used for. A hello world passes a provider array to
`Nexus.create`. Tests use `createTestingContainer(...).override()` from
`@nexusdi/testing`. Code-splitting and micro-frontends use
`load()`, which validates the new module against the live graph before it builds
anything. Per-request values use scopes and the `REQUEST` token.

### 2.4 Decisions settled after review

The owner accepted these after the first review. Each one is specified where the section
reference points.

1. A singleton may depend on a transient when the transient's closure, followed through
   transients and aliases, reaches no scoped provider and no `REQUEST` (section 5, pass 5).
2. In a deps tuple, a `MultiToken` must be wrapped in `all()` (section 3.3).
3. A module's own provider shadows an imported export of the same plain token
   (section 3.4).
4. A scope is pinned to the blueprint current at its creation. A token loaded later
   throws `NEXUS_LOADED_AFTER_SCOPE` until the scope calls `extend()` (sections 7.1 and
   7.4).
5. Superseded by D20: the ambient scope lives in `@nexusdi/node`, which has no
   unconfigured state (section 7.3).
6. `onInit` runs for singletons only (section 8.1).
7. `@Module` classes are not configurable: they have no `forRoot`. Configurable modules
   use `defineModule` (section 3.8).
8. A second polyfill file defines `Symbol.dispose` and `Symbol.asyncDispose`, and the
   runtime falls back to an internal `SuppressedError` class (sections 8.2 and 12).
9. The 0.3 docs stay at `/v0.3/` for six months after 0.4.0 final, or until 0.5.0 is
   released, whichever is later (section 14).
10. `override()` of a plain token replaces every provider of that token (section 11).
11. Scopes do not nest in 0.4 (section 3.6).
12. The codemod keeps its transforms for the async-branch-only APIs (section 13.2).

## 3. The public API

The docs use the Starship Meridian. The README hero and the Getting started page use
classes as their own tokens (section 0, D8):

```ts
import { Nexus } from '@nexusdi/core';

class Logger {
  log(line: string) {
    console.log(line);
  }
}
class UserService {
  static deps = [Logger] as const;
  constructor(readonly logger: Logger) {}
}

const app = await Nexus.create([Logger, UserService]);
app.get(UserService).logger.log('ready');
```

Every other page, and every example in this spec, is interface-first. Each service
has an interface and a token (`IReactorCore` and `REACTOR`, `IShipComputer` and
`COMPUTER`, `INavCharts` and `NAV_CHARTS`, `ISubspaceLink` and `SUBSPACE_LINK`,
`IFlightLog` and `FLIGHT_LOG`). A class implements an interface and depends on tokens,
and no concrete class depends on another concrete class. `FusionReactor` and
`ShipComputer` are singletons. `SurveyDrone` is transient. A shuttle launched from the bay
is a scope, and `ShuttleFlightLog` is scoped to it. `NAV_CHARTS` is built by an async
factory fed from `SUBSPACE_LINK`. A reactor scram is disposal. `Engineering`, `Tactical`
and `Comms` are modules, and `Comms` takes a frequency through `forRoot()`. `ShieldGrid` and
`PowerRouter` form the cycle. Tests swap in `FakeReactor`, `fakeCharts` and
`MemoryFlightLog` (section 11).

The modules in section 3.4 bind these classes to their tokens. The provider forms:

| Form                                                                | Kind in `graph()` | Notes                                                                                        |
| ------------------------------------------------------------------- | ----------------- | -------------------------------------------------------------------------------------------- |
| `provide(C)`                                                        | `class`           | Only for a class whose constructor takes no parameters.                                      |
| `provide(C, { deps, lifetime? })`                                   | `class`           | `deps` is checked against `C`'s constructor.                                                 |
| `provide(T, { useClass, deps?, lifetime? })`                        | `class`           | `useClass` must produce a `T`. Without `deps`, reads the class's declared deps.              |
| `provide(T, { useValue })`                                          | `value`           | `useValue` is typed `NoInfer<T>`. `undefined` is a valid value. The value is never disposed. |
| `provide(T, { useFactory, deps?, lifetime? })`                      | `factory`         | Sync or async. The container awaits a returned thenable. `deps` defaults to `[]`.            |
| `provide(T, { useExisting })`                                       | `alias`           | Resolves to the target's instance. It has no lifetime of its own.                            |
| `provide(M, { useClass \| useValue \| useFactory \| useExisting })` | as above          | `M` is a `MultiToken<T>`. Each call contributes one element.                                 |
| `C` (bare class in `providers`)                                     | `class`           | Uses `C`'s `@Injectable` metadata, or no deps when `C` takes no parameters.                  |
| `{ token: C, deps?, lifetime? }`                                    | `class`           | The literal form of `provide(C, { deps, lifetime })`.                                        |
| `{ token: T, useClass: C, deps?, lifetime? }`                       | `class`           | As `provide(T, { useClass })`.                                                               |
| `{ token: T, useValue: v }`                                         | `value`           | As `provide(T, { useValue })`.                                                               |
| `{ token: T, useFactory: fn, deps?, lifetime? }`                    | `factory`         | As `provide(T, { useFactory })`. `deps` defaults to `[]`.                                    |
| `{ token: T, useExisting: U }`                                      | `alias`           | As `provide(T, { useExisting })`.                                                            |
| `{ token: M, ... }`                                                 | as above          | `M` is a `MultiToken<T>`. Each literal contributes one element.                              |

`lifetime` defaults to `'singleton'`. `useValue` and `useExisting` take no lifetime.

A class or factory provider with lifetime `singleton` or `scoped` also takes
`eager?: boolean`, default `true`. `eager: false` builds the provider at its first
`get()`, where the default builds a singleton at `create` and a scoped factory at
`createScope` (section 6.6). The type rejects `eager: false` on an async factory, on a
class whose `onInit` returns a promise, and on a transient. A scoped class already
builds on first use, so `eager: false` changes nothing for it.

A provider literal is an object that sets `token` on itself, in the shape 0.3 used. The
compiler reads a literal and a `provide()` options object through one function, so a
literal and the `provide()` call with the same fields produce the same provider record,
the same `graph()` entry and the same errors. The same rules hold for both:

- The compiler reads own properties only: `token`, `deps`, `lifetime`, `useClass`,
  `useValue`, `useFactory` and `useExisting`. A key that only the prototype chain
  supplies is not an option, and an object whose `token` is inherited is not a literal
  (SEC-003).
- The compiler ignores every other key. A JavaScript caller, or a config loaded from
  JSON, may carry extra keys, and they change nothing. The TypeScript type of
  `providers` rejects an unknown key (section 4.6), so a typo such as `lifeTime` fails in
  the editor.
- A literal with no definition key is a class provider of `token`, as `provide(C, {...})`
  is. It never reads `@Injectable` metadata; a bare `C` does.
- A malformed literal is `NEXUS_INVALID_PROVIDER` with the module and the element index,
  for example `Engineering.providers[3] sets useValue and useFactory; use one of them.`

`provide()` stays the form the docs recommend. It types a factory's parameters from
`deps`, and a literal cannot (section 4.6).

When a class has `@Injectable` metadata, a bare `C` in `providers` uses that metadata,
and `provide(C, { deps, lifetime })` uses the explicit options as a whole, with no
merging. `provide(C)` with no options type-checks only for a class that takes no
parameters or declares `static deps`, and it never reads `@Injectable` metadata.

A plain class declares its deps without a decorator as a static field, as
`ShipComputer` above does with `static deps = [REACTOR] as const`.

Every class form without a `deps` option reads `static deps`: a bare `C`, `provide(C)`,
`provide(C, { lifetime })`, `{ token: C }` and `useClass: C`. A bare `C` and
`useClass: C` also read `@Injectable` metadata, so `provide(COMPUTER, { useClass: C })`
and `{ token: COMPUTER, useClass: C }` take the deps `C` declares either way. An explicit
`deps` option wins as a whole. The rules:

- The compiler reads `deps` as an own property of the class, or of the nearest parent
  class that has one, and stops before `Function.prototype`. A `deps` key that only
  `Function.prototype` or `Object.prototype` carries is never a declaration (SEC-012).
- Inheritance follows the `@Injectable` rules in section 3.8. A subclass with its own
  `static deps` uses them. A subclass without them inherits its parent's constructor
  deps, and the type check reports it when those do not fit the subclass's constructor.
- `@Injectable({ deps })` and `static deps` on one class, own or inherited, is
  `NEXUS_INVALID_PROVIDER` naming both. A precedence rule would let one declaration
  shadow the other without a word, and the two drift apart when either is edited, so
  the compiler makes the author keep one. `@Injectable({ lifetime })` without `deps`
  beside `static deps` is valid: the lifetime comes from the decorator.
- A `static deps` that is not an array, or whose getter throws, is
  `NEXUS_INVALID_PROVIDER`.
- A `useClass` binding without `deps` takes its lifetime from the binding, never from
  `@Injectable`. When the class declares no deps and takes parameters, pass 1 reports
  `NEXUS_MISSING_DEPS` naming the class, the token and the fix: add `deps` to the
  binding, `static deps` to the class, or `@Injectable`.

A bare class with constructor parameters, no `static deps` and no `@Injectable` metadata
is the compile error `NEXUS_MISSING_DEPS`. The compiler reads `C.length`, which does not
count parameters with defaults or rest parameters, so the docs state that such a class
needs `static deps`, `provide(C, { deps })` or `@Injectable` to have them injected.

### 3.3 Dependency modifiers

| Modifier      | Resolves to      | Edge kind in `graph()` | Notes                                                                                   |
| ------------- | ---------------- | ---------------------- | --------------------------------------------------------------------------------------- |
| `T`           | `T`              | `required`             |                                                                                         |
| `optional(T)` | `T \| undefined` | `optional`             | Resolves to `undefined` when no provider of `T` is visible.                             |
| `lazy(T)`     | `() => T`        | `lazy`                 | The only way to express a cycle. The compiler excludes lazy edges from cycle detection. |
| `all(M)`      | `T[]`            | `all`                  | `M` is a `MultiToken<T>`. An empty array when nothing contributes.                      |

In a deps tuple, a `MultiToken` must be wrapped in `all()`. The `Dep` type excludes a
bare `MultiToken`, so the graph always records a dependency on one as an `all` edge.
`get(M)` returns `T[]`.

A `lazy` thunk resolves in the container that built its owner: the root for a singleton
or a root-level transient, the scope for anything a scope built. Each call calls `get()`
on that container. A thunk called before its target is ready throws `NEXUS_NOT_READY`
(section 6.3).

### 3.4 Modules

```ts

```

`Engineering` does not import `Comms`, so `DiagnosticsPanel` receives `undefined` for its
optional `SUBSPACE_LINK`.

Only the bindings name the classes. `ShipComputer`, `DiagnosticsPanel` and `SurveyDrone`
depend on `REACTOR`, `SUBSPACE_LINK` and `COMPUTER`, so a simulator build swaps the
reactor by binding `REACTOR` to another class, and a test replaces it with `FakeReactor`
through `override()` (section 11). No consumer changes in either case.

`defineModule({ name, imports?, providers?, exports?, global?, options?, schema? })`
returns a frozen `ModuleDefinition`. An entry of `providers` is a bare class, a
`provide()` result or a provider literal (section 3.2).

A module sees three sets of providers: its own, the exports of the modules it imports,
and the exports of every `global: true` module. For a plain token, a module's own
provider shadows an imported export of the same token, as in NestJS. When two
imports both export a plain token, the compiler reports `NEXUS_AMBIGUOUS_PROVIDER` in
the importer. Modules can re-export each other in a cycle, for example when a global
module re-exports the modules that import it. The compiler settles visibility one
strongly connected component of re-exports at a time, so a cycle compiles in linear time,
and when a plain token has two providers inside a cycle, every lookup of it in the cycle
reports `NEXUS_AMBIGUOUS_PROVIDER` (SEC-009).

`MultiToken` contributions never conflict. A module sees the union of its own
contributions and every contribution its imports and the global modules export, in
module walk order and then declaration order. No contribution shadows another.

The same token provided in two modules produces two providers and, for singletons, two
instances. Two providers of the same plain token in one module are the compile error
`NEXUS_DUPLICATE_PROVIDER`. One entry listed twice in a module's `providers`, the same
class or the same `provide()` result by reference, is one provider, as one module
imported twice is one module; two distinct entries for one plain token still raise
`NEXUS_DUPLICATE_PROVIDER`.

`exports` lists tokens the module provides or can see through an import, or modules it
imports. A module that exports an imported module re-exports every export of that
module, and the importer receives the same provider instances (regression R03). An
export of a token the module cannot see is `NEXUS_INVALID_EXPORT`. A module that exports
a `MultiToken` exports every contribution it sees.

A configurable module declares `options: Token<Opts>` and optionally `schema`, and gets
two static methods, named as in NestJS:

```ts
Comms.forRoot({ frequency: 1420 });
Comms.forRootAsync({
  useFactory: async (vault) => ({
    frequency: await vault.read('comms/frequency'),
  }),
  deps: [VAULT],
});
```

`Mod.forRoot(value)` returns a new module instance that provides the options token with
`value`, typed `NoInfer<Opts>`. `Mod.forRootAsync({ useFactory, deps? })` returns one
whose options provider is that factory, sync or async, typed as `provide()` types a
factory: `deps` defaults to `[]`, and the factory's parameters come from `deps`. Two
methods keep a value and a factory apart by name, so an options object that holds a
`useFactory` function is a value. Each instance keeps every other field of the
definition (regression R13). The options token is private to the instance unless the
definition exports it. When a module imports a configurable module without `forRoot` or
`forRootAsync`, the compiler reports `NEXUS_MODULE_OPTIONS_MISSING`.

The runtime validates options with `schema['~standard'].validate()` when it builds the
options provider during `create` or `load`, so a factory form is validated after it
resolves. A failure is `NEXUS_INVALID_MODULE_OPTIONS` and carries the schema's issues.
Core copies the Standard Schema V1 interface into its own source, as the Standard Schema
spec recommends, and takes no dependency.

The walk deduplicates modules by object identity. Two imports of `Engineering` produce
one `Engineering`. Two calls to `Comms.forRoot(...)` produce two `Comms` instances, even
with equal options, so the docs tell users to call `forRoot()` once and import the
result.

A module import cycle is the compile error `NEXUS_MODULE_IMPORT_CYCLE`, with the full
path. A value that is not a module definition or an `@Module` class, passed to
`Nexus.create`, `imports`, `load` or the `{ module }` option, is `NEXUS_INVALID_MODULE`.

### 3.5 The container

```ts
import { Nexus } from '@nexusdi/core';

await using ship = await Nexus.create(Meridian);

const computer = ship.get(COMPUTER); // IShipComputer, sync
const charts = ship.get(NAV_CHARTS); // INavCharts, built during create
const checks = ship.get(DIAGNOSTICS); // IDiagnostic[]
ship.has(SUBSPACE_LINK); // false: Comms is private to Tactical
```

```ts
class Nexus {
  static create(root: RootRef, options?: CreateOptions): Promise<Nexus>;
  static check(root: RootRef, options?: CheckOptions): void;

  get<T>(token: MultiToken<T>, options?: LookupOptions): T[];
  get<T>(token: InjectionToken<T>, options?: LookupOptions): T;
  has(
    token: InjectionToken<unknown> | MultiToken<unknown>,
    options?: LookupOptions,
  ): boolean;
  resolve<const D extends DepsMap | readonly Dep[]>(
    deps: D,
    options?: LookupOptions,
  ): ResolvedDeps<D>;
  validate(deps: DepsMap | readonly Dep[], options?: LookupOptions): void;

  load(module: ModuleRef): Promise<void>;
  createScope(options?: { request?: NexusRequest }): Promise<Scope>;

  [Symbol.asyncDispose](): Promise<void>;
}

interface LookupOptions {
  module?: ModuleRef;
}

interface CreateOptions {
  plugins?: readonly NexusPlugin[];
}

interface CheckOptions {
  plugins?: readonly NexusPlugin[];
  /** Modules to compile after the root, in order, as load() would. */
  load?: readonly ModuleRef[];
}

type ModuleRef = ModuleDefinition | (abstract new (...args: never) => unknown);

type RootRef =
  | ModuleRef
  | readonly ProviderEntry[]
  | {
      readonly providers?: readonly ProviderEntry[];
      readonly imports?: readonly ModuleRef[];
      readonly exports?: readonly (AnyToken | ModuleRef)[];
    };
```

`Nexus.create` and `Nexus.check` take the same `root`. An array is the `providers` of a
root module, and a plain object with only `providers`, `imports` and `exports` keys is
the config of one. Core compiles either as a module named `root`, which appears under
that name in errors and in `graph()`. The object form takes no `name`, `global`,
`options` or `schema`; another own key is `NEXUS_INVALID_MODULE`. The array's elements
are checked per element, as a module's `providers` are (section 4.6).

`Nexus.check(root, options?)` runs the compiler of section 5 on `root`, then on each
module of `options.load` against the result, as `load()` would, and returns nothing when
every compile passes. It throws one `BlueprintError` otherwise. It builds nothing and
calls no user code except the plugins' compile hooks, so options schemas do not run. A
CI test calls it for every environment's graph, and `inspect()` in `@nexusdi/devtools`
reads the graph it compiles.

`ModuleRef` accepts a class decorated with `@Module` from `@nexusdi/decorators`.

Root `get()` is strict. It resolves only tokens visible to the root module. When the
token exists but is private to another module, `get()` throws `NEXUS_NOT_VISIBLE`, which
names the owning modules and suggests `get(T, { module: Owner })`. When no module
provides the token, `get()` throws `NEXUS_MISSING_PROVIDER`. With the `module` option,
`get()` resolves as if called from inside that module.

`has(T)` applies the same visibility rules as `get()` and constructs nothing. It returns
`true` when `get(T)` with the same options would find a binding. It reports visibility
only, so root `has()` of a scoped token returns `true` while root `get()` of it throws
`NEXUS_SCOPE_REQUIRED`. `has()` of a `MultiToken` returns `true` when at least one
contribution is visible. `has()` of a value that is not a token, such as a module class,
returns `false` (regression R16).

Root `get()` of a scoped token throws `NEXUS_SCOPE_REQUIRED`. Root `get()` of a transient
builds a new instance that the caller owns. The root does not track it, because nothing
would ever release it (regression R08). When that instance is disposable, the runtime
emits an `untracked` event to observing plugins, and the docs tell users to resolve
disposable transients inside a scope.

`load(Module)` compiles the module against the live blueprint, builds its singletons,
runs their `onInit`, and then publishes the new blueprint. The loaded module becomes an
import of the root module, so root `get()` sees its exports. Modules the loaded module
imports that already exist in the graph are reused, with their instances. The compiler
checks the root module's visibility again after the new import, and an export that
collides with another root import is `NEXUS_AMBIGUOUS_PROVIDER`. A `global: true` module
passed to `load()`, or a global module new to the graph that the loaded module imports
directly or transitively, is `NEXUS_LOAD_GLOBAL_MODULE`, because every existing module
would see new providers after its bindings were computed. A global module already in the
graph loads fine: its bindings are part of the current blueprint. When the module is already in the
graph and the root already imports it, `load()` does nothing. When the module is in the
graph but the root cannot see it, `load()` adds the root import and builds nothing.
Concurrent `load()` calls run one at a time, in call order. A compile failure throws a
`BlueprintError` and leaves the container unchanged. A build failure disposes what that
`load()` built and rethrows.

### 3.6 Scopes and `REQUEST`

```ts
declare module '@nexusdi/core' {
  interface NexusRequest {
    mission: Mission;
  }
}

{
  await using shuttle = await ship.createScope({
    request: { mission: { id: 'survey-7', target: 'Kepler-442b' } },
  });

  const drone = shuttle.get(SurveyDrone); // a new SurveyDrone
  shuttle.get(FLIGHT_LOG) === shuttle.get(FLIGHT_LOG); // true: one log per shuttle
  shuttle.get(COMPUTER) === ship.get(COMPUTER); // true
} // the shuttle docks: its scoped and transient instances are disposed
```

```ts
interface Scope {
  readonly id: string; // 's0', 's1', ...
  get<T>(token: MultiToken<T>, options?: LookupOptions): T[];
  get<T>(token: InjectionToken<T>, options?: LookupOptions): T;
  has(
    token: InjectionToken<unknown> | MultiToken<unknown>,
    options?: LookupOptions,
  ): boolean;
  resolve<const D extends DepsMap | readonly Dep[]>(
    deps: D,
    options?: LookupOptions,
  ): ResolvedDeps<D>;
  /** Re-pins the scope to the current blueprint and builds what later loads added. */
  extend(): Promise<void>;
  [Symbol.asyncDispose](): Promise<void>;
}
```

A scope's `[Symbol.asyncDispose]()` is idempotent: a second call returns the first call's
promise. Scopes do not nest in 0.4. `Scope` has no `createScope`, and every scope is a
child of the root. Nested scopes need rules for which scope owns a scoped instance and
whether an inner scope sees the outer `REQUEST`, and no use case in the approved design
needs them. A later release can add `scope.createScope()` without breaking this.

`REQUEST` is a built-in `Token<NexusRequest>` with lifetime `scoped`, visible in every
module. `NexusRequest` is an empty interface that applications extend through module
augmentation. A scope supplies it through `createScope({ request })`.

With `@nexusdi/node`, a server binds a scope to the async context of a request:

```ts
import { nodeScopes } from '@nexusdi/node';

const scopes = nodeScopes();
const ship = await Nexus.create(Meridian);

export async function handle(req: IncomingRequest) {
  await using shuttle = await ship.createScope({
    request: { mission: req.mission },
  });
  // `return await` keeps the shuttle open until dispatch settles.
  return await scopes.run(shuttle, () => dispatch(req));
}

// Deep inside dispatch():
const drone = scopes.current()?.get(SurveyDrone);
```

### 3.8 Decorator sugar

```ts
import { optional, provide } from '@nexusdi/core';
import { Inject, Injectable, Module } from '@nexusdi/decorators';

@Injectable({ deps: [REACTOR] })
export class ShipComputer implements IShipComputer {
  constructor(readonly reactor: IReactorCore) {}
}

@Injectable({ deps: [COMPUTER, MISSION], lifetime: 'transient' })
export class SurveyDrone {
  constructor(
    readonly computer: IShipComputer,
    readonly mission: Mission,
  ) {}
}

export class Bridge {
  @Inject(NAV_CHARTS) accessor charts!: INavCharts;
  @Inject(optional(SUBSPACE_LINK)) accessor link!: ISubspaceLink | undefined;
}

@Module({
  imports: [Tactical],
  providers: [provide(COMPUTER, { useClass: ShipComputer }), Bridge],
  exports: [COMPUTER, Bridge],
})
export class Command {}
```

A `useClass` binding reads the deps `@Injectable` declares, so a decorated class binds to
its interface token like any other; `useExisting` stays for aliasing one token to
another. These are standard decorators and need no compiler flag. Under
`experimentalDecorators: true`, TypeScript calls a decorator without a context object;
`@Injectable`, `@Inject` and `@Module` detect that and throw `NEXUS_LEGACY_DECORATORS`, an
error `@nexusdi/decorators` owns, whose message says to remove the flag or use
`static deps` and `provide()`. The decorators write through the class metadata functions
of section 3.10.7, so core holds no decorator code.

`@Injectable({ deps, lifetime })` writes the same definition `provide(C, ...)` builds into
`C[Symbol.metadata]`, typed against the class it decorates. A bare `C` reads its deps and
lifetime; `useClass: C` without `deps` reads its deps only. `@Inject(T)` on an `accessor`
field records a property injection. It accepts the `optional` and `lazy` modifiers. The
container sets injected properties after the constructor returns and before `onInit`.
It applies property injections to every instance it builds from a class, whether the
class came from a bare `C`, `provide(C, ...)` or `useClass`.

`@Module({...})` is sugar for `defineModule`, named
`context.name || target.name || '(anonymous module)'`. A bundler can leave both empty:
Rollup 4 drops the binding of a class nothing reads, and the class then has `name` `''`. A decorator
cannot add a typed static `forRoot()` to a class, so `@Module` classes are not configurable:
the decorator's parameter type rejects `options` and `schema`, and configurable modules use
`defineModule`. The codemod turns every `DynamicModule` subclass into `defineModule`, so
migrated code never needs the other form. `@Module` checks provider literals in
`providers` element by element, as `defineModule` does (section 4.6).

Metadata inheritance is explicit. The decorators write only own keys of the class's
metadata object, so a subclass never mutates its parent's entry (regression R10).

- A subclass with its own `@Injectable` uses its own deps. They replace the parent's.
- A subclass without `@Injectable` inherits the parent's constructor deps.
- Property injections accumulate. The container injects the parent's fields, then the
  subclass's.

### 3.9 Resolving a deps map

The framework adapters (integrations spec, decision D1) resolve a handler's dependencies as
one record per request, and check the record once, when the app starts:

```ts
import { all, lazy, optional, type DepsMap } from '@nexusdi/core';

const handlerDeps = {
  computer: COMPUTER,
  mission: MISSION,
  log: FLIGHT_LOG,
  link: optional(SUBSPACE_LINK),
  shields: lazy(SHIELD_GRID),
  checks: all(DIAGNOSTICS),
} as const satisfies DepsMap;

ship.validate(handlerDeps); // at startup; throws one BlueprintError on bad entries

// per request
const { computer, mission, log, link, shields, checks } =
  shuttle.resolve(handlerDeps);
```

`resolve(deps, options?)` takes a record of deps entries (`DepsMap`) or a deps tuple and
returns an object or tuple of the same shape. Each entry resolves exactly as a factory's
`deps` entry does: a token to its instance, `optional(T)` to the instance or `undefined`,
`lazy(T)` to a thunk with the readiness rules of section 6.3, and `all(M)` to a new
array. It is synchronous, like `get()`, and follows `get()`'s visibility rules and
`{ module }` option. On a scope it resolves with the scope's rules; on the root it follows
root `get()`, so a scoped entry throws `NEXUS_SCOPE_REQUIRED` and a transient it builds is
untracked. On the root, `lazy(T)` of a scoped `T` also throws `NEXUS_SCOPE_REQUIRED` at
`resolve`, since no call of the thunk could ever succeed there. It reads a record's own enumerable keys and defines each on the result, so a
key named `__proto__` is an entry. An entry that is not a token or a modifier, and a bare
`MultiToken`, throw `NEXUS_INVALID_TOKEN`. A required or lazy entry with no binding throws
what root `get()` would: `NEXUS_NOT_VISIBLE`, `NEXUS_MISSING_PROVIDER` or, on a scope,
`NEXUS_LOADED_AFTER_SCOPE`; a scoped entry resolved from the root throws
`NEXUS_SCOPE_REQUIRED`. Every error `resolve` or `validate` raises for an entry carries
`entry`, the entry's name (`deps.<key>` or `deps[<index>]`), and names it right after the
code; `received` still describes the value (section 9).

`validate(deps, options?)` runs the same lookups from the root module, or from
`options.module`, and builds nothing. It returns nothing when every entry passes, and
otherwise throws one `BlueprintError` (`NEXUS_BLUEPRINT_INVALID`) holding one error per
failing entry, in entry order: `NEXUS_INVALID_TOKEN`, `NEXUS_NOT_VISIBLE`, or
`NEXUS_MISSING_PROVIDER`, with near misses when `errors()` is registered. Each of them carries
the failing entry in `entry`. An optional or `all` entry never fails. Every lifetime
resolves from a scope, so `validate` reports no lifetime error; code that resolves from
the root meets `NEXUS_SCOPE_REQUIRED` at `resolve`.

The integrations spec calls these types `Deps` and `Resolved<D>`; in core they are
`DepsMap` and `ResolvedDeps<D>` (section 4.2).

### 3.10 Plugins

A plugin extends one container. It can rewrite definitions before the compiler validates
them, add compile errors, map tokens to keys, wrap instances as they are built, observe
lifecycle events, format error text, contribute modules and hold its own resources. It
cannot change a validated graph (section 3.10.9). Every first-party package that
extends the container is a plugin written against this section, with no other door into
core.

```ts
import { Nexus } from '@nexusdi/core';
import { devtools } from '@nexusdi/devtools';

const dev = process.env.NODE_ENV !== 'production';

await using ship = await Nexus.create(Meridian, {
  plugins: dev ? [devtools()] : [],
});
```

#### 3.10.1 The plugin object

```ts
export const NEXUS_PLUGIN_API = 1;

export interface NexusPlugin {
  /** Unique among one container's plugins; errors name the plugin by it. */
  readonly name: string;
  /** The plugin API version the plugin was written against. */
  readonly apiVersion: number;

  /** Modules added to the root's imports, compiled like any import. */
  readonly modules?: readonly ModuleRef[];
  /** false skips onInit at create and load. */
  readonly onInit?: false;

  /** The key the compiler and the runtime look a token up by. */
  tokenKey?(token: AnyToken): unknown;

  readonly compile?: {
    module?(
      module: ModuleDefinition,
      context: CompileContext,
    ): ModuleRef | undefined;
    provider?(
      provider: ProviderView,
      context: CompileContext,
    ): ProviderRewrite | undefined;
    check?(view: BlueprintView, report: (error: NexusError) => void): void;
  };

  construct?(
    instance: unknown,
    provider: ProviderView,
    scope: string | null,
  ): unknown;
  observe?(event: TraceEvent): void;
  formatError?(
    error: NexusError,
    view: BlueprintView | undefined,
  ): ErrorText | undefined;

  setup?(context: PluginContext): void;
  dispose?(): void | PromiseLike<void>;
}

type AnyToken = Token<unknown> | MultiToken<unknown> | Class;

interface CompileContext {
  readonly phase: 'create' | 'load' | 'check';
  /** The definition a forRoot or forRootAsync instance was made from. */
  configuredFrom(module: ModuleDefinition): ModuleDefinition | undefined;
}

type ProviderRewrite =
  | { readonly with: ProviderEntry; readonly pin?: true }
  | { readonly remove: true };

interface PluginContext {
  readonly container: Nexus;
  /** The current blueprint; a load() publishes a new one. */
  blueprint(): BlueprintView;
}

interface ErrorText {
  readonly message: string;
  readonly hints?: readonly string[];
  readonly fix?: string;
  readonly nearMisses?: readonly NearMiss[];
}
```

A plugin is a plain object, usually returned by a factory such as `devtools()`. Every
hook is optional. Core reads the hooks once, at registration, into per-hook arrays in
plugin order, so a hook added to the object later is never called.

The read-only views:

```ts
interface BlueprintView {
  readonly phase: 'create' | 'load' | 'check';
  /** false when a compile pass reported an error; the view then holds what the passes finished. */
  readonly complete: boolean;
  readonly modules: readonly ModuleView[];
  readonly providers: readonly ProviderView[];
  readonly edges: readonly EdgeView[];
  /** Provider ids of `token` visible in the module, in lookup order. */
  visible(moduleId: string, token: AnyToken): readonly string[];
}

interface ModuleView {
  readonly id: string;
  readonly name: string;
  readonly global: boolean;
  readonly imports: readonly string[];
  readonly exports: readonly string[];
  readonly definition: ModuleDefinition;
  /** The definition a compile.module hook replaced, or null. */
  readonly replaced: ModuleDefinition | null;
}

interface ProviderView {
  readonly id: string;
  readonly token: AnyToken;
  readonly name: string; // display name
  readonly module: string; // module id
  readonly kind: 'class' | 'value' | 'factory' | 'alias';
  readonly lifetime: Lifetime | null;
  readonly eager: boolean;
  /** The class a class provider constructs, or null. */
  readonly implementation: Class | null;
  /** The plugin whose compile.provider hook rewrote this provider, or null. */
  readonly rewrittenBy: string | null;
}

interface EdgeView {
  readonly from: string;
  readonly to: string;
  readonly kind: 'required' | 'optional' | 'lazy' | 'all' | 'alias';
}
```

Core builds the views only when a registered plugin has a hook that receives one, and
freezes every array and object in them. `definition`, `token` and `implementation` are
the user's own objects; the compiler has already copied what it needs from them, so a
change to one of them after compile changes nothing.

#### 3.10.2 Registration, order and versions

`Nexus.create(root, { plugins })` and `Nexus.check(root, { plugins })` validate the
array before anything else runs:

- Each element is an object with an own, non-empty string `name`, unique in the array.
- `apiVersion` is a version this core supports. Core 0.4 supports `1`. Another value is
  `NEXUS_PLUGIN_VERSION`, whose fields name the plugin, its `apiVersion` and the
  `supported` list.
- Each hook that is present has the right type: a function, the `compile` object of
  functions, a `modules` array, or `onInit: false`. Other own keys are ignored, so a
  plugin object can carry its own methods, as `devtools()` does.

Every fault is one `NEXUS_PLUGIN_INVALID` or `NEXUS_PLUGIN_VERSION`, and `create` throws
all of them in one `BlueprintError` before it compiles.

Order is the array's order, and each hook states what order means for it:

| Hook               | Order rule                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `modules`          | appended to the root's imports, plugin by plugin                                                                                     |
| `tokenKey`         | the first plugin that returns a value other than `undefined` decides                                                                 |
| `compile.module`   | the first plugin that returns a module decides; a second plugin that also returns one for the same module is `NEXUS_PLUGIN_CONFLICT` |
| `compile.provider` | as `compile.module`, per provider                                                                                                    |
| `compile.check`    | in order, after core's passes; reported errors follow core's in the `BlueprintError`                                                 |
| `construct`        | chained in order: each plugin receives the previous plugin's result                                                                  |
| `observe`          | in order                                                                                                                             |
| `formatError`      | the first plugin that returns text decides                                                                                           |
| `setup`            | in order                                                                                                                             |
| `dispose`          | in reverse order                                                                                                                     |

The plugin API is public API of `@nexusdi/core` under its semver. A change that would
break a plugin written for `apiVersion` N raises `NEXUS_PLUGIN_API` to N + 1, and core
lists the versions it still accepts in `SUPPORTED_PLUGIN_APIS`. A new optional hook, a
new field on a view and a new `TraceEvent` type do not raise it, so a plugin ignores
event types and fields it does not know. While core is 0.x, a minor release may raise
`NEXUS_PLUGIN_API`, and the check turns the mismatch into an error at `create`, before
any hook runs.

First-party plugins declare an exact peer dependency on `@nexusdi/core`. The version
check still runs for them, because a bundler can resolve two copies of core that the
package manager never saw.

#### 3.10.3 Compile hooks

The compiler (section 5) calls the compile hooks in `create`, in every `load`, and in
`Nexus.check`, with `context.phase` set to match.

- `compile.module(module, context)` runs in pass 1 for every module the walk meets,
  before the walk reads it. A returned module is walked in its place, and the hook is
  not called again for the replacement. `context.configuredFrom(module)` tells a
  `forRoot` instance from its base. `@nexusdi/testing` implements `overrideModule`, lazy
  overrides included, with this hook.
- `compile.provider(provider, context)` runs in pass 1, after the walk, for every
  provider record, before visibility. `{ with: entry }` replaces the provider: the
  compiler normalises `entry` as it normalises a module's `providers` element, and the
  record keeps its id, its module and, unless `entry` sets an own `lifetime`, its
  lifetime. `{ with: entry, pin: true }` also removes every other provider of the token
  and makes the replacement visible in every module, with its deps still bound in its
  own module. `{ remove: true }` removes the provider. `@nexusdi/testing` implements
  `override` with it: `with` for a plain token, `with` and `pin` for a `MultiToken`.
- `compile.check(view, report)` runs after pass 6, also when an earlier pass reported
  errors, with `view.complete` telling the two apart. `report(error)` appends a
  `NexusError` to the compile's errors, so the `BlueprintError` holds core's errors and
  then each plugin's, in plugin order. `@nexusdi/testing` reports
  `NEXUS_OVERRIDE_UNUSED` and `NEXUS_OVERRIDE_EXPORTS` here, and `@nexusdi/federation`
  reports `NEXUS_CONTRACT_VERSION`.

A rewrite happens before validation: passes 2 to 6 check the rewritten graph, so a
replacement that breaks a dependency, forms a cycle or violates a lifetime fails as it
would in the user's own module. A check hook can add errors and cannot remove one.

`tokenKey(token)` maps a token to the key every lookup uses, in the compiler and in
`get()`. Core calls it once per token object and caches the result in a `WeakMap`.
Without a `tokenKey` plugin the key is the token, and `get()` does no extra lookup.
Duplicate and ambiguity checks run on keys, so two tokens that map to one key collide as
two providers of one token would. `@nexusdi/federation` maps contract tokens from two
copies of a contracts package to one key.

#### 3.10.4 The construct hook

`construct(instance, provider, scope)` runs for class and factory providers, after the
constructor or the awaited factory returns and the injected properties are set, before
the runtime stores the instance and before `onInit`. It never runs for `useValue` or
`useExisting`. A return value other than `undefined` replaces the instance:

- `get()`, every consumer's deps, `onInit` and disposal see the returned object. The
  runtime tracks the returned object for disposal, so a wrapper must forward
  `Symbol.asyncDispose`, `Symbol.dispose` and `onInit`; a `Proxy` without a trap for
  them does.
- The hook is synchronous, because `get()` is. A returned thenable is
  `NEXUS_PLUGIN_FAILED`.
- A hook that throws fails the build of that provider: `create`, `load`, `createScope`
  and `get()` throw the `ProviderError` they throw for a failing constructor, whose
  `cause` is a `PluginError` (`NEXUS_PLUGIN_FAILED`, `hook: 'construct'`).

An interceptor plugin (issue #17) wraps service methods here. No 0.4 package uses the
hook, and section 3.10.8 records why it ships anyway.

#### 3.10.5 Lifecycle hooks

- `setup(context)` runs once per container, after `create` has built every singleton
  and run `onInit`, before `create` returns. `context.container` is the finished
  container, and `context.blueprint()` returns the current view, which a later `load()`
  replaces. `devtools()` records the container here, so `graph(ship)` can find it.
  `Nexus.check` calls no `setup`, and a failed `create` calls none.
- `observe(event)` receives every `TraceEvent` of section 10.2 as it happens, `compile`
  events of `Nexus.check` included. Core builds an event and reads the clock only when at
  least one plugin observes. An exception from `observe` propagates to the caller of the
  operation that emitted the event, except during disposal, which collects it with the
  disposer errors (section 8.2).
- `dispose()` runs during container disposal, after every root-owned instance, in
  reverse plugin order. Disposal awaits a returned promise and chains a thrown error
  with the disposer errors. A plugin releases its own resources here, such as a
  telemetry plugin (issue #19) that flushes its exporter after the last
  `dispose:instance` event.
- `onInit: false` makes `create` and `load` skip step 3 of section 8.1.
  `@nexusdi/testing` sets it for `create({ onInit: false })`.
- `modules` adds modules to the root's imports at `create`. They compile and validate
  like any import, may be `global: true`, and appear in `graph()`. A plugin that ships
  services with its behaviour, such as a telemetry plugin that observes events and
  provides a `TRACER` token, uses it.

Scope creation, scope disposal and `load()` have no hook that acts. `observe` sees each
of them (`scope:create`, `scope:extend`, `scope:dispose`, `compile` with
`phase: 'load'`), and a plugin that needs per-scope behaviour contributes a scoped
provider through `modules`.

#### 3.10.6 The error hook

`formatError(error, view)` supplies the text of an error that core raises in an
operation of a container, or of `Nexus.check`, that has the plugin registered. Section
9.1 gives the contract; `@nexusdi/errors` is the only first-party user.

#### 3.10.7 Class metadata functions

Decorators run when a class is defined, before any container exists, so they are not
plugins. `@nexusdi/decorators` writes class declarations through three core functions,
which a third-party decorator library may call too:

```ts
/** Declares a class's deps and lifetime on its decorator metadata object. */
export function declareClass(
  metadata: DecoratorMetadataObject,
  options: { deps?: readonly Dep[]; lifetime?: Lifetime },
): void;
/** Adds a property injection to a class's decorator metadata object. */
export function declareProperty(
  metadata: DecoratorMetadataObject,
  key: string | symbol,
  dep: Dep,
): void;
/** Makes a class a ModuleRef for the given module config. */
export function declareModuleClass(
  cls: Class,
  config: ModuleConfig,
): ModuleDefinition;
```

Core reads what they wrote from `C[Symbol.metadata]` under a key it keeps private, with
the rules of section 3.8. The functions write only own keys of the metadata object they
receive (regression R10).

#### 3.10.9 What a plugin can and cannot do

A plugin is code the application chose to run, with the application's privileges, like
any dependency. The API still keeps core's guarantees:

- It can replace or remove providers and modules before validation. It cannot change
  the blueprint after validation: views are frozen copies, and core never reads a view
  back.
- It can add compile errors. It cannot remove or downgrade one, so every graph that
  starts is a graph that passed every core pass.
- It can wrap an instance at construction. It cannot change which provider a token
  binds to, a lifetime, a level, the creation order or the disposal order, which the
  runtime records from its own build.
- It can format an error's text. It cannot change the code or the fields: core writes
  `[CODE]` at the start of the message itself, and the fields are set before the hook
  runs.
- It sees tokens, classes and module definitions through the views, and instances only
  through `construct` and `context.container`. Trace events carry no instances.
- Its failures are contained: a failing hook raises `NEXUS_PLUGIN_FAILED` naming the
  plugin and the hook, and a failed `create` still disposes what it built.

## 4. Type-level design

### 4.1 Tokens and providers

```ts
declare const TYPE: unique symbol;

export class Token<out T> {
  declare readonly [TYPE]: T;
  constructor(readonly description: string);
  toString(): string; // the description
}

declare const ELEMENT: unique symbol;

export class MultiToken<out T> {
  declare readonly [ELEMENT]: T;
  constructor(readonly description: string);
  toString(): string;
}

type Class<T = unknown> = abstract new (...args: never) => T;
export type InjectionToken<T> = Token<T> | Class<T>;

declare const PROVIDER: unique symbol;

// The opaque value provide() returns. Modules accept it in `providers`.
export interface Provider<out T> {
  readonly [PROVIDER]: T;
}
```

The `out` annotation and the phantom `[TYPE]` field make `Token<T>` covariant and
nominal in `T`. A `Token<IFusionCore>` fits where a `Token<IReactorCore>` is expected when
`IFusionCore` extends `IReactorCore`, and a `Token<string>` never fits a `Token<number>`.
The `[TYPE]` and `[PROVIDER]` fields are `declare`d, so they have no runtime presence.

`MultiToken<T>` is a separate class. If it extended `Token<T[]>`, then
`provide(DIAGNOSTICS, { useValue: [a, b] })` would type-check as a single provider of the
whole array.

### 4.2 The deps tuple

```ts
interface Optional<out T> {
  readonly kind: 'optional';
  readonly token: InjectionToken<T>;
}
interface Lazy<out T> {
  readonly kind: 'lazy';
  readonly token: InjectionToken<T>;
}
interface All<out T> {
  readonly kind: 'all';
  readonly token: MultiToken<T>;
}

type Dep =
  InjectionToken<unknown> | Optional<unknown> | Lazy<unknown> | All<unknown>;

// What a deps entry resolves to.
type Resolve<D> =
  D extends Optional<infer T>
    ? T | undefined
    : D extends Lazy<infer T>
      ? () => T
      : D extends All<infer T>
        ? T[]
        : D extends Token<infer T>
          ? T
          : D extends Class<infer T>
            ? T
            : never;
type ResolveAll<D extends readonly unknown[]> = {
  -readonly [K in keyof D]: Resolve<D[K]>;
};

// Which deps entries can supply a parameter of type P.
type DepFor<P> =
  | InjectionToken<P>
  | (undefined extends P ? Optional<Exclude<P, undefined>> : never)
  | (P extends () => infer R ? Lazy<R> : never)
  | (P extends readonly (infer E)[] ? All<E> : never);
type Tokens<P extends readonly unknown[]> = {
  readonly [K in keyof P]: DepFor<P[K]>;
};

// A record of deps entries, as resolve() and validate() take it (section 3.9).
type DepsMap = Readonly<Record<string, Dep>>;
type ResolvedDeps<D extends DepsMap | readonly Dep[]> = {
  -readonly [K in keyof D]: Resolve<D[K]>;
};
```

A class provider maps constructor parameters to accepted deps (`Tokens`). A factory maps
deps to arguments (`ResolveAll`), so its parameters are contextually typed from `deps`.

### 4.3 `provide()`

`provide()` has three overloads. With three, TypeScript prints every overload's error
when a call matches none, so the user sees the real cause.

```ts
type Lifetime = 'singleton' | 'scoped' | 'transient';
type Ctor = new (...args: any) => unknown;

// True when a class takes no parameters, or its static deps supply them.
type DeclaresDeps<C extends Ctor> =
  ConstructorParameters<C> extends []
    ? true
    : C extends { readonly deps: Tokens<ConstructorParameters<C>> }
      ? true
      : false;

// deps is optional for a class that declares its deps or takes no parameters.
type DepsFor<C extends Ctor> =
  DeclaresDeps<C> extends true
    ? { deps?: Tokens<ConstructorParameters<C>> }
    : { deps: Tokens<ConstructorParameters<C>> };

// The four `never` keys keep overload 1 from matching an options object
// written for overloads 2 and 3. TypeScript types a callback's parameters
// from the first overload whose structural check passes, so without them
// `provide(Cls, { useFactory: (a) => ..., deps })` types `a` as any.
type ClassOptionsObject<C extends Ctor> = {
  lifetime?: Lifetime;
  useClass?: never;
  useValue?: never;
  useExisting?: never;
  useFactory?: never;
} & DepsFor<C>;

type ClassOptions<C extends Ctor> =
  DeclaresDeps<C> extends true
    ? [options?: ClassOptionsObject<C>]
    : [options: ClassOptionsObject<C>];

// deps is optional on useClass: the compiler reads the class's @Injectable
// metadata or static deps, and no type records metadata. A static deps that
// a type can see is still checked against the constructor.
type UseClassDeps<C extends Ctor> = C extends { readonly deps: unknown }
  ? DepsFor<C>
  : { deps?: Tokens<ConstructorParameters<C>> };

type NoLifetimeMessage =
  'NEXUS_INVALID_PROVIDER: useValue and useExisting take no lifetime. Remove lifetime';

// Each member excludes the others' definition keys, so TypeScript reports a
// lifetime on useValue against the value member.
type TokenDefinition<T, C extends Ctor> =
  | ({
      useClass: C;
      lifetime?: Lifetime;
      useValue?: never;
      useExisting?: never;
    } & UseClassDeps<C>)
  | {
      useValue: NoInfer<T>;
      lifetime?: NoLifetimeMessage;
      useClass?: never;
      useExisting?: never;
    }
  | {
      useExisting: InjectionToken<NoInfer<T>>;
      lifetime?: NoLifetimeMessage;
      useClass?: never;
      useValue?: never;
    };

type FactoryDefinition<D extends readonly Dep[], R> = {
  useFactory: (...args: ResolveAll<D>) => R;
  deps?: D; // D is [] when the call has no deps
  lifetime?: [R] extends [PromiseLike<unknown>]
    ? 'singleton' | 'scoped' | AsyncTransientError
    : Lifetime;
};

type AsyncTransientError =
  "NEXUS_ASYNC_TRANSIENT: get() is synchronous, so a transient factory cannot be async. Use lifetime: 'scoped', or make the token a function type and provide () => Promise<T>";
type PromiseTokenError =
  'NEXUS_PROMISE_TOKEN: the container awaits a factory result, so a token cannot hold a Promise. Type the token as the resolved value, or as () => Promise<T>';

// 1. A class as its own token.
function provide<C extends Ctor>(
  cls: C,
  ...options: ClassOptions<C>
): Provider<InstanceType<C>>;

// 2. A token with a class, a value or an alias.
function provide<T, C extends new (...args: any) => NoInfer<T>>(
  token: InjectionToken<T> | MultiToken<T>,
  options: TokenDefinition<T, C>,
): Provider<T>;

// 3. A token with a factory.
function provide<
  T,
  R extends NoInfer<T> | PromiseLike<NoInfer<T>>,
  const D extends readonly Dep[] = [],
>(
  token: [T] extends [PromiseLike<unknown>]
    ? PromiseTokenError
    : InjectionToken<T> | MultiToken<T>,
  options: FactoryDefinition<D, R>,
): Provider<T>;
```

`T` comes from the token alone. `NoInfer` stops `useValue`, `useExisting` and the
factory's return type from widening it. The `const D` parameter infers `deps` as a
tuple, and defaults to `[]` when the call has no `deps`, so a factory without `deps`
takes no arguments and a factory parameter no entry supplies is a type error. `D`
follows `R` because a type parameter with a default cannot precede a required one. A
lifetime on `useValue` or `useExisting` fails against `NoLifetimeMessage`, the same
type the literal check uses (section 4.6). The factory overload checks the async-transient rule through `lifetime`'s type,
and rejects a token whose type is itself a promise, because the runtime awaits every
thenable a factory returns.

This sketch was checked on TS 6.0.3 while writing this spec. The diagnostics it produced,
quoted from the diagnostics test, whose fixtures stay concrete classes because they test
the type mechanics:

| Call                                              | Error TypeScript reports                                                                  |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `provide(ShipComputer, { deps: [SubspaceLink] })` | `Property 'output' is missing in type 'SubspaceLink' but required in type 'ReactorCore'`  |
| `provide(ShipComputer)`                           | `Expected 2 arguments, but got 1`                                                         |
| `provide(NAV_CHARTS, { useValue: { nope: 1 } })`  | `'nope' does not exist in type 'NavCharts'`                                               |
| `provide(COMPUTER, { useExisting: ReactorCore })` | `Property 'reactor' is missing in type 'ReactorCore' but required in type 'ShipComputer'` |

| factory for a `Token<Promise<NavCharts>>`         | `... not assignable to parameter of type '"NEXUS_PROMISE_TOKEN: ..."'`                    |
| `provide(NAV_CHARTS, { useValue, lifetime })`     | `... '"NEXUS_INVALID_PROVIDER: useValue and useExisting take no lifetime. ..."'`          |

Section 17 pins these messages in tests. The runtime has a backstop for JavaScript
callers and `any`: a transient factory that returns a thenable throws
`NEXUS_ASYNC_TRANSIENT` at the `get()` that built it.

`eager` (section 6.6) follows the same pattern:

```ts
type LazyAsyncMessage =
  'NEXUS_LAZY_ASYNC: an async provider is built during create or createScope, so it cannot be eager: false. Remove eager: false, or make the token a function type and provide () => Promise<T>';

// In FactoryDefinition<D, R>:
//   eager?: [R] extends [PromiseLike<unknown>] ? true | LazyAsyncMessage : boolean;
// In the class forms, for a class C whose onInit returns a promise:
//   eager?: true | LazyAsyncMessage;
```

A `lifetime: 'transient'` option shape has no `eager` key, so `eager` beside it is an
unknown-key error. The plan prototypes these types on TS 5.4, 6.0.3 and 7 before the
diagnostics table gains their rows, as it did for revision 1's types. The runtime
backstop is `NEXUS_LAZY_ASYNC` at the first `get()` (section 6.6).

### 4.4 Decorators

`@nexusdi/decorators` exports these; `Ctor`, `Dep`, `Lifetime`, `DepsFor` and `Resolve`
are core's public types.

```ts
function Injectable<C extends Ctor>(
  options: { lifetime?: Lifetime } & DepsFor<C>,

function Inject<D extends Dep>(
```

### 4.5 `REQUEST` and consumer `lib`

```ts
export interface NexusRequest {}
export const REQUEST: Token<NexusRequest>;
```

`createScope({ request })` takes `request?: NexusRequest`. The type cannot know whether
any provider depends on `REQUEST`, so the runtime checks (section 7.2).

The published declarations use `Symbol.asyncDispose` and `AsyncDisposable`. The entry
`.d.ts` files start with `/// <reference lib="esnext.disposable" />`, so a consumer with
`lib: ["es2022"]` and no `@types/node` compiles without a `lib` change. That directive was
checked on TS 6.0.3 with `skipLibCheck: false`. The docs say that the directive adds the
disposable globals to the consumer's program.

### 4.6 Provider literals

```ts
export interface ProviderLiteral {
  readonly token: Token<unknown> | MultiToken<unknown> | Class;
  readonly deps?: readonly Dep[];
  readonly lifetime?: Lifetime;
  readonly useClass?: Ctor;
  readonly useValue?: unknown;
  readonly useFactory?: (...args: never) => unknown;
  readonly useExisting?: InjectionToken<unknown>;
}
export type ProviderEntry = Provider<unknown> | Class | ProviderLiteral;

// Each element of the providers tuple, checked with the rules provide() enforces.
export type ProviderEntries<P extends readonly unknown[]> = {
  [I in keyof P]: CheckedEntry<P[I]>;
};

function defineModule<Opts = never, const P extends readonly unknown[] = []>(
  config: Omit<ModuleConfig, 'providers'> & {
    readonly providers?: ProviderEntries<P>;
    readonly options?: Token<Opts>;
    readonly schema?: StandardSchemaV1<unknown, NoInfer<Opts>>;
  },
): [Opts] extends [never] ? ModuleDefinition : ConfigurableModule<Opts>;
```

The `const P` parameter infers `providers` as a tuple, one type per element.
`ProviderEntries` is a homomorphic mapped type, so TypeScript infers `P` through it and
reports a failed check on the element, at the key that breaks the rule. `CheckedEntry`
passes a `provide()` result through, checks a bare class's `static deps` against its
constructor parameters, and for a literal builds the type
`provide()` would demand from its keys: `useValue: NoInfer<T>` (a lifetime is an
error), `useExisting: InjectionToken<NoInfer<T>>`, `useClass` producing `T` with
`UseClassDeps<C>`, a class token with `DepsFor<C>`, and a factory whose parameters take
`ResolveAll<deps>`, whose `lifetime` rejects `'transient'` for an async factory, and
whose token rejects a `Promise` type. A widened `ProviderEntry[]` passes unchanged, and
the compiler checks it at runtime.

`defineModule` has one signature. For an overloaded function, TypeScript reports "No
overload matches this call" and prints each overload's error, which buries the element. `@Module` takes `providers?: ProviderEntries<P>` the same way (section 3.8), and so does
the provider array of `Nexus.create` (section 3.5).

```ts
interface ConfigurableModule<Opts> extends ModuleDefinition {
  forRoot(options: NoInfer<Opts>): ModuleDefinition;
  forRootAsync<const D extends readonly Dep[] = []>(config: {
    useFactory: (
      ...args: ResolveAll<D>
    ) => NoInfer<Opts> | PromiseLike<NoInfer<Opts>>;
    deps?: D;
  }): ModuleDefinition;
}
```

The diagnostics TypeScript 6.0.3 reports, pinned in
`provider-literal.diagnostics.test.ts` (section 17), whose fixtures stay concrete classes
because they test the type mechanics. TypeScript 5.4.5 and 7.0.2 report
them on the same lines:

A literal falls short of `provide()` in three places:

1. Parameter types. TypeScript types a literal element from the element itself, so a
   function whose parameters need a contextual type (a factory, or a function-valued
   `useValue`) gets none, and TypeScript leaves that element uninferred. The check then
   reports `UntypedFunctionMessage` on the function and TS7006 on each parameter. With
   annotated parameters the check is complete: an annotation that does not accept what
   the `deps` entry resolves to is an error. `provide()` types the parameters from
   `deps` through its overloads. A design that inferred `deps` in a separate type
   parameter typed the parameters in some arrays and lost them when a bare class sat
   beside the literal, so the spec does not depend on it.
2. Unknown keys. The message prints the whole type the element was checked against.
3. Widened arrays. An array typed `ProviderEntry[]`, or a spread of one, is checked only
   at runtime.

The docs therefore recommend `provide()` and show literals as the form 0.3 code keeps.

## 5. Compilation

`Nexus.create`, `load` and `Nexus.check` run the same compiler. It takes definitions and
returns a `Blueprint` or a `BlueprintError`. It constructs nothing and calls no user code
other than the registered plugins' compile hooks (section 3.10.3). Standard Schema
`validate()` and `forRootAsync` factories run later, in the build (section 6).

Before pass 1, `create` and `check` validate the plugin array (section 3.10.2); a fault
there throws before any pass runs.

The compiler runs six passes. Each pass collects errors and continues when it can. A pass
whose input is broken by an earlier error skips the affected providers, so one missing
token produces one error.

1. Walk and deduplicate. A depth-first walk from the root follows `imports`. It keys
   modules by identity, assigns ids in walk order (`m0`, `m1`, ...), and keeps the walk
   path on a stack. When the walk meets a module that is already on the stack, it reports
   `NEXUS_MODULE_IMPORT_CYCLE` with the path from the first occurrence to the repeat. A
   value that is not a module is `NEXUS_INVALID_MODULE`. The walk normalises every
   provider into a record, and a provider literal gives the record the matching
   `provide()` call gives (section 3.2):

   ```ts
   interface ProviderRecord {
     id: string;
     kind: 'class' | 'value' | 'factory' | 'alias';
     token: Token<unknown> | MultiToken<unknown> | Class;
     module: string;
     lifetime: Lifetime | null; // null for value and alias
     deps: DepEntry[]; // constructor or factory arguments, in order
     props: Array<{ key: string | symbol; dep: DepEntry }>; // @Inject accessors
     target?: InjectionToken<unknown>; // useExisting only
   }
   ```

   It rejects malformed providers (`NEXUS_INVALID_PROVIDER`, `NEXUS_INVALID_TOKEN`,
   `NEXUS_MISSING_DEPS`, `NEXUS_DUPLICATE_PROVIDER`). A module in `providers` is
   `NEXUS_INVALID_PROVIDER` with the fix "add it to imports". For `load`, modules already
   in the live blueprint count as visited, so the walk stops at them.

   Plugins act inside this pass: `compile.module` before the walk reads each module, and
   `compile.provider` after the walk, before any duplicate check (section 3.10.3). The
   compiler keys every token through `tokenKey` when a plugin supplies one.

2. Compute visibility. For each module, the compiler builds `Map<token, providerId[]>`
   from its own providers, its imports' exports (following re-exports transitively), and
   the global modules' exports, applying the shadowing and merging rules of section 3.4.
   It checks each `exports` entry (`NEXUS_INVALID_EXPORT`) and each ambiguity
   (`NEXUS_AMBIGUOUS_PROVIDER`). `REQUEST` is visible in every module.
3. Bind. For each entry in `deps` and `props`, and for each alias `target`, the compiler
   looks the token up in the owning module's visibility map and records an edge
   `{ from, to, kind }`. An alias target produces an edge of kind `alias`. A required,
   lazy or alias entry with no binding is `NEXUS_MISSING_PROVIDER`, carrying the token,
   the requester and its module. Core does no near-miss search. With `errors()`
   registered, the plugin searches every module of the compile's view for the token and
   fills `nearMisses` (section 9.1):
   - "exists in Engineering, not exported"
   - "exported by Tactical, which Comms does not import"
   - "a Token with the same description 'NavCharts' exists in Tactical" (two distinct
     `Token` objects with one description)

   An `optional` entry with no binding records no edge. An `all` entry binds to every
   visible contribution.

4. Detect cycles. Tarjan's algorithm runs over required, optional, `all` and alias edges,
   and skips lazy edges. Every strongly connected component with more than one node, or
   with a self-edge, is one `NEXUS_CIRCULAR_DEPENDENCY` error. Two aliases that point at
   each other form such a cycle. The error's `path` walks the cycle from its lowest
   provider id back to itself, for example `ShieldGrid → PowerRouter → ShieldGrid`, and
   its message suggests `lazy()` on one named edge.
5. Check lifetimes. For each singleton, the compiler follows its edges, lazy ones
   included, through transient providers and aliases. When that walk reaches a scoped
   provider or `REQUEST`, the compiler reports `NEXUS_LIFETIME_VIOLATION` with the path
   from the singleton to the scoped provider. A singleton may therefore depend on a
   transient whose closure reaches no scoped provider and no `REQUEST`, and the runtime
   builds that transient once for the singleton. Scoped and transient providers may depend
   on anything visible.
6. Compute levels. Singleton levels come from the non-lazy edges, alias edges included:
   a singleton with no singleton deps is level 0, and every other singleton is one more
   than its highest dep. A transient or an alias contributes the levels of what it
   reaches. The compiler computes the same levels over scoped factory providers and
   their scoped deps, for `createScope`.

The compiler also records `needsRequest`: true when any provider has a non-optional edge
to `REQUEST`. Providers with `eager: false` get no level; the runtime builds them on
first use (section 6.6).

After pass 6, the plugins' `compile.check` hooks run in order and may report more errors
(section 3.10.3).

If any pass or hook reported an error, the compiler throws one `BlueprintError`
(`NEXUS_BLUEPRINT_INVALID`) whose `errors` array holds every error in pass order, then
the plugins' errors in plugin order, and whose message lists each one on its own line.

The `Blueprint` is frozen. It holds the modules, the provider records, the edges, the
per-module visibility maps, the levels and `needsRequest`. `load` produces a new
`Blueprint` that contains the old one, and the runtime switches to it after the load's
build succeeds.

## 6. Runtime

### 6.1 Build at `create` and `load`

For each singleton level in order, the runtime starts every provider in the level:

- A class provider resolves its deps, calls `new C(...deps)`, and then sets its injected
  properties.
- A factory provider resolves its deps and calls the factory. If the result is a
  thenable, the runtime awaits it.
- A value provider stores `useValue` as it is. The runtime never awaits a value.
- An alias stores nothing. `get()` of an alias resolves the alias's bound target, which
  pass 3 bound with the alias's own module visibility.

Providers in one level run concurrently. The runtime waits for every provider in the level
to settle (`Promise.allSettled`) before it starts the next level, and records each
instance in the creation order when it completes.

A transient dep resolves in the container of the frame that requested it (section 6.3).
Transient deps of a singleton are built inline, once, while the singleton is built. They
join the creation order, and the root owns them.

After the last level, the runtime runs `onInit` (section 8). Then `create` returns the
sealed container.

### 6.2 `get()` and `has()`

Root `get(T)` looks up `T` in the root module's visibility map, which the compiler
precomputed, and then:

- For a singleton, it returns the built instance. The runtime stores instances in a `Map`
  and checks with `Map.has`, so a falsy singleton (`0`, `''`, `false`, `null`,
  `undefined`) is built once (regression R05).
- For a transient, it builds a new instance synchronously.
- For a scoped provider, it throws `NEXUS_SCOPE_REQUIRED`.
- For an alias, it returns `get()` of the bound target.
- For a `MultiToken`, it returns a new array of the visible contributions, each resolved
  by its own lifetime.

`has(T)` runs the same lookup and returns whether it found a binding.

The public methods (`get`, `has`, `resolve`, `validate`, `load`, `createScope`, and a
scope's `extend`) check the disposed flag first and throw `NEXUS_DISPOSED` after
disposal starts (regression R17). `graph(ship)` from `@nexusdi/devtools` still works
after disposal. Section 8.2 says what thunks do during disposal.

### 6.3 Readiness, lazy thunks and the construction stack

Each container (the root or a scope) keeps two maps keyed by provider id:

- `built`: the provider's construction has settled.
- `ready`: the provider is built and, during `create` or `load`, its `onInit` has
  settled. A provider enters `ready` when it is built if no `onInit` phase applies: scoped
  and transient instances, value providers, `eager: false` providers, and every provider
  when a plugin sets `onInit: false`.

Constructors and factories receive their non-lazy deps from `built`. A lazy thunk reads
only `ready`. A thunk call throws `NEXUS_NOT_READY`, naming the thunk's owner and its
target, in three cases:

1. A constructor calls the thunk before a later level has built the target.
2. An async factory calls the thunk in a continuation after `await` while the target is
   still in flight.
3. An `onInit` calls the thunk before the target's `onInit` has run. `onInit` order
   follows the levels, which ignore lazy edges, so a lazily linked provider's `onInit`
   can run before or after its owner's.

For a scoped class or a transient, the thunk builds the target on demand, and the runtime
throws `NEXUS_NOT_READY` only when the target's own frame is on the construction stack.

The runtime keeps a synchronous construction stack of frames
`{ providerId, container }`. It pushes a frame before it calls a constructor or factory
and pops it in a `finally`. When `NEXUS_NOT_READY` fires while the target's frame is on
the stack, the error's `path` holds the runtime cycle read off the stack.
`NEXUS_PROVIDER_FAILED` also reports the stack as its `path`.

The stack is separate from `ScopeContext`. `ScopeContext` answers "which scope is this
request in"; the stack answers "what is being built right now". An async factory's
continuation after `await` runs with an empty stack. The runtime restores nothing there,
because it resolved the factory's deps before calling it.

### 6.4 Concurrency

Concurrency exists only inside `create`, `load` and `createScope`, where one level's async
factories run together. The `built` map holds `instance | Promise<instance>`. A second
request for a provider that is in flight receives the same promise. The runtime checks
the map with `Map.has`, never with a truthiness test.

### 6.5 Ownership

The root keeps one identity set of every object it or any scope tracks for disposal, plus
a set of every `useValue` object. The runtime tracks an object only when neither set
already holds it. So a scope never disposes an object the root tracks, a factory that
returns an existing singleton adds nothing to the disposal order, and a factory that
returns a `useValue` object never makes it disposable (regression R07). `onInit` uses the
same identity check, so an object reached through two providers gets one `onInit` call.

### 6.6 `eager: false`

`create` leaves a singleton with `eager: false` out of its levels, and `createScope` and
`extend()` leave out a scoped factory with `eager: false`. The first request for the
provider builds it synchronously, in the container that owns it (the root for a
singleton, the scope for a scoped factory), with its non-lazy deps, and stores it. A
request is a `get()`, a `resolve()`, a lazy thunk call, or the build of an eager provider
that depends on it; so an eager dependent builds it during `create`, and `eager: false`
defers only a provider that nothing eager needs.

- The runtime pushes the provider's frame on the construction stack (section 6.3), so a
  runtime cycle through lazy thunks still reports `NEXUS_NOT_READY` with its path.
- The instance joins the creation order when it is built, so disposal stays in reverse
  creation order.
- A singleton's `onInit` runs right after the build, synchronously. It must not return a
  promise; the type rejects that class (section 4.3), and at runtime a returned thenable
  is `NEXUS_LAZY_ASYNC`.
- A factory that returns a thenable at that build is `NEXUS_LAZY_ASYNC`. The runtime
  attaches a rejection handler to the thenable, so the process sees no unhandled
  rejection, and stores nothing, so the next request tries again.
- A failure throws the `ProviderError` a failing `get()` of a transient throws, and the
  runtime stores nothing.
- Observing plugins receive the `construct` event at the build, with its duration.

## 7. Scopes

### 7.1 Semantics

A scope is a child of the root container. It resolves tokens with the root module's
visibility, and accepts the same `{ module }` option.

- Singletons always come from the root. `shuttle.get(COMPUTER) === ship.get(COMPUTER)`
  (regression R12).
- The scope owns its scoped instances. Each scope builds each scoped provider at most once.
- The scope owns the transient instances it builds and tracks them for disposal. A
  transient injected into a scoped instance is built once for that instance.
- `REQUEST` resolves to the value passed to `createScope`.

A scope resolves against the blueprint that was current when the scope was created. A
token from a module loaded after that throws `NEXUS_LOADED_AFTER_SCOPE`, whose fix is
`await scope.extend()` after the `load()` (section 7.4). Requests are short, so the next
scope sees the new module without it.

### 7.2 `createScope`

1. If the blueprint's `needsRequest` is true and `options.request` is `undefined`, throw
   `NEXUS_REQUEST_MISSING`, naming the providers that depend on `REQUEST`.
2. Create the scope and bind `REQUEST`.
3. Build every scoped factory provider and the scoped providers they depend on, level by
   level, as in section 6.1. Scoped class providers build lazily, on the first `get()`.
   After each level, check the root's disposed flag (section 8.2).
4. Emit `scope:create` and return the scope.

The runtime cannot tell a sync factory from an async one without calling it: a plain
function can return a promise, and a transpiled `async` function is a plain function.
Step 3 therefore builds every scoped factory, sync or async. So a scoped factory runs once
per scope even when the request never asks for its token. The docs say so, and steer
on-demand resources, such as a per-request database transaction, to a scoped class,
which builds on first use, or to a provider whose value is a function the caller invokes.

A failure in step 3 disposes what the scope built, in reverse order, and rethrows.

### 7.3 Ambient scope

Core has no ambient scope (section 0, D20). No core code reads a current scope: a lazy
thunk resolves in the container that built its owner, and a scope's `get()` needs no
context. `@nexusdi/node` exports the ambient scope for servers:

```ts
interface NodeScopes {
  run<R>(scope: Scope, fn: () => R): R;
  current(): Scope | undefined;
}
export function nodeScopes(): NodeScopes;
```

Each `nodeScopes()` call owns one `AsyncLocalStorage`. `run` calls `storage.run(scope, fn)`,
and `current()` returns the scope of the enclosing `run`, or `undefined` outside one. It
is not a plugin: it needs no core hook and holds no container. `@nexusdi/node` is the
only package that imports a `node:` module. A later package wraps `AsyncContext.Variable`
(TC39 Stage 2) the same way once an engine implements it.

### 7.4 `scope.extend()`

`await scope.extend()` re-pins a scope to the container's current blueprint and builds
the scoped factories that modules loaded since its pin contribute. It returns at once
when nothing was loaded since.

1. Built instances are kept, with their identity. Every token the scope resolved before
   `extend()` resolves to the same provider after it, because `load()` is additive: the
   compiler rejects a load that would change an existing binding
   (`NEXUS_AMBIGUOUS_PROVIDER`, `NEXUS_LOAD_GLOBAL_MODULE`). `REQUEST` and `scope.id` do
   not change, so an `AsyncLocalStorage` store that holds the scope stays valid.
2. `extend()` computes the delta, the scoped factory providers of the current blueprint
   that the pinned one lacks, and builds them level by level with the builder
   `createScope` uses. Scoped deps the scope already built are reused. Scoped classes
   still build on first `get()`, and a scoped factory with `eager: false` is skipped.
   The pin moves only after every level settles, so no `get()` sees a half-built delta.
3. When a new provider depends on `REQUEST` and the scope has none, `extend()` throws
   `NEXUS_REQUEST_MISSING` naming the new dependents, and the pin stays.
4. Calls on one scope run one at a time. A call that starts while another is in flight
   for the same blueprint returns that call's promise. A `load()` that publishes during
   an `extend()` does not affect it, and the next call picks up the rest. `get()` during
   an `extend()` uses the old pin.
5. A factory that throws makes `extend()` dispose what it built, in reverse order, leave
   the pin unchanged, and throw a `ProviderError`, as `createScope` does.
6. Instances `extend()` builds join the scope's creation order after the older ones, so
   the scope disposes them first. Scope disposal during an `extend()` aborts it with
   `NEXUS_DISPOSED` after it disposes what it built. Root disposal awaits in-flight
   `extend()` calls as it awaits `createScope`. `extend()` on a disposed scope throws
   `NEXUS_DISPOSED`.
7. Observing plugins receive `scope:extend` with the scope id, the loaded module names,
   the count built and the duration (section 10.2).

The framework adapters call `extend()` after their `di.load()` when the request's scope
exists, so a lazy route answers its first request.

## 8. Lifecycle order

### 8.1 Startup

1. Validate the plugins, then compile. A `BlueprintError` means nothing was built.
2. Build singletons, level by level (section 6.1).
3. Run `onInit`. The runtime calls `onInit` on every built singleton instance that has
   one, level by level, and skips `useValue` objects. Calls within one level run
   concurrently, and each level waits for the previous one, so a provider's non-lazy
   dependencies finish their `onInit` first. Lazy edges do not order `onInit`.
   A plugin with `onInit: false` skips this step; `@nexusdi/testing` registers one for
   `create({ onInit: false })`.
4. Run each plugin's `setup`, in order (section 3.10.5).
5. Seal and return.

`onInit` runs only for singletons, at `create` and at `load`. Scoped and transient
instances get no `onInit`. A scoped provider that needs async setup uses an async
factory, which `createScope` awaits. An `onInit` on a transient would run on every
`get()` and could not be awaited.

If step 2, 3 or 4 fails, the runtime disposes every instance built so far, one at a
time, in reverse creation order. A `setup` failure then throws a `PluginError`
(`NEXUS_PLUGIN_FAILED`) with its `disposalErrors`; the rest of this paragraph covers steps
2 and 3. Then it throws a `ProviderError` (`NEXUS_PROVIDER_FAILED`)
for the first failure by declaration order. Its `cause` is the thrown value, its
`alsoFailed` array holds the other failures from the same level, and its
`disposalErrors` array holds every error a disposer threw during the cleanup. A failed
startup always throws a `ProviderError`, so callers can rely on its `code`.

Disposal that starts while `create`, `load` or `createScope` is building aborts the
build: the operation disposes what it built and throws `NEXUS_DISPOSED`, because the
caller's own disposal stopped it; no provider failed, so there is no `ProviderError`. The errors that rollback's
disposers throw go into the root's abort errors, and the root's disposal chains them
first (section 8.2).

### 8.2 Disposal

The container disposes only through `[Symbol.asyncDispose]()`, directly or through
`await using`. A call:

1. Sets the disposed flag, so every public method throws `NEXUS_DISPOSED`. A second call
   returns the first call's promise.
2. Awaits every in-flight `load()` and `createScope()`. Each of those checks the flag
   after every level, disposes what it built in reverse order, and rejects with
   `NEXUS_DISPOSED`.
3. Disposes open scopes, newest first.
4. Disposes root-owned instances one at a time, in reverse creation order. Modules added
   by `load()` sit later in the creation order, so their instances go first. After each
   instance's disposer settles, the runtime emits `dispose:instance` for it.
5. Emits `dispose`.
6. Runs each plugin's `dispose`, in reverse plugin order, awaiting each.

The disposed flag blocks only the public methods. While disposal runs, a lazy thunk still
returns a target that is built and not yet disposed, so a disposer can reach a
dependency that outlives it. A thunk whose target has already been disposed throws
`NEXUS_DISPOSED`.

For each instance, the runtime awaits `instance[Symbol.asyncDispose]()` when it exists, or
calls `instance[Symbol.dispose]()`. It disposes each object once (section 6.5). It never
disposes a `useValue` value. The runtime treats a factory's return value as created by
the container and disposes it; the docs say that a factory hands ownership of its result
to the container.

When a disposer throws, disposal continues. So does an `observe` hook that throws while
disposal emits `dispose:instance`, `scope:dispose` or `dispose`, and a plugin's
`dispose` that throws: the runtime catches each and collects it with the disposer errors,
and disposal always completes. The runtime
chains errors the way `DisposableStack` does: each new error becomes the `error` of a
`SuppressedError` whose `suppressed` is the previous one. The errors from builds that
disposal aborted (section 8.1) come first in the chain, then the root's own. After the
last instance, it throws the chain. The
runtime uses `globalThis.SuppressedError` when it exists, and otherwise an internal class
with the same `error` and `suppressed` fields. It never writes a global. Node 24 and
later define `SuppressedError`; Node 22 does not.

A scope disposes in the same way on `await using` exit: its own scoped and transient
instances, one at a time, in reverse creation order, with one `dispose:instance` event
each, then `scope:dispose`.

The runtime emits `dispose:instance` once for each object it disposes, in disposal order,
including an object whose disposer threw. An object that several providers reach
produces one event (section 6.5). A `useValue` value and an untracked transient produce
none, because the runtime never disposes them.

A process signal handler disposes the container like this:

```ts
const ship = await Nexus.create(Meridian);

const scram = async () => {
  try {
    await ship[Symbol.asyncDispose]();
  } catch (error) {
    console.error(error);
    process.exitCode = 1;
  }
};
process.once('SIGTERM', scram);
process.once('SIGINT', scram);
```

Both signals may fire. The second call receives the same promise, so the reactor scrams
once.

## 9. Error catalogue

Every error is a `NexusError`, one concrete class (section 0, D21):

```ts
/** Maps each code to its fields. Packages add their codes by augmentation. */
export interface NexusErrorFields {
  NEXUS_MISSING_PROVIDER: {
    token: string;
    requester: string;
    module: string;
    entry: string | null;
    nearMisses: readonly NearMiss[];
  };
  // one member per code of the tables below
}
export type NexusErrorCode = keyof NexusErrorFields;

export class NexusError<
  C extends NexusErrorCode = NexusErrorCode,
> extends Error {
  readonly name: 'NexusError';
  readonly code: C;
  readonly fields: Readonly<NexusErrorFields[C]>;
  constructor(code: C, fields: NexusErrorFields[C], options?: ErrorOptions);
}

export function isNexusError<C extends NexusErrorCode>(
  value: unknown,
  code?: C,
): value is NexusError<C>;
```

`isNexusError` checks the brand `Symbol.for('nexusdi.error')`, which every copy of core
writes on its errors, so it recognises an error from another copy where `instanceof`
cannot. A package registers its codes with
`declare module '@nexusdi/core' { interface NexusErrorFields { ... } }` and constructs
`new NexusError(code, fields)`; none subclasses the class. `cause` is the standard
`Error.cause`, set through `options`, for `NEXUS_PROVIDER_FAILED` and
`NEXUS_PLUGIN_FAILED`. First-party codes start with `NEXUS_`, a third-party plugin uses
a prefix of its own, and a code is never renamed or reused. The codes and the fields are
the stable API; the message text is not.

The prose of this spec still names errors by revision 1's class names, such as
`ProviderError` or `BlueprintError`. Each name means the `NexusError` with the code its
row lists, and the "Name in prose" columns below keep the mapping. The names are not
exports.

Core writes one line per error, from the code and the fields, with no text per code:

```
[NEXUS_MISSING_PROVIDER] token=NavCharts requester=ShipComputer module=Engineering. https://nexus.js.org/errors/NEXUS_MISSING_PROVIDER
```

The line prints every field whose value is a string, a number, or an array of strings,
in the field order of the table below. A `BlueprintError`'s line is
`[NEXUS_BLUEPRINT_INVALID] <n> errors. <link>`, followed by each inner error's message on
its own line, indented by two spaces. Two errors are raised where no container exists:
`defineModule`'s `NEXUS_INVALID_MODULE` for a config without a `name`, and
`new Token('')`'s `NEXUS_INVALID_TOKEN`. Core keeps their revision 1 text, est. under

### 9.1 `@nexusdi/errors`

```ts
import { errors, explain } from '@nexusdi/errors';

const ship = await Nexus.create(Meridian, { plugins: [errors()] });
```

`errors()` returns a plugin whose only hook is `formatError`. `devtools()` includes the
same hook, so a development setup registers one of the two.

The `formatError` contract, which any plugin may implement:

- Core calls it for every `NexusError` that core raises inside an operation of a
  container that has the plugin: `create` once the plugins are validated, `load`, `get`,
  `has`, `resolve`, `validate`, `createScope`, `extend`, a lazy thunk call and disposal.
  `Nexus.check` calls it too. Core formats a `BlueprintError`'s inner errors first, then
  the aggregate. It never formats a value user code threw, such as a `ProviderError`'s
  `cause`.
- `view` is the compile's view (`complete: false`) for a compile error, the current
  blueprint's view for a runtime error, and `undefined` for a plugin registration error.
- The returned `ErrorText` sets the message: core writes `[CODE] `, then `message`, then
  each of `hints` on its own line indented by two spaces, then ` Fix:` and `fix` when
  present. That is revision 1's layout. `nearMisses`, when returned, fills the error's
  field of that name. Core sets the other fields before the call, and the hook cannot
  change them.
- A hook that throws, or returns something other than an object with a string
  `message`, leaves core's one-line message in place. A formatter never hides the error
  it formats.
- Core formats an error object once. An error rethrown through a second operation keeps
  its text.

`@nexusdi/errors` holds revision 1's message builders, moved from core with their text
unchanged, and the near-miss search, which reads the view: every module's `visible()`
for the token, the modules that export it, and the tokens that share its description.
The duplicate-core message reads `otherCopy`. `explain(error, view?)` returns the
`ErrorText` for any `NexusError`, for code that caught an error from a container without
the plugin.

Section 17 requires every error test from revision 1 to pass unchanged with `errors()`
registered.

## 10. Introspection and trace

`@nexusdi/devtools` holds both, built on the `setup` and `observe` hooks and on
`Nexus.check`:

```ts
import { devtools, graph, inspect, trace } from '@nexusdi/devtools';

const ship = await Nexus.create(Meridian, { plugins: [devtools()] });
graph(ship); // NexusGraph of the live container

inspect(Meridian, { load: [Science] }); // NexusGraph from Nexus.check; builds nothing

await Nexus.create(Meridian, { plugins: [trace((event) => log.debug(event))] });
```

- `devtools(options?)` returns one plugin with `setup`, `observe` and the `errors()`
  `formatError`. `options.trace` receives every event, as `trace(fn)` does.
- `graph(ship)` reads the view `setup` recorded for that container, which follows every
  `load()`, and the `construct` events it observed. For a container registered without
  `devtools()` it throws `NEXUS_DEVTOOLS_UNREGISTERED`.
- `inspect(root, options?)` runs `Nexus.check` with `devtools()` and `options.plugins`
  registered, and returns the graph of the last compile. It throws the `BlueprintError`
  `Nexus.check` throws. The graph CLI of #18 calls it.
- `trace(fn)` returns a plugin whose only hook is `observe`.

### 10.1 `graph()`

```ts
interface NexusGraph {
  modules: Array<{
    id: string; // 'm0'
    name: string;
    global: boolean;
    imports: string[]; // module ids
    exports: string[]; // provider ids and module ids
  }>;
  providers: Array<{
    id: string; // 'p0'
    token: string; // display name
    module: string; // module id
    lifetime: 'singleton' | 'scoped' | 'transient' | null; // null for value and alias
    kind: 'class' | 'value' | 'factory' | 'alias';
    eager: boolean;
    async: boolean | null; // factories: whether the last build returned a thenable; null before any build
  }>;
  edges: Array<{
    from: string; // provider id
    to: string; // provider id
    kind: 'required' | 'optional' | 'lazy' | 'all' | 'alias';
  }>;
}
```

`async` is `false` for class and value providers, and `null` for aliases, for a factory
that has not run yet, and for every provider in `inspect()`'s graph.

The display name is the class's `name` or the token's `description`. Ids are stable for a
given set of definitions, so two runs of the same app produce the same graph. The docs
warn that minifiers rename classes, so a production graph can show `t` in place of
`ShipComputer`, and recommend `Token` descriptions or `keepNames` where names matter.

`graph(ship)` includes modules added by `load()` and modules plugins contributed. The
docs playground renders this JSON, and the future graph CLI (#18) reads it.

### 10.2 Trace events

```ts
type TraceEvent =
  | {
      type: 'compile';
      phase: 'create' | 'load' | 'check';
      modules: number;
      providers: number;
      errors: number;
      durationMs: number;
    }
  | {
      type: 'construct';
      token: string;
      providerId: string;
      module: string;
      lifetime: Lifetime | null; // null for value and alias providers
      scope: string | null;
      async: boolean;
      durationMs: number;
    }
  | {
      type: 'untracked';
      token: string;
      providerId: string;
      reason: 'root-transient' | 'singleton-thunk';
    }
  | { type: 'init'; token: string; providerId: string; durationMs: number }
  | { type: 'scope:create'; scope: string; built: number; durationMs: number }
  | {
      type: 'scope:extend';
      scope: string;
      modules: string[];
      built: number;
      durationMs: number;
    }
  | {
      type: 'scope:dispose';
      scope: string;
      disposed: number;
      errors: number;
      durationMs: number;
    }
  | {
      type: 'dispose:instance';
      token: string;
      providerId: string;
      scope: string | null; // null for root-owned instances
    }
  | { type: 'dispose'; disposed: number; errors: number; durationMs: number };
```

Core emits these to the plugins' `observe` hooks and holds the type; `@nexusdi/devtools`
re-exports it. The runtime emits `construct` for value and alias providers when it
registers them, with `durationMs: 0`.

Section 8.2 gives the order of `dispose:instance` events. For an object several
providers reach, `token` and `providerId` name the provider that built it first.

The runtime emits `untracked` when it builds a disposable transient that no container
tracks: one from root `get()`, or one from a singleton's lazy thunk to a transient, which
builds a new root-level instance on every call. Nothing disposes such an instance. The
docs name this as a leak and recommend a scope.

`scope` is a scope id (`s0`, `s1`, ...). The runtime measures durations with
`performance.now()`. Without an observing plugin, each emit site runs one length test,
builds no event and reads no clock. An exception thrown by `observe` propagates to the
caller of the operation that emitted the event, except during disposal, which catches it
and reports it with the disposer errors (section 8.2).

## 11. Testing API

Plain constructors need no container, so a unit test calls
`new ShipComputer(new FakeReactor())`, where `FakeReactor` implements `IReactorCore`.

`@nexusdi/testing` builds a container with replacements:

```ts
import { createTestingContainer } from '@nexusdi/testing';

await using ship = await createTestingContainer(Meridian)
  .override(REACTOR, { useClass: FakeReactor })
  .override(NAV_CHARTS, { useValue: fakeCharts })
  .override(FLIGHT_LOG, { useClass: MemoryFlightLog })
  .override(SUBSPACE_LINK, { useFactory: () => new LoopbackLink() })
  .override(DIAGNOSTICS, { useValue: passingDiagnostic })
  .overrideModule(Comms, CommsStub)
  .create({ onInit: false });

ship.get(COMPUTER).reactor instanceof FakeReactor; // true: ShipComputer is unchanged
```

`create(options)` calls `Nexus.create` with the root and one plugin, placed before
`options.plugins`, built from the builder's state. The package imports nothing from core
but its public entry.

- `override(T, def)` accepts `useValue`, `useClass` or `useFactory`, typed with the
  same overloads as `provide()`. For a plain token, the plugin's `compile.provider`
  returns `{ with: def }` for every provider of `T`, in every module, so each keeps its
  module and lifetime unless `def` sets `lifetime`. A test that needs one module's
  provider replaced uses `overrideModule`. For a `MultiToken`, the hook returns
  `{ with: def, pin: true }` for the first contribution, so the whole set becomes the one
  contribution `def` describes. An override that matches no provider is reported by the
  plugin's `compile.check` as `NEXUS_OVERRIDE_UNUSED`, inside the `BlueprintError`.
- `overrideModule(Mod, Stub)` replaces a module wherever the walk meets it, through
  `compile.module`. When `Mod` is a configurable module's base definition, the override
  replaces every `forRoot` and `forRootAsync` instance of it, which the hook recognises
  through `context.configuredFrom`. `Stub` must export every token `Mod` exports, or the
  check hook reports `NEXUS_OVERRIDE_EXPORTS`. When no module in the compiled graph is
  `Mod`, it reports `NEXUS_OVERRIDE_UNUSED`.
- `overrideModule(Mod, Stub, { lazy: true })` registers the same replacement for a module
  the app adds later. Compile hooks run in every `load()`, so `ship.load(Mod)`, or a
  `load()` of any module that imports `Mod` directly or transitively, walks `Stub` in its
  place, and the check hook checks `Stub`'s exports in that `load()`. A lazy override
  that no `load()` uses is valid, since `create` cannot know which modules will load.
  The walk also replaces `Mod` at `create` when the root graph already contains it.
- `create(options)` takes `CreateOptions` plus `onInit?: boolean` (default `true`);
  `onInit: false` sets the plugin's `onInit: false`.
- The testing container runs the full compiler, so an override that introduces a missing
  dep, a cycle or a lifetime violation fails exactly as in production.

The builder is immutable. Each call returns a new builder, so a `beforeEach` can share a
base builder.

that imports `Injectable`, so the polyfill runs first.

### 12.3 ESM only

`dependencies` is empty in every package but `@nexusdi/devtools`. Node 20 reached end of
life on 2026-04-30, so `engines` starts in 22, the oldest line still in maintenance, at
22.12, the release that unflagged `require()` of ES modules. The packages therefore
never run where a CommonJS consumer cannot load them. The build emits nodenext ESM with
explicit `.js` extensions, as `fix/core-export-map` established. `main` and `module` go,
since the exports map covers every resolver the engines floor supports.

Every package ships ESM only. There is no CommonJS build and no dual export map: each
entry has `types`, `import` and `default` conditions and no `require` condition. One
module format also rules out the dual-package hazard, where an application loads an ESM
copy and a CJS copy of core and ends up with two `Token` classes and two sets of metadata
symbols, so a token from one copy never matches a provider from the other.

A CommonJS project loads them on every Node release `engines` allows. Node 22.12.0 (and
23.0.0, and the 20.19.0 backport) took `require()` of an ES module out from behind the
`--experimental-require-module` flag, and 22.13.0 dropped its experimental warning, per
the history of "Loading ECMAScript modules using `require()`" in the Node modules docs.
`require('@nexusdi/core')` and `require()` of each optional package resolve through the
`default` condition and return the module namespace, so
`const { Nexus, provide } = require('@nexusdi/core')` works. `require()` throws
`ERR_REQUIRE_ASYNC_MODULE` for an ES module graph that uses top-level `await`, so no
module in any package's graph uses it, and the packaging check enforces that
(section 17).

### 12.4 The size report

Core has no numeric size budget (section 0, D5). A CI job reports core's size on every
pull request and makes growth a decision its author states:

1. The workflow `size-report.yml` runs on `pull_request` events `opened`, `synchronize`
   and `edited`, so an edit of the description re-runs it.
2. It builds `@nexusdi/core` at the pull request's head and at its merge base with
   `main`, and bundles the fixture of section 17.2 against each: an ESM consumer,
   esbuild `--bundle --minify --format=esm`, gzip level 9. The same job measures each
   optional package's fixture.
3. It writes one comment on the pull request, and updates that comment on later runs: a
   table of core and each package, with the base size, the head size and the change in
   bytes and percent.
4. When core grows by more than the threshold in `size-report.json` (proposed: 2%), the
   job fails unless the pull request's description contains a `## Size` section. The
   section says what the added bytes give the user and why they cannot live in a plugin. The
   job reads the description from the event payload, so no token is needed to read it.
5. Package growth is reported and never fails the job; a package's weight is the choice
   of the teams that install it.
6. On `main`, the job writes `size.json`, which the README's size figure and the launch's
   size column read. No document states a size a person measured by hand.

### 12.5 Consolidation

Shrinking core is a planned workstream, and every step keeps behaviour. The existing
tests pin it: a step changes no test except the assertions D21 rewrites, and the size
report shows each step's saving.

- One error class (D21). The 24 subclasses become `NexusError` with typed fields. Tests
  that assert `toBeInstanceOf(MissingProviderError)` assert the code and the fields, and
  the error tests of section 17 run unchanged otherwise.
- The compiler. The provider normaliser for `provide()` options, literals, `static deps`
  and metadata already runs through one function; the plan merges the per-form checks
  into one table of rules, and merges visibility's re-export walk with the module walk
  where both traverse the same edges.
- The runtime. `create`, `load`, `createScope` and `extend()` share one level builder,
  and the singleton, scoped and lazy-build paths share one construct function with the
  plugin hook in one place.
- The plan orders these after the features of revision 2 are in, so each consolidation
  step starts from a complete test suite.

## 13. Migration

### 13.1 Guide outline

The guide lives at `docs/docs/migration/0.3-to-0.4.md` and has these sections:

1. Run the codemod (`npx @nexusdi/codemod 0.4`, `@next` during the RC), read its report,
   resolve every `TODO(nexusdi-0.4)`.
2. Packages: which of the optional packages the migrated code needs, and which the
   codemod added to `package.json`.
3. tsconfig: remove `experimentalDecorators` and `emitDecoratorMetadata`, set the TS
   floor. A project that needs the flag for other libraries keeps it and uses
   `static deps` and `provide()`.
4. Tokens: symbol tokens to `Token<T>`, `TokenType` to `InjectionToken`.
5. Services: `@Service` and `@Provider` to `static deps` (the default) or, with
   `--style=decorators`, `@Injectable` from `@nexusdi/decorators`; `@Inject` params to
   deps entries, `@Optional` to `optional()`, property injection to `accessor`.
6. Modules: `@Module` configs (provider objects keep their `{ token, ... }` shape),
   `DynamicModule` to `defineModule` plus `forRoot` and `forRootAsync`, exports and
   encapsulation (the change most likely to produce `NEXUS_MISSING_PROVIDER` after
   migrating; the `module-exports` transform handles the static cases).
7. Bootstrapping: `new Nexus()` plus `set()` to `await Nexus.create([...])`, or to a root
   module when the container registered modules.
8. Lifetimes and scopes: what `createChildContainer` becomes. 0.3 built every provider
   at its first `get()`, and 0.4 builds singletons at `create`; `eager: false` restores
   the old timing for a provider that needs it.
9. Tests: `container.set(T, { useValue })` to `createTestingContainer().override()` from
   `@nexusdi/testing`.
10. Errors: old exception classes to codes, and `errors()` for full messages.
11. The full mapping table below.

### 13.2 Codemod design

`@nexusdi/codemod` lives in `libs/codemod`, is published from this repo, and runs as
`npx @nexusdi/codemod 0.4 [paths...]`. It depends on `ts-morph` for type information, on
`jsonc-parser` for tsconfig edits, and on a diff library for dry-run output. Core's
zero-dependency rule does not apply to it.

```
npx @nexusdi/codemod 0.4 [paths...]
  --tsconfig <path>     default: ./tsconfig.json
  --dry-run             print a unified diff, write nothing
  --report <path>       default: ./nexusdi-0.4-report.json
  --only <id,...>       run only these transforms
  --style <style>       static (default) or decorators
```

Architecture:

- `src/cli.ts` parses arguments and selects the migration by its first positional
  argument. `0.4` is the only migration today, and the registry is keyed by version so a
  later migration adds a key.
- `src/migrations/0.4/index.ts` exports an ordered array of transforms. Order matters,
  because later transforms read the output of earlier ones.
- A transform has the shape:

  ```ts
  interface Transform {
    id: string; // 'services'
    description: string;
    run(file: SourceFile, context: MigrationContext): void;
  }

  interface MigrationContext {
    project: Project; // ts-morph, loaded from --tsconfig
    checker: TypeChecker;
    moduleGraph: StaticModuleGraph; // built once from the 0.3 sources, see module-exports
    todo(node: Node, code: TodoCode, reason: string): void;
    note(node: Node, code: NoteCode, message: string): void;
    recordChange(file: SourceFile, transformId: string): void;
  }
  ```

- The runner loads the project once, runs every transform over every source file in
  order, then writes all files or, with `--dry-run`, prints a unified diff per file.
- `context.todo()` inserts `// TODO(nexusdi-0.4): <reason>` above the statement and adds
  a report entry. `context.note()` adds a report entry and changes no code; it records a
  behaviour change the user should know about.

The transforms for `await container.get`, `createModuleConfig`, `setMany` and `child()`
target APIs that exist only on `archive/async-container`; npm never published them. The
codemod keeps them, and their fixtures come last in priority, because anyone who
followed the async-branch docs has code in that shape.

Transforms, in order:

1. `symbol-tokens`: `Symbol('x')` and `Token.create` or `createUnique` used as tokens
   become `new Token<T>('x')`. The transform reads `T` from the injection sites'
   parameter types through the checker. When the sites disagree or are `any`, it writes a
   TODO (`untyped-token`). `a.equals(b)` on tokens becomes `a === b`. `toSymbol()` gets a
   TODO (`token-to-symbol`). `toString()` stays.
2. `services`: one pass per class, so no later transform writes into a declaration an
   earlier one created.
   - By default, `@Service` and `@Provider` go, and the class gets
     `static deps = [...] as const`, so the migrated code needs no decorator and no
     Babel plugin on any toolchain. With `--style=decorators` they become `@Injectable`
     from `@nexusdi/decorators`. A class with `@Inject` or `@Optional` constructor
     parameters and no class decorator gets `static deps` in either style.
   - Constructor `@Inject(X)` and `@Optional(X)` parameters become the deps, in parameter
     order, as `X` and `optional(X)`, in `static deps` or in `@Injectable`.
   - An undecorated parameter received `undefined` in 0.3.1, because 0.3.1 read
     `design:paramtypes` and nothing wrote it. A class-typed parameter becomes a dep of
     that class, with a note (`undecorated-param-injected`) that 0.4 now injects it. An
     interface-typed or primitive parameter gets a TODO (`undecorated-param`). The report
     does not claim either case preserves 0.3.1 behaviour.
   - A token argument (`@Service(TOKEN)`) is recorded for `module-config`, which lists
     the class bare and adds `provide(TOKEN, { useExisting: Impl })`.
   - `singleton: false`, `scope` and `type` get a TODO each (`provider-singleton-false`,
     `provider-scope-option`, `provider-type-option`). 0.3.1 ignored them and
     cached every instance, so a mechanical `lifetime: 'transient'` would change
     behaviour. `eager: false` (async branch) moves to the binding as `eager: false`.
   - A `@Service` class with `static deps` and a `lifetime` option becomes a bare class
     plus `provide(C, { lifetime })` in its module, since `static deps` carries no
     lifetime.
3. `property-injection`: every property `@Inject` gets a TODO (`property-injection`),
   because moving to `accessor` changes class field semantics the codemod cannot verify.
4. `module-config`:
   - An `@Module` provider object `{ token, useClass | useValue | useFactory }` that is a
     valid 0.4 literal (section 3.2) stays as it is. A `useClass` literal whose class
     `services` gave `static deps` or `@Injectable` is valid. The transform rewrites a
     literal to a `provide()` call only when 0.4 still rejects it, and the rewrite adds
     the `deps` that `services` read. A class recorded with a token by `services` becomes `Impl` plus
     `provide(TOKEN, { useExisting: Impl })`, which keeps 0.3's `get(Impl)` working.
     Note for the codemod plan on `plan/codemod-0.4`: its `module-config` fixtures for
     provider objects expect the literal unchanged when it is valid 0.4.
   - A `DynamicModule` subclass becomes a `defineModule` const with `options`.
     `.config(v)` becomes `.forRoot(v)`, `.configAsync(fn)` becomes
     `.forRootAsync({ useFactory: fn })`, and `createModuleConfig(Mod, c)` becomes
     `Mod.forRoot(c)`. The 0.3 names map one to one, so the call sites keep their shape.
   - By default an `@Module` class becomes a `defineModule` const of the same name, with
     `name` set to the class name. A class with members or a `typeof Mod` use gets a TODO
     (`module-class-members`). With `--style=decorators`, `@Module` stays and its import
     moves to `@nexusdi/decorators`.
   - The class-to-const change gets a TODO at each site the codemod cannot rewrite:
     `typeof Mod` (`dynamic-module-typeof`), static members on the class
     (`dynamic-module-static`), a bare `imports: [Mod]`, which 0.4 rejects with
     `NEXUS_MODULE_OPTIONS_MISSING` (`dynamic-module-unconfigured`), and a spread of a
     `.config(v)` result (`dynamic-module-spread`). Calls to `getModuleConfig()` and
     `getConfigToken()` get a TODO (`dynamic-module-config-api`).
5. `container-bootstrap`: a function-local `new Nexus()` followed by `set()` calls in the
   same function, before any `get()`, becomes `await Nexus.create([...])` when every call
   registers a provider, and `await Nexus.create({ providers, imports })` when a call
   registers a module. A module-level `new Nexus()`, exported or not, gets a TODO
   (`top-level-container`), because the rewrite needs top-level `await`, which CommonJS
   output, Jest in CJS mode and some SSR builds lack. A `set()` after a `get()` or in
   another function gets a TODO (`set-after-startup`). A `set(ServiceClass)` becomes a
   bare entry in the provider array.
6. `module-exports`: 0.3 let any provider see every other provider, and 0.4 encapsulates
   modules. This transform computes cross-module token use from the static 0.3 module
   graph and adds the `exports` and `imports` the 0.4 compiler needs.
   - `context.moduleGraph` holds every module the codemod can resolve statically: its
     providers, its imports, and the tokens each provider depends on after transforms 2
     and 4.
   - For each dependency on a token another module provides, the transform adds the
     token to the provider module's `exports`, and adds the provider module to the
     consumer's `imports` when no import path already exports it.
   - For each `get(X)` and `has(X)` on the root container, it exports `X` along a path to
     the root module.
   - An added import that would create a module import cycle gets a TODO
     (`module-exports-cycle`).
   - Where the graph is dynamic, the transform writes a TODO (`dynamic-module-graph`)
     and adds nothing: computed `imports` or `providers` arrays, spreads, conditional
     entries, or registration outside a module.
7. `await-get`: `await container.get(X)` becomes `ship.get(X)`.
8. `container-leftovers`: each remaining container call gets a TODO: `resolve`
   (`container-resolve`), `clear` (`container-clear`), `list` (`container-list`),
   `createChildContainer` and `child` (`child-container`), and the async-branch
   `dispose()` and `init()` (`container-lifecycle`). `has` stays.
9. `imports`: rewrites import specifiers, moves the decorators' imports to
   `@nexusdi/decorators` and `createTestingContainer` to `@nexusdi/testing`, rewrites
   each `instanceof` of a 0.3 error class into `isNexusError` with the matching codes
   (section 0, D21), and removes unused imports. Any other use of a 0.3 error class, such
   as `new NoProvider()` or a subclass, gets a TODO (`error-class-use`). A use of a removed export gets a TODO: the provider types
   (`removed-provider-type`), the metadata API (`removed-metadata-api`) and the guards
   (`removed-guard`). Code that matches on a 0.3 error message gets a TODO
   (`error-message-match`), because 0.4 messages start with a code.
10. `tsconfig`: edits every tsconfig the project owns in its `extends` chain with a JSONC
    editor, so comments and trailing commas survive the edit. It removes
    `experimentalDecorators` and `emitDecoratorMetadata`. When a base in the chain lives
    in `node_modules` and sets either flag, the transform writes a local override to
    `false` in the project's own tsconfig. When the project still has decorators from
    other packages, it keeps the flags, writes a TODO (`legacy-decorators-in-use`), and
    the report says to use `static deps`, `provide()` and `defineModule()`, because
    `@Injectable` throws `NEXUS_LEGACY_DECORATORS` under the flag.
11. `package-json`: sets `@nexusdi/core` to the migration's version, and adds
    `@nexusdi/decorators` to `dependencies` and `@nexusdi/testing` to `devDependencies`
    at the same version when the migrated code imports them. It edits with a JSON
    editor that keeps the file's formatting.

After the transforms, the runner emits the note `eager-construction` once per project:
0.3 built each provider at its first `get()`, 0.4 builds every singleton at `create`, and
a provider with an expensive or side-effecting constructor may want `eager: false`. It
also emits the note `vite-decorator-plugin` once per project whose `package.json`
depends on `vite` 8 or later and whose migrated output uses `@Injectable`, `@Inject` or
`@Module`, which only `--style=decorators` produces. The note says that Vite 8's Oxc transform does not
lower standard decorators, and that the project either adds `@rolldown/plugin-babel` with
`@babel/plugin-proposal-decorators` (`version: '2023-11'`) or registers those classes
with `provide()` and `defineModule()`.

Every TODO and note has a stable code. The codemod package exports both lists, and the
docs site's guard enumerates them so each code has a docs entry:

- A dry-run test asserts that `--dry-run` writes nothing and prints the diff the real run

## 14. Release plan

0.4 is released as a release candidate first, so users can report problems before the
API is final.

- The versions are `0.4.0-rc.0`, `0.4.0-rc.1`, and onward, published under the npm
  dist-tag `next`. `nx release` numbers the first prerelease `rc.0`. `latest` stays on
  0.3.x until 0.4.0 final.
- An RC may break the previous RC. The RC's release notes list each breaking change, and
  the same RC includes a matching codemod update.
- `@nexusdi/core`, `@nexusdi/decorators`, `@nexusdi/testing`, `@nexusdi/node`,
  `@nexusdi/errors`, `@nexusdi/devtools` and `@nexusdi/codemod` publish at rc.0, at one
  version and dist-tag, so `npx @nexusdi/codemod@next 0.4` matches `@nexusdi/core@next`.
  `@nexusdi/federation` publishes in an RC before 0.4.0 final, as synthesis C7 placed
  `defineContract`. Users who run the codemod on real codebases give the RC its most
  useful feedback.
- `@nexusdi/react` ships in 0.4, before 0.4.0 final. It gets its own spec after this
  revision and targets rc.0 with the other framework adapters (section 0, D18).
- The docs site, with the Playground and the concept consoles, is in the RC plan. The
  Academy missions ship after 0.4.0 final, because they teach APIs that must be settled
  first.
- Feedback goes to a pinned GitHub Discussion, "0.4 RC feedback", and to a new issue
  template that applies the `rc-feedback` label. A maintainer adds `rc-blocker` to an
  issue that must be fixed before final.
- The release workflow needs a prerelease path: `nx release version --preid rc` and
  `nx release publish --tag next`. Every new package has never been published, so the
  owner bootstraps each with one manual publish and configures its trusted publisher, as
  `RELEASING.md` describes for `@nexusdi/core`.

0.4.0 final requires all of:

1. Four weeks have passed since the last RC that contained a breaking change.
2. No issue labelled `rc-blocker` is open.
3. The codemod has been verified against the repo's examples and at least one external
   codebase.
4. The integrations spec calls `nodeScopes()` where it called `runInScope` and
   `currentScope` (section 0, D20).

Docs during the RC: the docs deploy serves a frozen copy of the live 0.3 site at the root
and the new 0.4 site under `/next/`. At 0.4.0 final the two swap: the 0.4 site moves to
the root and the 0.3 snapshot moves to `/v0.3/`. The snapshot stays there for six
months after 0.4.0 final, or until 0.5.0 is released, whichever is later. The docs site
gets its own spec. This spec states only that the release depends on that deploy.

The rc.0 release checklist:

1. A blog post on the docs site announces the 0.4 RC. It covers what changed and why,
   the packages and the plugin API, the codemod, how to install `@nexusdi/core@next`, the
   feedback channel, and the timeline to 0.4.0 final.
2. An info box at the top of the repo root `README.md` and of each package's `README.md`
   (which npm renders) points to the RC, its docs at `/next/`, and the "0.4 RC feedback"
   Discussion. The box is added in the rc.0 release commit and removed or reworded at
   0.4.0 final.
3. The pinned Discussion and the `rc-feedback` issue template exist before rc.0 is
   published.
4. Every package of rc.0 is bootstrapped and publishes at `0.4.0-rc.0`.

### 14.1 Positioning

NexusDI is a DI container for any TypeScript app (section 0, D6). The README, the landing
page and the launch copy lead with one line (D7):

> NestJS-style modules and async startup for any TypeScript app, checked before it runs,
> with no compiler flags.

- Supporting facts, in this order: whole-graph validation at `create`, async factories
  with a synchronous `get()`, `forRoot` configuration, plugins for everything optional,
  a core that grows only with a stated reason,
  no `reflect-metadata`, TypeScript 5.4 to 7.
- Two guides show the shapes the wargame found strongest: one graph shared by an API, a
  worker and a CLI; and a shell with sections from several teams.
- A short "When you do not need a container" section closes the README and the landing
  page.
- Size figures in the README and the launch copy come from the size report's
  `size.json` on `main` (section 12.4).
- The first docs page uses classes as tokens (D8); the interface-first form starts on
  the second page.

- A legacy `emitDecoratorMetadata` mode that reads `design:paramtypes`. TypeScript emits
  `Object` for a parameter typed with an interface, so the mode cannot inject by

  class declares `static deps`.
- Nested scopes (section 3.6).
- The docs site restructure, beyond the `/next/` requirement in section 14.

Each item is a named test the 0.4 engine must pass. They live in
`libs/core/src/regressions/`, one file per item, titled in the indicative mood that

Details the titles leave out:

- R01 runs two async singleton factories at one level that share a dep. It runs 50
  concurrent `createScope` calls whose scoped factories share a scoped dep. It also calls
  a lazy thunk from an async factory's continuation: to an in-flight target the thunk
  throws `NEXUS_NOT_READY`, never a cycle error, and to a ready target it returns the
  instance.
- R06 puts a rejecting async factory three imports deep and asserts that `create`
  rejects with it and that the test process sees no unhandled rejection.
- R07 records `dispose:instance` events through an observing plugin and asserts that their
  sequence is exactly the reverse of the `construct` sequence for tracked instances, with
  one event per object. R07 also covers a factory that returns an existing singleton and a scoped factory that
  returns a root singleton: each object is disposed once, by the root.
- R08 resolves a disposable transient from the root, drops the reference, holds a
  `WeakRef` to it, runs `globalThis.gc()` under `--expose-gc`, and asserts the `WeakRef`
  is empty. It also asserts that a scope disposes every transient it built.
- R14 also resolves `{ token: T, useValue: undefined }` written as a provider literal.
- R15's provider object without a token is `NEXUS_INVALID_PROVIDER`, because an object
  without an own `token` is not a provider literal (section 3.2).
- R11 covers both shapes: `provide(A, { useClass: C })` plus `provide(B, { useClass: C })`
  gives two instances, and `provide(B, { useExisting: A })` gives one.
- R16 checks `has()` and `get()` on the root and on a scope, with and without the
  `{ module }` option.
- R20 runs in a Vitest browser-mode project and also backs the repo-check in section 12.

## 17. Test strategy

- Unit tests per layer. `definitions/` tests run without a container. `blueprint/` tests
  compile definitions and assert on the blueprint or on error codes and fields, without
  constructing anything. `runtime/` tests cover build order, readiness, `get`, `has`,
  scopes, `extend()`, `eager: false`, ownership, disposal and trace events. `plugins/`
  tests cover registration and the views.
- Type tests. `*.test-d.ts` files use `expectTypeOf` and `// @ts-expect-error`, as in the
  libraries repo. They cover token variance, every `provide()` overload, the deps mapping
  for each modifier, `NoInfer` on `useValue` and `useExisting`, the async-transient and
  promise-token messages, `@Injectable` deps checking, `REQUEST` augmentation,
  `override()` typing, and provider literals: every form, and an error on the offending
  element for a wrong dep, a missing dep, a bad value, an async transient, a lifetime on
  a value or an alias, a Promise-typed factory token, an unknown key and an unannotated
  factory, in `defineModule` and in `@Module`; `useClass` without `deps`, with the
  `static deps` check still applied through it; and `static deps`: every class form
  accepts a class whose `static deps` fits, and a bare class whose own or inherited
  `static deps` does not fit reports the error on the element. They also cover
  `forRoot` and `forRootAsync` (a value of the wrong shape, a factory whose parameters
  come from `deps`, an options object holding a `useFactory` function accepted as a
  value), `eager` (rejected on an async factory, on a class with an async `onInit` and
  beside `lifetime: 'transient'`), the provider array and the object form of
  `Nexus.create`, and `NexusPlugin` (a hook of the wrong type, and a `construct` hook
  whose return type is checked against `unknown`). Vitest's typecheck mode runs them on TS 6.0.3, the workspace
  version. A failed `expectTypeOf` assertion is itself a type error, so a separate CI job
  checks the same files with plain `tsc --noEmit` on TS 5.4 (the floor) and with `tsgo`
  from `@typescript/native-preview` on TS 7, without Vitest.
- Diagnostic tests. `libs/core/src/definitions/provide.diagnostics.test.ts` compiles the
  fixtures behind the table in section 4.3 with the TypeScript compiler API and asserts
  that each diagnostic's message chain contains the real cause: the missing property for
  a wrong dep, the argument count for a missing dep, the unknown property for a bad
  value, the `NEXUS_ASYNC_TRANSIENT` and `NEXUS_PROMISE_TOKEN` strings, and
  `NoLifetimeMessage` for a lifetime on `useValue` or `useExisting`.
  `provider-literal.diagnostics.test.ts` does the same for the table in section 4.6 and
  also asserts the source text each diagnostic points at, so an error that moves off the
  offending element fails the test.
- Literal equivalence. `records.test.ts` normalises each literal form and the matching
  `provide()` call and asserts equal record shapes and equal errors, including a
  polluted `Object.prototype`, an inherited option, an unknown key and a throwing getter.
  The same file covers `static deps` in every class form, inheritance, an explicit
  `deps` winning, the `@Injectable` conflict, and a polluted `Function.prototype`.
- Concurrency tests. Parallel levels with shared deps, many concurrent `createScope`
  calls, a failure in one branch of a level while others are in flight, concurrent
  `load()` calls, disposal while a `load()`, a `createScope()` and an `extend()` are in
  flight, two `extend()` calls on one scope, and a `load()` that publishes during an
  `extend()`. The tests use deferred promises, never timers, to control interleaving.
- `extend()` tests. One test per rule of section 7.4, and a test that asserts, for every
  module that existed before a `load()`, that its visibility map after the load is a
  superset with equal entries for the old tokens.
- `eager: false` tests. A singleton and a scoped factory built on first `get()`, through
  a dep, through a lazy thunk and through `resolve()`; an eager dependent that builds it
  at `create`; disposal order with a late-built instance; `NEXUS_LAZY_ASYNC` for a
  thenable from a factory and from `onInit`, with no unhandled rejection; a retry after a
  failure.
- Plugin tests. Registration: each `NEXUS_PLUGIN_INVALID` reason,
  `NEXUS_PLUGIN_VERSION`, and all faults in one `BlueprintError`. Order: one test per
  row of the table in section 3.10.2. Compile hooks: a rewrite that breaks a dep, forms a
  cycle or violates a lifetime fails validation; `pin`; `NEXUS_PLUGIN_CONFLICT`; check
  errors after core's; hooks in `load()` and `Nexus.check`. `tokenKey`: two tokens on one
  key collide as duplicates. `construct`: the returned object is what `get()`, deps,
  `onInit` and disposal see, a thenable is `NEXUS_PLUGIN_FAILED`, and a throw is a
  `ProviderError`. `setup` runs after `onInit` and not after a failed `create`;
  `dispose` runs in reverse order and chains its errors. Invariants: every view is
  frozen, and a change to a definition, a class or a view after compile changes nothing.
- Dogfooding. A repo-check fails when an optional package imports a core path other than
  the package entry (section 12.1), and each package's own tests run against the packed
  core tarball, which exports nothing else.
- Error tests. Every error test from revision 1 runs twice. With `errors()` registered it
  asserts revision 1's message text unchanged, character for character, including the
  near misses, the fix lines, the requester and entry locations and the `BlueprintError`
  text. Without a plugin it asserts the code, every field and the one-line message. The
  `formatError` contract of section 9.1 has its own tests: a throwing hook leaves the
  line, an error is formatted once, and `explain()` returns the same text as the
  plugin.
- Lifecycle tests. `onInit` order against the dependency graph, the exact reverse-creation
  disposal order read from `dispose:instance` events for the root and for a scope, no
  `dispose:instance` event for a `useValue` value or an untracked transient, `NEXUS_NOT_READY` for
  each of the three cases in section 6.3, disposal order, thunks during disposal,
  `SuppressedError` chaining, and the `ProviderError` fields after a partial startup.
- README doctests. `libs/core/README.md` examples run as tests through the region loader
  and the `// -> value` rewriter from the libraries repo's `tools/doc-examples`.
  `chore/tooling-upgrade` does not include that tool, so porting it is a prerequisite of
  the docs work.
- Packaging. `scripts/verify-packaging.mjs` packs every package and `@nexusdi/codemod`,
  installs the tarballs into throwaway consumers, and checks:
  - A CommonJS consumer `require()`s `@nexusdi/core` and each optional package,
    destructures `{ Nexus, provide }`, and resolves a provider, on Node 22.12 (the
    `engines` floor) and on Node 24.
  - No module in the published output uses top-level `await`, which would make
    `require()` throw `ERR_REQUIRE_ASYNC_MODULE`.
  - Every entry keeps its `default` condition and has no `require` condition.
  - Every entry resolves with types under `moduleResolution: nodenext` and `bundler`.
  - Every optional package's `peerDependencies` names `@nexusdi/core` at exactly the
    version being packed.
  - A consumer with `lib: ["es2022"]`, no `@types/node` and `skipLibCheck: false`
    compiles `await using ship = await Nexus.create(...)`.
  - A consumer compiles a class decorated from `@nexusdi/decorators` with no
    `experimentalDecorators`.
  - A bundle of `@nexusdi/core` alone contains no `Symbol.metadata` assignment.
  - The codemod's bin runs.
- Codemod tests, as section 13.2 describes, with fixtures for both `--style` values.
- The regression list in section 16.
- Coverage thresholds follow `tools/repo-checks/src/coverage-config.test.ts`.

### 17.1 Toolchain matrix

`examples/toolchain-matrix` builds and runs the packed `@nexusdi/core` under ten
toolchains, in two variants each, and compares every run's output with `golden.json`:

- Variants. `plain` uses `static deps`, `provide()` and `defineModule()` in erasable TypeScript only. `decorated` uses `@Injectable`, `@Inject` and `@Module` from `@nexusdi/decorators`.
- Cells, with the versions `toolchains.json` pins: tsc 6.0.3, TypeScript 7.0.2 (`tsgo`),
  esbuild 0.28.2, SWC 1.16.2, Babel 8.0.6, Vite 8.3.0, Vite 8.3.0 with the Babel plugin,
  Bun 1.4.2, Deno 2.9.6, and Node 24's type stripping (`node-strip-types`).
- Two cells are unsupported, and the matrix records why: `decorated` on Vite, because
  Vite 8.3 (Oxc) passes standard decorators through unlowered and no option lowers them,
  with the Vite-plus-Babel cell as the workaround Vite's migration guide documents; and
  `decorated` on `node-strip-types`, because Node erases types and lowers no syntax.
  Every other cell passes.
- `toolchain-matrix.json` holds the result of each cell (toolchain, version, variant,
  `pass` or `unsupported` with a note). The matrix script writes it, and with `--check`
  it fails when a fresh run differs from the committed file.

### 17.2 The size fixture

`examples/size` holds the fixture the size report of section 12.4 measures: an ESM
consumer (`"type": "module"`) whose `main.ts` defines two services, one depending on the
other through `static deps`, passes both to `Nexus.create`, and calls `get()`. Each
optional package has a sibling fixture that adds the package's main export to the same
app. `size-report.json` holds the threshold (`{ "coreGrowthPercent": 2 }`). A test of
the job's script runs it on a pair of fixed bundles and asserts the comment table, the
failure over the threshold, and the pass once the description has a `## Size` section.

### 17.3 The dispatch benchmark

A benchmark in `libs/core/bench` runs `create`, 10,000 `get()` calls and 1,000
`createScope` calls over graphs of 50 and 2,000 providers, with no plugin registered,
against the same build compiled with every hook site removed by a build-time constant.
It fails when the median of the build with hook sites is slower than the other's by more
than the run-to-run noise it measured for the pair, so "no measurable cost" is a test.
