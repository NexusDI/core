## 1. Problem

The docs site sells NexusDI to two readers and teaches one. The evaluator arrives at `/` and
decides in a few seconds whether NexusDI solves a problem they have. The
learner walks the Concepts band and needs each mechanism to make sense. Today `/` is the
overview page of docs-site section 5.2: an H1, four H2 sections, one executed region, one
numbered list and one bullet list. The owner judged it weak on 2026-10-02 and asked for a
sales page with mostly graphics and a little fun, built around a schematic of the Starship Meridian, and running the
real `@nexusdi/core` in the browser.

The owner's front-page concepts settled the interactions (concept E): cut a conduit and
watch `Nexus.check` name the broken link, and power up the ship to show async startup.
The owner added the faults on 2026-10-03. The design system replaced concept E's cel-shaded look with the grounded one. No
spec yet says what the page holds section by section, what each interaction prints, what a
reader without JavaScript sees, or how the page fits the budgets the build already checks.
The same gap holds for the feature pages and for the docs chrome under the new look.

The positioning, set by the owner on 2026-10-01: if it type-checks and starts, the wiring
is right. TypeScript checks each `deps` list against its constructor, and `Nexus.create`
and `Nexus.check` check the whole graph before anything builds. The claim covers the
wiring. It says nothing about the reader's own code. Each page in this spec shows the type
check or the startup check.

## 3. Who reads which surface

| Reader                                         | Arrives at                               | Needs in the first minute                             | Leaves to                           |
| ---------------------------------------------- | ---------------------------------------- | ----------------------------------------------------- | ----------------------------------- |
| An evaluator from a link or a search           | `/`                                      | what NexusDI is, the claim, proof the claim holds     | `/getting-started/`, a feature page |
| An evaluator comparing containers              | `/`, `/comparison/`, a `/features/` page | which features NexusDI has that their container lacks | `/comparison/`, GitHub              |
| A learner on the teaching path                 | `/getting-started/`, a concept page      | the mechanism, a program that runs, a way to break it | the next concept page               |
| A user with a goal (an error, an API, a guide) | `/errors/<CODE>/`, `/api/`, search       | the answer, the fix, the signature                    | back to their code                  |

The front page and the feature pages serve the first two rows, and the docs chrome serves
the last two. The two kinds of surface share the bulkhead and the ship, so a
reader who follows a link from a feature page into a concept page stays on the same ship.

## 4. The front page

### 4.1 Shape

contents, as `content/_meta.ts` already sets. It keeps `kind: overview` (U1), so it still
holds a two-sentence definition, one executed region, when to reach for NexusDI, when to
skip it, and the entry links the overview kind requires. The page orders them for the
evaluator and shows most of them as graphics.

### 4.2 Hero

The hero opens on the painted Meridian against space: the `sv01-hero` three-quarter render
(design system 8.1), as the mesh render until the paint-over exists. The starfield of
design system 9.4 shows around the hull. The headline sits over space at the left on a
wide screen and under the art on a phone.

Copy (Q2):

- Headline, in `display`: "If it type-checks and starts, the wiring is right."
- Definition, in `lead`, two sentences: "NexusDI is a dependency injection container for
  TypeScript. It checks every module, provider and dependency before it builds anything."
- One button, "Get started", to `/getting-started/`. It is the hero's `primary` button,
  and each screen of the page has one `primary` button at most (design system 7.4).
- The install line in a terminal strip with a copy button: `npm install @nexusdi/core@next`
  during the RC, `npm install @nexusdi/core` from 0.4.0 final. Beside it, in `micro`, the
  version that `app/release-state.ts` reads at build time, such as "0.4.0-rc.3 on the
  `next` tag". The page hard-codes no version.
- A quiet link under the button: "See the pre-flight check", an anchor to section 4.3,
  whose bay carries the id `pre-flight`.

The art is a `<picture>` with AVIF and WebP sources at 1x and 2x, and a phone crop at
720 pixels wide. It carries `fetchpriority="high"` and fixed `width` and `height`, so the
hero never shifts the layout. Its `alt` reads "The Starship Meridian, a survey frigate, in
space." The headline renders as text and is the largest contentful paint candidate on a
phone, where the art sits below it.

The hero moves only in its starfield, which runs inside the hero's frame under the
frame-rate and battery rules of docs-site 9.3 and the 8 kB budget of 9.4. It renders one
frame under reduced motion. The starfield runs longer than five seconds, so the hero and
the footer carry the "Pause background" switch of docs-site 16.1 (WCAG 2.2.2). Without JavaScript the starfield is a static image baked into the
art, and every other part of the hero is HTML.

### 4.3 The pre-flight bay

The pre-flight bay is the page's centre. It holds the vector cutaway, and the terminal
with its controls. The cutaway is `ship_svg.py`'s side cutaway inlined as SVG at
16 pixels per metre on a wide screen, 12 on a tablet, and one hull section at a time on a
phone (section 4.11). It draws the hull sections, the systems in them, the conduits
between sections and a hatch on each section's edge for each export.

The front page's conduits are the module-import layer of ship-systems 16.5: one conduit
per entry of a module's `imports`, drawn as the DI edges of design system 8.4 (1px `data`,
a broken one in `alarm` ending at an empty socket labelled with the token). The cutaway
draws no power, coolant or atmosphere lines, since the docs ship simulates no physics. A
powered room fills with `lamp` at 12% over its `screen` fill, an unpowered room keeps the
plain fill with its emissive screens lit, and an alarmed room pulses an `alarm` fill at
12% (design system 9.2). Design system 8.4 lists these three fills.

The program is the docs ship of docs-site section 7.1 (U5), placed by ship-systems 16.3:

| Hull section                            | Module        | Systems (providers)                                                                                                                                                                                            | Hatches (exports)     |
| --------------------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| engineering, reactor bay, computer core | `Engineering` | `REACTOR` (`FusionReactor`) on the reactor bay's `reactor-bay.vessel`, `COMPUTER` (`QuantumComputer`) in the computer core                                                                                     | `COMPUTER`            |
| comms                                   | `Comms`       | `SUBSPACE_LINK`, from `ShipComms`, the one `Comms.forRoot()` constant that `Tactical` and `Meridian` both import                                                                                               | `SUBSPACE_LINK`       |
| chart room, drone bay                   | `Tactical`    | `NAV_CHARTS` (async factory), `DRONE` (`SurveyDrone`, transient)                                                                                                                                               | `NAV_CHARTS`, `DRONE` |
| shuttle bay                             | `BridgeApi`   | `FLIGHT_LOG` (`ShuttleFlightLog`, scoped)                                                                                                                                                                      | `FLIGHT_LOG`          |
| bridge                                  | `Meridian`    | the root; it imports `Engineering`, `ShipComms`, `Tactical` and `BridgeApi` and binds `DIAGNOSTICS_PANEL` (`StatusBoard`, deps `[COMPUTER, SUBSPACE_LINK]`); the bridge readout reads `NAV_CHARTS` and `DRONE` | none                  |

The seed is a region in `examples/meridian/src/pages/index.md`, so the examples test runs
it and the page's executed region is the same program. Two rules shape it:

1. Each module that another module imports is also reachable from the root on a second
   path, so a cut conduit leaves the exporting module in the graph and the error names the
   near miss ("SubspaceLink is exported by Comms, which Tactical does not import").
2. The system the offline drill removes has consumers in two modules, so one
   `BlueprintError` lists two `NEXUS_MISSING_PROVIDER` entries, beside the `NEXUS_INVALID_EXPORT` of 4.6.

`NAV_CHARTS` awaits a chart download of 400 ms in its factory, so the power-up shows an
async provider holding its level open for a visible time. Each new name the seed needs
goes into docs-site section 7.1 first, in the pull request of delivery step 2.

A legend sits in the bay's top edge, as four placards with a line to an example on the
ship: "Hull section = module", "System = provider", "Conduit = dependency", "Hatch =
export". Every label on the ship pairs the ship word with the code name, such as "Comms
(module)" and "SubspaceLink (provider)".

The terminal (design system 7.2) sits beside the cutaway on a wide screen and under it on
a phone. Its header reads `preflight.ts`. Its body shows the program the CI step runs:

```ts
import { Nexus } from '@nexusdi/core';
import { errors } from '@nexusdi/errors';
import { Meridian } from './meridian.js';

Nexus.check(Meridian, { plugins: [errors()] }); // CI runs this
console.log('pre-flight ok');
```

Its output pane shows the run: `$ npm run preflight`, then either `pre-flight ok` with
`exit 0` and the nominal status, or the error text and `exit 1` with the alarm status. The
error code in the output links to its page at `/errors/<CODE>/`.

The controls sit in a panel beside the terminal:

- The drills: four buttons, each a one-click fault (sections 4.5 and 4.6).
- The system list: every conduit, system and hatch on the ship as a rocker switch with its
  state word (design system 7.4), grouped by hull section. This list is the keyboard and
  screen-reader path to every part of the ship (section 4.12).
- "Launch", the bay's one `primary` button, and "Reset", a `secondary` one. The drill
  buttons are `secondary` with no confirm: they act on a simulation that Reset restores,
  so none is destructive in the sense of design system 4.2.
- "Show the graph", the overlay switch of section 5.4.

A reader can also click a conduit, a system or a hatch on the cutaway itself. The click
flips the same switch in the system list, so the two never disagree.

### 4.4 Launch and the power-up

Launch runs `Nexus.create(Meridian, { plugins: [errors(), trace(record)] })` over the
current state of the ship. The power-up is the page's one orchestrated motion (design
system V6). It lights the ship in the order core reported.

The script:

1. The reader presses Launch. The button reads "Launching" and is `aria-disabled` until
   the run ends. Every hull section dims to its unpowered state: dark but for its emissive
   screens.
2. The terminal prints `$ npm start` and `ship = await Nexus.create(Meridian)`.
3. A `construct:await` event marks an async factory that has started and not settled: its
   system takes the `active` status (filled circle, data cyan) and a callout (design system
   7.3, `HoloLabel`) reading "Downloading charts" for `NAV_CHARTS`. A `construct` event
   marks a stored instance: its system turns `nominal` with the callout "Online". A
   provider with an `onInit` stays `active` until its `init` event, since core emits
   `init` only for such a provider. A hull section takes the powered `lamp` fill of section
   4.3 once every singleton in it is nominal. Transient and scoped providers build nothing
   at startup and emit no `construct`, so a section that holds only those (the shuttle bay
   with `FLIGHT_LOG`) shows the standby status with "Builds per request", and the drone bay
   lights from `DRONE`'s first `get()`. The options value of `Comms.forRoot()` emits a
   `construct` with `level` null and lights nothing.
4. Systems in one build level light together. `NAV_CHARTS` holds its level for its real
   400 ms, so the reader sees the next level wait on it.
5. The live region and the step list beside the ship read one line a level, numbered from
   the events' `level` field plus one, since core counts levels from 0: "Level 1.
   Reactor and Comms online." "Level 2. Computer core and Tactical online." "Level 3. Diagnostics online." The fixture's
   trace gives the real lines.
6. The run ends. The terminal prints the startup time core measured, in `data`, and
   "Ready." The bridge readout shows `ship.get(NAV_CHARTS).plot('Kepler-442b')`'s answer.
   Launch reads "Relaunch".

Steps run at the sequence tier, 120 ms a step and 2.4 s at most (design system 9.1), and
the factory's real 400 ms counts inside that. A run with more steps than fit shortens the
step.

Autoplay: the power-up runs Launch's `Nexus.create` on the seed state and plays once per session, from dark, after the run chunk of 5.6 has
loaded and once the bay is at least half in view (Q5). It runs 2.4 s at most. It never
plays when `navigator.connection.saveData` is true or under reduced motion. It never
blocks a control: any control stops it, and the
ship jumps to its final state. Under reduced motion, Launch shows the final state at once
and lists the order as text in the step list (design system 9.5). The server HTML holds
the lit state, so a reader without JavaScript and a screenshot see the ship lit, and the
bay dims only when the power-up starts.

Without JavaScript the bay renders the final lit state from the fixture, the terminal
shows `pre-flight ok`, and Launch is absent. A line under the terminal says "The
pre-flight check runs in your browser with JavaScript." The step list renders the fixture's
level order as text.

### 4.5 Cut a conduit

The cut conduit is concept E's interaction, the one the hero link points at. The first
drill button reads "Cut a conduit" and cuts the conduit from Comms to Tactical. A static
placard "Cut me" (Q4) points at that conduit until the reader uses any control. The
placard does not move, since the power-up is the page's one motion that runs unprompted.

The script:

1. The reader cuts the conduit with the drill button or with a click on the conduit
   (which flips its switch in the list). The conduit shows a gap where the reader cut it.
2. In the same frame, the page rebuilds the root from the ship's state (Tactical no longer
   imports Comms) and runs `Nexus.check` with the `errors()` plugin.
3. The check's failure drives the ship. The conduit turns `alarm` red, and an empty socket
   labelled `SubspaceLink` appears at the Tactical end, placed from the `BlueprintError`
   fields (design system 8.4, section 5.2). A callout reads "Link lost". The alarm banner
   (design system 7.6) drops across the top of the bay:
   "NEXUS_MISSING_PROVIDER in Tactical", with the line "NavCharts (provider) in Tactical
   (module) cannot reach SubspaceLink. Launch is locked." The banner announces once,
   assertive. The chart room takes the alarm fill, pulsing at 1 Hz.
4. The terminal prints the check's output, `exit 1` and the alarm status. The text is what
   core and `@nexusdi/errors` print (section 5.9).
5. Launch stays disabled, with the reason beside it: "Launch is locked until the check
   passes."
6. The reader restores the conduit. The check runs again and passes. The banner clears,
   the terminal prints `pre-flight ok` with the nominal status, a callout reads "Linked",
   and Launch unlocks.

The reader may cut several conduits and take several systems offline at once. One check
then lists every error in one `BlueprintError`, which the terminal shows entry by entry
and the banner counts ("3 errors"). This shows the claim in the comparison of section 4.9:
NexusDI reports every missing provider in one error.

### 4.6 The three faults

Each fault is a drill button and a set of switches. Each drill states what it changes in a
placard on the ship, so the reader sees the cause beside the effect.

#### Take a system offline

The drill removes a provider from its module: the system goes
dark with the `offline` status (crossed circle) and the placard "Removed from
Engineering". `Nexus.check` fails with one `NEXUS_MISSING_PROVIDER` entry for each
consumer, in each module that consumes it (rule 2 of section 4.3). The drill for `COMPUTER` leaves Engineering exporting what it no longer provides, so the check lists three entries: `NEXUS_INVALID_EXPORT` for Engineering, then `NEXUS_MISSING_PROVIDER` in Meridian (`DiagnosticsPanel`) and in Tactical (`SurveyDrone`), and the banner reads "3 errors". Each consumer
gets an empty socket labelled with the missing token. Launch locks. When the reader restores the system, the check
passes.

#### Close a hatch

The hatch shows hazard banding when closed (design system 4.5). Core
raises `NotVisibleError` (`NEXUS_NOT_VISIBLE`) for a root `get()` of a token that a module
keeps private, and `NEXUS_MISSING_PROVIDER` with a "does not export it" line when another
module's provider needs it. The drill shows the importer case (Q3):

1. The drill closes Engineering's `COMPUTER` hatch. The placard reads "Hatch closed:
   Engineering keeps ShipComputer private".
2. `SurveyDrone` in Tactical and `DiagnosticsPanel` in Meridian need `COMPUTER`, so
   `Nexus.check` fails with two `NEXUS_MISSING_PROVIDER` entries, and the text names the closed hatch: "ShipComputer is
   provided in Engineering, which does not export it."
3. The banner reads "2 errors" with the first entry, "NEXUS_MISSING_PROVIDER in Meridian", and Launch locks.
4. When the reader reopens the hatch, the check passes.

Free play and the `/modules/` explorable of section 7 keep the root-lookup case:

1. The reader closes Tactical's `DRONE` hatch. No module depends on `DRONE`, so the check
   passes and Launch stays open. The placard reads "Hatch closed: Tactical keeps
   SurveyDrone private".
2. The reader launches. The power-up runs, and the bridge readout calls
   `ship.get(DRONE)`.
3. The readout fails. The terminal prints `NEXUS_NOT_VISIBLE` and its fix line, the bridge
   shows the alarm, and the banner reads "NEXUS_NOT_VISIBLE on the bridge".
4. A caption under the terminal states what happened: "The wiring passed. The bridge's
   lookup is your own code, which no check sees, and it asked for a system that Tactical
   keeps private."

#### Fail at startup

The drill flips the chart room's switch "Chart server: reachable" to
"unreachable". `NAV_CHARTS`' factory then rejects.

1. The check passes, and the terminal prints `pre-flight ok`. A placard on the chart room
   reads "The check runs no factories".
2. The reader launches. The power-up lights levels 1 and 2. The chart room shows
   "Downloading charts", then the alarm.
3. `Nexus.create` rejects with `NEXUS_PROVIDER_FAILED` and the factory's error as its
   cause. Core rolls back: each `dispose:instance` event dims its system, newest first, so
   the lit ship goes dark in reverse order. Core emits `dispose:instance` only for an
   instance with a disposer, so a built system with none dims with the `run` event that
   ends the failed startup.
4. The terminal prints the error with its cause first, as the error view of docs-site 12.3
   does. The caption reads "Nexus.check passed: the wiring is right. The chart server
   failed at startup, and Nexus.create took down what it had built."

In this drill the reader sees what the check covers and what it leaves to startup, so the
headline claims no more than core does.

Reset returns every switch to its seed state and reruns the check.

### 4.7 Type-checks

The section under the bay shows the other half of the headline: TypeScript checks a
class's `deps` against its constructor. It holds one `twoslash` fence, compiled at build
time by the site's twoslash runner with its `@errors:` declaration (no TypeScript loads in
the browser): `QuantumComputer` lists `[SUBSPACE_LINK]` in `static deps` where its

## 5. The front-page run

### 5.1 State

The bay holds one state object: for each conduit, system and hatch, whether it is intact,
plus the chart-server switch. A pure function `rootOf(state)` builds the `Meridian` module
from the seed's parts for that state. Every check and every launch calls it, so the ship
on screen and the module core checks come from one source.

### 5.2 Check

A change to the state runs `Nexus.check(rootOf(state), { plugins: [errors()] })`
synchronously in the click handler. The check calls the options schema of `Comms.forRoot()`
and no other user code, so it runs in well under a frame on the Meridian's sizes. The handler then maps each entry of the thrown
`BlueprintError` onto the ship through its fields: `token`, `requester` and `module` place
the empty socket, and the near miss names the cut conduit or the closed hatch. The scene
reads the fields only through what core exports (extension principle P1) and never parses
a message.

### 5.3 Launch

Launch awaits `Nexus.create` with the `trace` plugin from `@nexusdi/devtools`, collects the
events, and plays them as section 4.4 describes. The scene keeps the live ship until the
next state change or Relaunch, then disposes it with `await ship[Symbol.asyncDispose]()`.

### 5.4 Overlay

The bay's toolbar has one switch, "Show the graph", that draws the network overlay of
ship-systems 16.5 from `inspect()` of the root, with the edge styles of design system 8.4.
While the overlay is on, the module-import conduits dim to 40%, so the provider edges read
on top of them.

### 5.5 Fixture

`apps/docs/tools/scene-fixtures.mjs` runs the seed in Node against the
workspace-built core at build time, once for the seed state and once for each drill. Each
run records the check's output, the trace events with every `*Ms` field set to 0 (`startMs`, `syncMs`, `awaitMs`, `finishMs`, `durationMs`; a null `awaitMs` stays null), and the
terminal text, and writes one JSON file per state to `components/front-page/fixtures/` (generated, not committed). The server renders the bay from the
seed state's file. The scene's unit tests assert that a browser run and the fixture agree
on every code and every event type.

### 5.6 Loading

The bay's client code splits in two:

1. The bay controller: the state, the switches, the SVG bindings and the terminal.
   `index.mdx` loads it with `import()`, so no other page carries it (section 12.1).
2. The run: core, `@nexusdi/errors`, `@nexusdi/devtools`' `trace` and `inspect`, and the
   seed. It loads when the bay nears the viewport, or on the first control the reader
   uses, whichever comes first. A control used before it arrives queues and runs on
   arrival, under a "Running pre-flight" status.

The owner asked for some fun. The ship responds to the reader: a room pulses its alarm
when the check names one of its providers, and the lit ship goes dark in reverse order as
core emits each `dispose:instance` after a failed startup (4.6). Each of these follows a
container outcome. Concept E also had a CRT toggle, sound, music and four hidden secrets in

### 6.3 F1, extension points

The question the page answers: how does a library own a collector that every module feeds?

The explorable shows the power bus. `PlasmaRouter` in Engineering reads
`all(POWER_CONSUMERS)`. Four contributor modules (life support, comms, propulsion,
weapons) each hold one contribution. The router's `all()` edges draw along the power routes
of ship-systems 16.5 to each contributor, and the router's readout lists the loads it
read.

The script:

1. The reader docks the weapons module into the root. The router's list grows by one, and
   Engineering's code panel shows no change: no module imports a contributor (K1).
2. The reader flips weapons' "Publish" switch off, which removes `POWER_CONSUMERS` from its
   exports. The check fails with `NEXUS_UNREAD_CONTRIBUTION` and its three fixes (K2). The
   weapons edge shows the alarm. When the reader flips it back, the check passes.
3. The reader flips "Weapons reads the router", which gives the weapons mount a dependency
   on `POWER_ROUTER`. The check fails with `NEXUS_CIRCULAR_DEPENDENCY`, and the cycle draws as
   a ring. The reader then flips the router's "Read lazily" switch, which makes its read
   `lazy(all(POWER_CONSUMERS))`, and the ring breaks for every contributor at once (K3).
   Core's fix line for this ring suggests `lazy(PowerConsumer)`, which core rejects with
   `NEXUS_INVALID_PROVIDER` (issue #248). Until that is fixed, the caption names
   `lazy(all())` and the terminal shows core's text as printed.
4. The reader presses "Load the FTL drive". The scene calls
   `ship.load(FtlDrive, { imports: [Engineering] })`, and the FTL core lights after the
   ship has started (K4). A switch "Import Engineering" off makes the same load reject with
   `NEXUS_BLUEPRINT_INVALID` holding `NEXUS_MISSING_PROVIDER` for `PowerRouter`, whose near
   miss reads "PowerRouter is exported by Engineering, which FtlDrive does not import."
   `NEXUS_LOAD_IMPORT` covers other cases: a load import of a module the graph lacks, of the
   root, or changed load imports on a repeat load.
5. "Check the load" runs `Nexus.check(root, { load: [{ module: FtlDrive, imports:
[Engineering] }] })`, so CI checks the load import before anything starts. With the
   import switch off, it throws the same `BlueprintError` as the load.
6. A switch "FTL core draws power" makes `FtlDrive` export a `POWER_CONSUMERS`
   contribution. The load rejects with `NEXUS_LOAD_CONTRIBUTION`: "FtlDrive publishes a
   contribution to PowerConsumer, and load() cannot add to a multi token: collectors built
   at startup hold their lists."

Interaction test: K1 changes where a contribution flows. A reader who docks a module sees
the list grow, and each step stands in for a paragraph of extension-points sections 4 to 7.

## 8. The explorable contract

### 8.1 Frame

An explorable is a screen (design system V1) set into the article or the feature page. Its
frame is a `ConsoleFrame` on the `screen` face, which stays dark in both themes as the
terminal's does (design system 7.2), with a placard title and these parts:

- the stage: the ship view or the graph the lesson needs;
- the controls: amber, with control shapes (design system 4.2 and 7.4);
- the readouts: cyan, in `readout` type with units in `micro`;
- the terminal, when the lesson prints something;
- the caption: one sentence in `small` under the stage that states what the current state
  shows, updated with the state.

Every time-based explorable has the same four controls in the same place, so a reader
learns them once: Play or Pause, Step, Reset, and a speed control. The speed control is a
three-option segmented control (0.5×, 1×, 2×), a row of `secondary` buttons with the
current one pressed. A step at 1× takes the sequence tier's 120 ms (design system 9.1),
and a step that waits on real async work takes as long as the work. An explorable without
time has Reset alone beside its own controls.

An author places it in MDX as `<Explorable seed="<id>" steps={[...]} caption="..." />`.
`caption` is required, as for `ConsoleView`. Delivery step 3 extends G4 (`doc-control`)
to accept `<Explorable>` as a section's control and to fail one without a caption.

### 8.2 Run

An explorable imports core and its seed as an ordinary client chunk (U2). Its seed is
trusted code from a doctested region, so it needs no sandbox. The sandboxed runtime of
docs-site section 11 runs only code a reader edits, and "Edit this in the Playground" hands
the seed to it.

An explorable reads core's results through exported fields alone (extension principle P1):
error `code`s against the codes core exports, trace events by `type` against
`TraceEventByType`, and graph nodes through `NexusGraph`. A code or event type the
explorable does not know renders as a plain line in the terminal (P2).

### 8.3 Without JavaScript

Every explorable renders its first state on the server from a fixture that
`scene-fixtures.mjs` of section 5.5 writes, one file per seed and state (U3): the stage as static SVG, the readouts as text, the
terminal as its output. The controls render `hidden` and show once the explorable has
hydrated, as `ApiFilter.tsx` does, so a reader without JavaScript sees no control that does
nothing. The caption states the first state's lesson in words.

### 8.4 Reduced motion

Under `prefers-reduced-motion: reduce` an explorable opens paused on its final state, a
step changes the highlight with no animation, an alarm holds a steady border, and conduit
flow shows a static arrow (design system 9.5).

### 8.5 Keyboard and screen readers

Every control is an HTML button, switch or input in the DOM. The stage is `aria-hidden`,
and a DOM list beside it names each part with its state, as the front page's system list
does. Each step announces as one sentence in a polite live region ("ShipComputer
constructed in level 1"). Focus never moves on its own.

### 8.6 Loading

The fixture's static render is in the page HTML. The explorable's code loads when its frame
nears the viewport, and core loads with the first explorable on the page. A page with
several explorables loads core once. The chunks carry the marker strings of section 12, so
`check-budgets.mjs` counts each against its own row.

## 10. View transitions

Navigations inside the site go through `next/link`, so they stay in one document. They
animate with React's `<ViewTransition>`, which the router triggers when Next's
`experimental.viewTransition` flag is on. The first implementation task checks the flag
under `output: 'export'` on Next 16.4.2. If the flag fails there, the site keeps the
instant swap for navigations and keeps the in-page transitions of docs-site 10.5.

Design system 9.3 sets cross-document view transitions for page navigations. Next's
client router makes most navigations same-document, so this section refines 9.3: the same
two names animate through `<ViewTransition>` within the document, and the cross-document
rule covers full loads. Design system 9.3 records the refinement.

Two names carry across a navigation:

- `meridian-ship`: the front page's crop that the reader clicked, the feature page's header
  crop, and, on a concept page with a shared explorable, its stage. A page assigns the name
  to one element at a time: the front page sets it on the clicked crop alone.
- `meridian-article`: the article plate on every docs page, so the plate stays in place and
  only its contents change.

A full page load (a link from outside, a reload, a swap between `/` and `/next/`) uses
`@view-transition { navigation: auto; }`. A browser without the API swaps with no
animation. Under reduced motion every transition is instant, as `global.css` already sets.

## 11. Service worker

### 11.1 What it caches

The site registers `sw.js` from the base path with that path as its scope (Q9). The root
build registers `/sw.js` with the scope `/` and excludes `/next/` and `/v0.3/` in its
fetch handler, and the `/next/` build registers `/next/sw.js` with the scope `/next/`.
Each worker prefixes its cache names with its base path (`root-`, `next-`), so the two
never read each other's caches. The Academy's pages sit inside their base path's scope and
use its worker, and the Academy registers no worker of its own
(`specs/2026-10-29-meridian-map-runtime-ux.md` section 6.10). The page registers the
worker with `updateViaCache: 'none'`, so the browser fetches `sw.js` and its imports from
the network on every update check. The worker registers after the page has loaded and gone idle,
and it skips precaching when `navigator.connection.saveData` is true.

The fetch handler answers same-origin GET requests alone and leaves every other request to
the browser. The Playground's run frame has an opaque origin (docs-site 11), so the worker
never controls it, and the frame's requests stay on the HTTP cache.

The handler sorts each request by its client: a navigation by its own URL, and any other
request by the URL of the page that sent it. The rich surfaces are the front page, the
feature pages, the Playground and the Academy. Every other page is a plain docs page, and
the first row of the table applies to it. The other rows apply to the rich surfaces.

| Request                                                                      | Strategy                                                     | Why                                                                |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------ |
| any request whose client is a plain docs page, its HTML and its assets       | the network, with no Cache Storage                           | the owner's 2026-10-12 note: restraint suits plain docs pages (Q9) |
| `_next/static/` and every other content-hashed asset                         | cache first                                                  | a hashed URL never changes content                                 |
| the core runtime chunk, the front page's run chunk, the fixtures             | precached on idle after the first visit                      | the second visit's first click runs with no request                |
| the Playground's TypeScript worker and declarations, after docs-site phase 2 | precached on idle after the reader opens the Playground once | 1.05 MB that the HTTP cache keeps for ten minutes only             |
| Pagefind's wasm, its entry and its index fragments                           | stale while revalidate                                       | search answers at once on a repeat visit                           |
| fonts and hero art                                                           | cache first                                                  | hashed by `next/font` and by file name                             |
| page HTML                                                                    | network first, the cache as fallback                         | a visited page reads offline; a deploy shows at once               |

The owner decides whether visited plain docs pages read offline, the one question left
open (Q9). If the owner turns it on, only the fetch handler changes: it then serves plain
docs pages by the rows of the rich surfaces.

### 11.2 Updates and the kill switch

Each build writes its build id into `sw.js`, and the worker names its caches with it. On
`activate` it deletes every cache of an older build. A new worker waits until no tab uses
the old one, so a reader never mixes assets of two builds in one tab.

The kill switch: a deploy that replaces `sw.js` with a worker whose `install` handler
unregisters itself and clears its caches removes the worker on every reader's next visit.
`?nosw` on any URL also unregisters it, for a reader who reports a stale page.

### 11.3 Wasm

Pagefind runs its search in wasm, so search is the site's one wasm surface today. No other
surface in this spec has work that wasm would make faster: the front page's check takes
well under a frame in JavaScript. A wasm TypeScript checker for the Playground would
replace the 1.05 MB worker when one exists. That is a docs-site section 11 change and out
of scope here.

## 17. Decisions on the open questions

The architect proposed an answer to each question this spec raised, and the tech lead
ruled on 2026-10-30 under the owner's delegation of PRs #246 and #247. Each entry names the sections that carry it. One item stays with the owner: offline reading of visited
plain docs pages (Q9).

Q1. Size and the comparison in the proof section.

The proof section (4.9) prints NexusDI's gzipped size and its dependency count, 0, as facts
and ranks neither. It compares startup time with InversifyJS alone. Startup is the
harness's cold-start figure: a fresh Node process loads the library and resolves the bridge of the eight-provider app, which builds every singleton of the app. The
figures come from the harness through `<Figure of>`, the run id and the run's date sit
beside the row, and the page types no percentage. The section compares startup checks with
InversifyJS, tsyringe, awilix and needle-di on features alone, and
`benchmarks/results/probes.json` or a dated reading of the other project's documentation
backs each row. This spec's brief asked to compete with the small containers on size,
which the positioning of 2026-10-01 contradicts. The harness measured the eight-provider
app at 0.4.0-rc.2, gzipped with esbuild, at 21.9 kB for NexusDI and 21.0 kB for
InversifyJS, so the page makes no size claim.

Q2. The headline and the definition.

The hero (4.2) uses the draft: the headline "If it type-checks and starts, the wiring is
right." and the definition "NexusDI is a dependency injection container for TypeScript. It
checks every module, provider and dependency before it builds anything."

Q3. The closed hatch.

The hatch drill closes Engineering's `COMPUTER` hatch. `SurveyDrone` in Tactical needs it,
so `Nexus.check` fails with `NEXUS_MISSING_PROVIDER` and the line "ShipComputer is provided
in Engineering, which does not export it.", and Launch locks. Free play and the
`/modules/` explorable keep the root-lookup case: closing Tactical's `DRONE` hatch passes
the check, and the bridge's `ship.get(DRONE)` fails with `NEXUS_NOT_VISIBLE`. Its caption
calls it a lookup in the reader's own code that no check sees. The tech lead reversed the
draft's recommendation here. The owner's fault list named `NotVisibleError` for a closed
hatch, and core raises it only for a root `get()`, so the drill shows the importer's
`NEXUS_MISSING_PROVIDER`. Sections 4.6, 5.9, 5.10 and 12.5 carry the drill.

Q4. Concept E's extras.

Q9. The service worker and offline reading of the docs.

The architect and the tech lead split on offline reading, so the spec adopts the default
below and leaves that one item to the owner. Each base path has one worker, and the
Academy joins it. The worker serves same-origin GET requests alone, and the opaque-origin
run frame stays on the HTTP cache. The page registers it with `updateViaCache: 'none'`, and

read offline. If the owner turns that on, only the fetch handler changes. The e2e suite blocks
service workers by default, and one spec runs the worker (12.5).
