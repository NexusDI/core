`@nexusdi/core` 0.3.2 is on npm under the `latest` dist-tag, published with npm provenance. It fixes three faults that 0.3.0 and 0.3.1 share, and it removes an unused dependency. It also declares which of its modules have side effects, so a bundler keeps the `Symbol.metadata` polyfill. 0.3.2 changes no exported name or signature, so an upgrade needs no code change.

<!--truncate-->

## Upgrade

```sh
npm i @nexusdi/core@0.3.2
```

0.3.2 declares `"engines": { "node": ">=20" }`.

## Node ESM imports

In 0.3.0 and 0.3.1, the files in `dist/` imported each other without file extensions, for example `from './constants'`. Node's ESM resolver requires the extension, so `import { Nexus } from '@nexusdi/core'` failed with `ERR_MODULE_NOT_FOUND` in any program Node ran without a bundler. Bundlers resolve extensionless paths, so bundled applications did not fail. 0.3.2 writes every relative import with its `.js` extension, and an import of a directory names its `index.js`.

## The `development` export condition

The 0.3.0 and 0.3.1 export maps had a `development` condition that pointed at `./src/index.ts`. Both packages contained only `dist/`, so that file did not exist in `node_modules`. Tools that enable the `development` condition, such as the Vite dev server and Vitest, resolved `@nexusdi/core` to the missing file and failed. 0.3.2 removes the condition. The `import` and `default` conditions resolve to `dist/index.js`, and `types` resolves to `dist/index.d.ts`.

## The `Symbol.metadata` polyfill under tree-shaking

`dist/index.js` installs a `Symbol.metadata` polyfill when the runtime has none. The polyfill is a module-level statement with no export, and a bundler removes such a statement when the package declares its modules free of side effects. 0.3.2 adds a `sideEffects` field to `package.json` that lists `dist/index.js`. A bundler keeps the polyfill, and it can drop the other modules that an application never imports.

## `Token` after a bundler renames the class

0.3.0 and 0.3.1 recognised a `Token` by checking that the name of its constructor was `Token`. esbuild renames a top-level class when two modules in one bundle declare the same name, so the bundle can contain the class as `_Token`. The container then rejected a valid token with `InvalidToken`. Applications failed this way whenever their bundler renamed the class.

0.3.2 checks `instanceof Token` first. The `Token` constructor also marks every instance under the registered symbol `Symbol.for('nexusdi.token')`, and the check accepts an object that carries the mark. A token created by a second copy of `@nexusdi/core` in the same bundle passes the check the same way.

## tslib

0.3.0 and 0.3.1 listed `tslib` in `dependencies`, and no file in `dist/` imported it. 0.3.2 removes it, and `@nexusdi/core` has no runtime dependencies.

## Decorators in 0.3

[The post that announced 0.3](./2025-06-26-native-decorators-simpler-modules.md) and several pages on this site described the 0.3 decorators incorrectly. NexusDI 0.3 uses TypeScript's legacy decorators, and it requires `experimentalDecorators` in `tsconfig.json`:

```json
{
  "compilerOptions": {
    "experimentalDecorators": true
  }
}
```

0.3 does not support standard (TC39) decorators. The 0.3 decorators store their metadata under the `Symbol.metadata` key, and the package polyfills `Symbol.metadata` when the runtime lacks it. NexusDI 0.3 reads no metadata that `emitDecoratorMetadata` emits, so a project does not need that option. The 0.3.2 README and the pages on this site now state the requirement.

## NexusDI 0.4

NexusDI 0.4 is in development against an approved design. It replaces the 0.3 engine, and its API is incompatible with 0.3. The design lists these changes, and a release candidate can still change them:

- Async startup with a synchronous `get()`. `await Nexus.create(RootModule)` compiles the module graph, builds every singleton, awaits async factories and runs `onInit()`. Async work happens only in `Nexus.create`, `load` and `createScope`, and `get()` stays synchronous everywhere.
- A core without decorators. `provide()` and `defineModule()` are the primary API, and each provider lists its dependencies in a typed `deps` tuple that TypeScript checks against the constructor. `@Injectable`, `@Inject` and `@Module` remain as optional sugar, written as standard TC39 decorators (the 2023-11 version of the proposal). 0.4 needs neither `experimentalDecorators` nor `emitDecoratorMetadata`, and it drops legacy parameter decorators.
- Validation before construction. `Nexus.create` checks the whole graph before any constructor runs, and it reports every error at once in one `BlueprintError`: missing providers, module import cycles, dependency cycles with their full path, and singletons that depend on scoped providers.
- Encapsulation, scopes, disposal and introspection. An importing module resolves only the providers that a module lists in `exports`. `createScope()` opens a scope that carries per-request values under the `REQUEST` token. The container disposes instances in reverse creation order through `Symbol.asyncDispose`, which `await using` calls. `graph()` returns the compiled graph as JSON, and a `trace` callback receives typed lifecycle events.
- Migration. The `@nexusdi/codemod` package rewrites a 0.3 project with `npx @nexusdi/codemod 0.4`, and a migration guide maps every 0.3 API to its 0.4 form.

0.4 will be published first as release candidates under the npm `next` dist-tag. The `latest` dist-tag stays on 0.3.x until 0.4.0 final.
