NexusDI 0.4.0-rc.1 is now available on npm under the `next` dist-tag across all nine `@nexusdi/*` packages. To maintain stability, `latest` for `@nexusdi/core` remains on 0.3.2 until the final 0.4.0 release.

This release candidate introduces no breaking changes since rc.0. It focuses on optimizing startup performance for large module graphs, shipping source maps to improve the developer experience, and providing comprehensive documentation and migration guides.

<!--truncate-->

## Try it

**Install the RC version** using the `next` tag:

```sh
npm i @nexusdi/core@next
```

**Synchronize your packages.** Every `@nexusdi/*` package must match the version of `@nexusdi/core`. If you are upgrading from rc.0, update all packages in a single command:

```sh
npm i @nexusdi/core@next @nexusdi/devtools@next
npm i -D @nexusdi/testing@next @nexusdi/cli@next
```

Without the `@next` tag, npm will install core 0.3 and trigger a peer conflict.

## Faster startup for apps with many modules

**Optimized token resolution** now allows core to determine token visibility in a single pass over the module graph. By building each module's export map once and looking up only provided or exported tokens, core avoids walking the graph for every individual token.

On a benchmark app with 32 modules and 301 providers:

- Warm `Nexus.create` dropped from 7.9 ms to 1.27 ms
- Cold `Nexus.create` dropped from 32 ms to 9.8 ms

A benchmark guard now ensures `create` for this app stays within twice the time of the same providers contained in a single module.

**Efficient metadata processing** now reads each class's metadata once per provider and builds provider records in one step. Valid providers no longer allocate closures for error reporting, though the set and order of errors remain unchanged.

**Consistent error ordering** for visibility errors now follows a defined sequence: ambiguous providers (by module walk order), then by the token's first record, followed by invalid exports (by module and export list order).

## Source maps in every package

**Improved debugging** is now available as every package ships declaration maps and source maps alongside the TypeScript source.

- **Direct navigation** in your editor now opens the shipped TypeScript source for NexusDI functions instead of compiled JavaScript or `.d.ts` files.
- **Accurate stack traces** when using `node --enable-source-maps` now map frames directly to `.ts` files.

These changes do not affect your app bundles. Additionally, the published `package.json` files no longer include the workspace-only `@nexusdi/source` export condition accidentally published in rc.0.

## The 0.4 documentation is live

**The new documentation** is available at [nexus.js.org/next/](https://nexus.js.org/next/). Every page follows a problem-solution approach, introducing the goal before the API.

- [Upgrading from 0.3](https://nexus.js.org/next/upgrade/) provides a sequential list of changes with 0.3 and 0.4 code comparisons, including nine behavioral changes that do not trigger compiler errors.
- [Lazy edges and cycles](https://nexus.js.org/next/lazy/) explains how NexusDI detects cycles of any length (e.g., A → B → C → A), how `lazy()` breaks them, and why `lazy()` is opt-in.
- [Lifecycle and disposal](https://nexus.js.org/next/lifecycle/) details why NexusDI shuts down services in reverse order and compares this approach to other containers.

## Smaller fixes

- **Visual consistency** in `@nexusdi/devtools` now ensures cluster labels in DOT graphs use the same font as nodes.
- **Contextual linking** in README images and example links now points to the specific release tag of your installed version.

## What is not ready yet

**The `nexusdi upgrade` command** is not yet available. A future RC will include this tool to automate package updates and rewrite 0.3 code to the 0.4 API, including support for monorepo roots. Until then, please use the [migration guide](https://nexus.js.org/next/upgrade/) manually.

## What 0.4.0 final needs

The final 0.4.0 release will be published once the following criteria are met:

- Four weeks have passed since the last RC containing a breaking change.
- No open issues are labeled `rc-blocker`.
- The `nexusdi upgrade` command from `@nexusdi/cli` has been verified against at least one external codebase.
