# Configurable Modules

In a real-world application, you often need the same module to behave differently depending on the environment or the specific instance. For example, a `CommsModule` might connect to a local relay in development but a satellite link in production.

**Configurable Modules** allow you to define a module that requires a set of options to be provided during its import. This allows you to maintain a single module definition while varying its behavior through configuration.

## Defining Options with `defineModule`

To make a module configurable, you specify an `options` token in the `defineModule` call. This token acts as the "configuration slot" for the module. The module's providers list that token in their deps like any other token.

```ts file=examples/meridian/src/pages/configurable-modules.md region=for-root

```

The `forRoot(value)` method allows an importer to supply the required options. `forRoot()` returns a module, so it goes in `imports` where the plain module would go. `SubspaceRelay` declares `static deps = [COMMS_OPTIONS] as const`, and NexusDI hands it the value `forRoot()` received.

The type of that value comes from the token, so `Comms.forRoot({ frequency: '1420', transport: 'relay' })` fails to compile: `tsc` reports `Type 'string' is not assignable to type 'number'` on the `frequency` line.

If a module declares an options token but is imported without a `forRoot` call, `Nexus.create` rejects with `NEXUS_BLUEPRINT_INVALID`, and its `errors` list holds `NEXUS_MODULE_OPTIONS_MISSING`. The error carries `module=Comms`. See [NEXUS_MODULE_OPTIONS_MISSING](/errors/NEXUS_MODULE_OPTIONS_MISSING/). This region catches the error and prints the inner codes:

```ts file=examples/meridian/src/pages/configurable-modules.md region=missing-for-root

```

**Try it:** Save the first region as `comms.ts` and run `npx tsx comms.ts`. It prints `relay on 1420`. Change the import to `Comms` with no `forRoot()` call and run it again. `tsc` accepts the change, and `Nexus.create` rejects with the error above. Put the `forRoot()` call back and it prints `relay on 1420` again.

## Dynamic Implementations

Options aren't just for simple values; they can be used to determine which class should fulfill a token.

By using a factory for a provider and reading the options token, you can switch implementations based on the configuration. `Comms` binds `SUBSPACE_LINK` in one factory over `COMMS_OPTIONS`, and the factory builds a `LaserLink` or a `SubspaceRelay` from the `transport` option.

## Asynchronous Configuration with `forRootAsync`

Sometimes your configuration isn't known at compile time (it might need to be fetched from a database or an environment variable). `forRootAsync` allows you to compute your options during the container's startup phase. The call takes `{ useFactory, deps }`.


The options factory can be `async`. NexusDI awaits it during `Nexus.create`, before it builds the module's providers. The factory's own `deps` are built first, as `COMPUTER` is in the region above.

The factory's `deps` resolve inside the module: from its own providers, from the tokens its imports export and from the global modules. `Engineering` is a global module here, so the `COMPUTER` token is visible inside `Comms`.

**Try it:** Save the region as `async-comms.ts` and run it. It prints `relay on 1701`. Remove `global: true` from `Engineering` and run it again. `Nexus.create` rejects with `NEXUS_BLUEPRINT_INVALID`, and its one inner error is [NEXUS_MISSING_PROVIDER](/errors/NEXUS_MISSING_PROVIDER/) with `token=ShipComputer requester=CommsOptions module=Comms`: the options factory resolves its deps inside `Comms`, which no longer sees `COMPUTER`. Put `global: true` back and it prints `relay on 1701` again.

## Validating Options with Schemas

To prevent your app from starting with invalid configuration, you can attach a `schema` to your module. NexusDI supports any Standard Schema validator (such as Valibot). The examples use valibot 1.5.0, whose schemas implement Standard Schema, so NexusDI validates them with no valibot-specific code.

```ts file=examples/meridian/src/pages/configurable-modules.md region=schema

```

If the options provided to `forRoot` fail the schema check, `Nexus.create` rejects with `NEXUS_PROVIDER_FAILED`, whose `cause` is `NEXUS_INVALID_MODULE_OPTIONS`. The module's providers are never built with the bad value. The cause carries the schema's issues. `Nexus.check` runs the same schema without building anything, as the next section shows. See [NEXUS_PROVIDER_FAILED](/errors/NEXUS_PROVIDER_FAILED/) and [NEXUS_INVALID_MODULE_OPTIONS](/errors/NEXUS_INVALID_MODULE_OPTIONS/).

**Schema defaults** allow you to simplify the configuration required by the importer. `CommsSchema` gives `transport` the default `'relay'`, so `Comms.forRoot({ frequency: 1420 })` leaves the field out. `forRoot()` and the `forRootAsync()` factory take the schema's input type, while `COMMS_OPTIONS` resolves to the schema's output, the value with all defaults filled in. `SubspaceRelay` reads `transport` from that output, and the last line of the region prints `relay on 1420`. A module without a schema types `forRoot()` with its options token, and so does a module whose schema declares its input as `unknown` or `any`.

**Try it:** Install valibot with `npm install valibot@1.5.0`, save the region as `schema.ts` and run it. It prints the codes, `Invalid value: Expected >=1 but received -5` and `relay on 1420`. Change `-5` to `1420` and run it again. `Nexus.create` resolves, so the first two lines print `null` and the third prints `[]`. Add `transport: 'beam'` to the second `forRoot()` call, and `tsc` reports that `"beam"` is not assignable to the schema's input type on that line.

## Checking Options before Startup

`Nexus.check(root)` compiles the module graph as `Nexus.create` does and builds no provider. When every compile passed, it calls the options schema of each `forRoot()` value, so a test in CI can catch a bad value before the app starts. It throws `NEXUS_BLUEPRINT_INVALID` whose `errors` hold `NEXUS_INVALID_MODULE_OPTIONS` for each value that a synchronous schema rejects. The inner error is the one `Nexus.create` gives as the `cause` of `NEXUS_PROVIDER_FAILED`, with the same text.

```ts file=examples/meridian/src/pages/configurable-modules.md region=check-schema

```

Two cases can fail only at `Nexus.create`: a schema whose `validate` returns a promise, since `Nexus.check` is synchronous, and a module with a schema imported with `forRootAsync()`, whose options exist only once its factory ran. `Nexus.check` returns both in `unchecked`, each with its `module` and a `reason` of `'async-schema'` or `'for-root-async'`. After the graph compiles, `Nexus.check` calls every options schema, an async one included, and awaits none, so keep each schema free of side effects. A schema that throws makes `Nexus.check` throw the same exception.

**Try it:** Install valibot with `npm install valibot@1.5.0`, save the region as `check.ts` and run it. It prints `[ 'NEXUS_INVALID_MODULE_OPTIONS' ]` and `[ 'Comms: for-root-async' ]`. Change `-5` to `1420` and run it again. The first `Nexus.check` call throws nothing, so `codes` stays empty and the first line prints `[]`.

## Sharing Configured Modules

Every call to `forRoot()` or `forRootAsync()` creates a new instance of the module. Each instance has its own providers. If you want multiple parts of your app to share the same configured module (and thus share its singletons), you should call `forRoot` once and export the resulting module constant. Import that constant everywhere the configured module is needed.
