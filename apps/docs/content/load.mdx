# Adding Modules After Startup

In many applications, you don't want to load every single provider at boot time. For example, a specific set of tools might only be needed when a user visits a certain route.

**Dynamic Loading** allows you to add new modules to a running NexusDI container on demand. `load()` is named for sections of an application that load lazily, such as a route whose code is split into its own bundle:

```ts no-run
await ship.load((await import('./survey.js')).SurveyModule);
```

## Using `ship.load()`

The `load()` method allows you to inject a new module into the existing container. This is particularly useful for code-splitting in frontend or Node.js applications. `ship.load(Survey)` compiles `Survey` as a new import of the root module.

```ts file=examples/meridian/src/pages/load.md region=load-module

```

When you call `load()`, NexusDI performs three critical steps:

1. **Validation:** It validates the new module against the current live graph to ensure no wiring mistakes are introduced.
2. **Initialization:** It builds the new module's singletons and runs their `onInit` methods. It awaits their async factories first.
3. **Publication:** It updates the container's internal registry so the new providers are now available via `get()`.

Before the call the container does not see `DRONE`. After it, `NAV_CHARTS` has finished its async download and `ScoutDrone.onInit()` has run, so `get(DRONE)` is synchronous like every other `get()`.

**Try it:** Save the region as `load.ts` and run `npx tsx load.ts`. Its last line is `course to Kepler-442b`. Move the `const course = ship.get(DRONE).survey();` line above `await ship.load(Survey);` and run it again: `get()` throws [NEXUS_MISSING_PROVIDER](/errors/NEXUS_MISSING_PROVIDER/), because the container does not see `DRONE` before the load. Move the line back and the last line is `course to Kepler-442b` again.

## Validation and Safety

Dynamic loading does not bypass NexusDI's safety guarantees. `load()` runs the same compiler `Nexus.create` runs, against the graph the container already holds. A loaded module sees its own providers, the exports of the modules it imports, the exports of global modules, and the exports of the host modules the load grants it. A provider in the root module is not visible to it unless one of those exports it. If the module depends on a token it cannot see, `load()` rejects with a `NEXUS_BLUEPRINT_INVALID` error. The container stays as it was. See [NEXUS_BLUEPRINT_INVALID](/errors/NEXUS_BLUEPRINT_INVALID/).

This ensures that your application never enters a partially-broken state where some dependencies are missing. Here `ScoutDrone` needs `NAV_CHARTS`, which nothing provides, so the `errors` list holds one `NEXUS_MISSING_PROVIDER`, and `ship.has(DRONE)` is still `false`:

**Try it:** Add `provide(NAV_CHARTS, { useFactory: () => ({ plot: (to: string) => to }) })` to the providers of `Survey` and run the region again. The load resolves, the `errors` list is empty, and the region prints `[]` and `true`. Delete the line and the region prints `['NEXUS_MISSING_PROVIDER']` and `false` again.

## Updating Scopes with `scope.extend()`

Scopes are snapshots of the graph at the moment they were created. If you load a new module into the root container, existing scopes won't see those new providers by default. A token that a later `load()` added throws [NEXUS_LOADED_AFTER_SCOPE](/errors/NEXUS_LOADED_AFTER_SCOPE/) in that scope.

## Giving a Loaded Plugin Access to Host Services

When a host loads code it does not own (such as a runtime plugin package or a federation remote), that code often requires access to host services. For example, a plugin might need the ship's star charts to function. Because the plugin is loaded dynamically, it cannot import the host's modules by name. Previously, hosts solved this by making services global, but that exposed those services to every module in the graph, regardless of whether they needed them.

A **grant** provides a targeted alternative. By using `load(module, { imports })`, the host explicitly names which modules the loaded code can "see" as if they had been imported. This restricts visibility to only the requested modules for that specific load. In contrast, a lazy feature within the host's own codebase continues to import host modules by name and requires no grant.

The following example shows a plugin `Survey` that depends on `NAV_CHARTS`, which is exported by the host module `Tactical`. Because `Survey` cannot import `Tactical` directly, the first load attempt fails with `NEXUS_BLUEPRINT_INVALID`. The second load succeeds because it grants access to `Tactical`:

### A Grant Reaches the Whole Loaded Subtree

A grant extends to the entire dependency tree introduced by the load. This includes the primary loaded module and any modules in its subtree that were not already present in the graph. Each of these modules can access the exports (including re-exports) of the granted modules. A grant only exposes a module's public exports. It gives none of that module's private providers.

In the example below, `Survey` imports `Sensors`, and `Sensors` provides the probe that requires `NAV_CHARTS`. A single grant on the initial load satisfies the requirements for both modules:

The blueprint records this grant for every module added during the load. Subsequent loads do not alter existing recorded grants, and modules already present in the graph do not receive new access from later grants.

### What a Grant Accepts and Refuses

NexusDI validates grants against the current container graph. An invalid grant rejects with [NEXUS_LOAD_GRANT](/errors/NEXUS_LOAD_GRANT/), returning an error object with the `module` being loaded, the `grant` being attempted, and a `reason` field.

- **`not-in-graph`**: A grant only adds visibility; it does not load the module itself. Every granted module must already exist in the graph. The host passes the object it imported. Passing the result of a fresh `forRoot()` call fails with this reason because it creates a new definition not yet in the graph.
- **`root`**: The root module cannot be granted. If a loaded module needs root providers, the host must export those providers from a different module and grant that module instead.
- **`already-loaded`**: A repeat `load()` of a module already in the graph is ignored if the grant set is identical (ignoring order) or empty. If the repeat load attempts to provide a different set of grants, it fails with this reason. Similarly, loading a module that the root already imports statically fails if any grant is provided, as the root records no grant for that module.

Granting a global module is legal but redundant, as every module in the graph already sees the exports of a global module.

### Grants in Adapters and in the Graph

The grant configuration is passed as the second argument to `di.load(module, options)` within adapters. This is supported by the Express, Fastify, Hono, and React Router adapters, as well as the `lazySection(name, loader, options)` function in `@nexusdi/react`.

These adapters call `loadOnce(container)` from `@nexusdi/core`. This ensures `load()` is called only once per module and grant set, sharing the pending promise across concurrent requests. If a load fails, it is removed from the cache so that subsequent requests can attempt the load again.

Each module view maintains a `grants` list containing the IDs that a grant added to the module's imports. You can view these via `graph()`, `inspect()` from `@nexusdi/devtools`, or the `nexusdi graph` CLI tool. In diagram outputs, grants are drawn distinctly from standard imports ([Introspection](/introspection/)). `inspect()` also lists in `unchecked` the modules whose options only `Nexus.create` can validate.

A grant is a wiring mechanism; it does not provide process isolation or a security boundary. Because the loaded module runs in the host's process, it can access anything the host's code can. The grant solely determines which module exports the loaded module's providers can name as dependencies.

## Design Constraints

To maintain the integrity of the graph, NexusDI imposes a few restrictions on dynamic loading:

- **No Global Modules:** You cannot `load()` a module marked as `global: true`. Global modules must be declared in the root module at startup because they affect the visibility of every other module. A global module makes its exports visible to every module, so a global module new to the graph would change what every existing module sees. Import a global module from the root module before `Nexus.create`, or load it without `global: true`. A host that wants a loaded module to see one of its modules [grants that module](#giving-a-loaded-plugin-access-to-host-services) in the load, and the module need not be global.
- **No contributions to Multi Tokens.** A loaded module cannot publish a contribution to a [`MultiToken`](/multi-providers/). Because a collector created by `Nexus.create` holds its own list, a subsequent `load()` cannot extend it. The load guard determines if a contribution is published by checking if the module exports the token or if a `compile.provider` hook pins the token to it; pins created during a load also count as publishing. Contributions kept private by the module remain legal, and the module reads them itself. To add a provider from a loaded module to a collector, register it via a registry offered by the collector during the module's `onInit` and unregister it when the module is disposed.
- **Sealed Container:** Once a provider is registered, it cannot be changed. `load()` adds new providers but does not allow you to replace existing ones.

`load()` rejects a global module with [NEXUS_LOAD_GLOBAL_MODULE](/errors/NEXUS_LOAD_GLOBAL_MODULE/), which it throws directly, outside a `NEXUS_BLUEPRINT_INVALID` error. Its `module` property names the module, `Science` here:

### Why There Is No `set()`

In 0.3, `set()` registered one provider into a mutable container at any time, before or after the first `get()`. `Nexus.create` in 0.4 validates the whole graph before it builds anything, so every provider is declared in a module, and the container is sealed once `create` resolves. `load()` keeps that guarantee: it takes a whole module and validates it against the live graph. A per-token `set()` after `create` would add a provider the compiler never validated. The [upgrade guide](/upgrade/) shows what each 0.3 `set()` call becomes.

## Rules

- On a compile error, the container stays as it was. When a build or an `onInit` fails during the load, NexusDI disposes what the load built.
- `load()` of a module the root already imports, or a second `load()` of the same module, does nothing when the call grants nothing or the grant that module already has. Another grant fails with `already-loaded`.
- Concurrent `load()` calls run one at a time, in call order.
- `get()` of a token from a module that is not loaded yet throws `NEXUS_MISSING_PROVIDER`.
- `load()` cannot publish a contribution to a `MultiToken`: the module exports the token, or a `compile.provider` hook pins it, and a pin first made at a load counts. It fails with `NEXUS_LOAD_CONTRIBUTION`.
- `load(module, { imports })` grants the exports of host modules already in the graph to every module the load adds. A grant gives no private providers, is recorded per module and stays fixed on later loads. It fails with `NEXUS_LOAD_GRANT` for a module outside the graph (`not-in-graph`), the root (`root`) or another set on a repeat (`already-loaded`).
- `Nexus.check(root, { load: [{ module, imports }] })` checks a grant synchronously and reports its error inside `NEXUS_BLUEPRINT_INVALID`.
- A grant is wiring, with no isolation and no security boundary.
