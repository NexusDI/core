# Adding Modules After Startup

In many applications, you don't want to load every single provider at boot time. For example, a specific set of tools might only be needed when a user visits a certain route.

**Dynamic Loading** allows you to add new modules to a running NexusDI container on demand.

## Using `ship.load()`

The `load()` method allows you to inject a new module into the existing container. This is particularly useful for code-splitting in frontend or Node.js applications.

```ts file=examples/meridian/src/pages/load.md region=load-module
```

When you call `load()`, NexusDI performs three critical steps:
1. **Validation:** It validates the new module against the current live graph to ensure no wiring mistakes are introduced.
2. **Initialization:** It builds the new module's singletons and runs their `onInit` methods.
3. **Publication:** It updates the container's internal registry so the new providers are now available via `get()`.

## Validation and Safety

Dynamic loading does not bypass NexusDI's safety guarantees. If a module you try to load depends on a token that isn't provided by the root or any other loaded module, `load()` will reject with a `NEXUS_BLUEPRINT_INVALID` error.

This ensures that your application never enters a partially-broken state where some dependencies are missing.

## Updating Scopes with `scope.extend()`

Scopes are snapshots of the graph at the moment they were created. If you load a new module into the root container, existing scopes won't see those new providers by default.

To bring a scope up to date with the latest graph, use `scope.extend()`.

```ts file=examples/meridian/src/pages/load.md region=extend-scope
```

This allows a long-lived scope (like a user session) to gain access to features that were loaded dynamically after the session started.

## Design Constraints

To maintain the integrity of the graph, NexusDI imposes a few restrictions on dynamic loading:

- **No Global Modules:** You cannot `load()` a module marked as `global: true`. Global modules must be declared in the root module at startup because they affect the visibility of every other module.
- **Sealed Container:** Once a provider is registered, it cannot be changed. `load()` adds new providers but does not allow you to replace existing ones.
