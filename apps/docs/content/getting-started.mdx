# Getting Started

Most dependency injection containers are "optimistic". They assume your wiring is correct and only tell you something is missing when your app crashes at runtime.

NexusDI takes a different approach. It validates your entire dependency graph during startup. If a dependency is missing or a circular reference exists, NexusDI catches it immediately, ensuring that once your app starts, it stays running.

This tutorial will guide you through installing NexusDI, building a simple application, and intentionally breaking it to see how the validation system helps you fix errors.

## Installation

NexusDI 0.4 is currently a release candidate. To get started, create a new project and install the core package using the `next` tag.

```bash
mkdir meridian && cd meridian
npm init -y
npm pkg set type=module
npm install @nexusdi/core@next
npm install -D typescript tsx @types/node
```

`@nexusdi/core` is published as ES modules. If you are using Node 22.12 or later, you can use `require()` in a CommonJS project, but ESM is recommended.

## TypeScript Configuration

NexusDI requires TypeScript 5.4 or later. Leave `experimentalDecorators` and `emitDecoratorMetadata` **off**: the core API uses no decorators, and the optional `@nexusdi/decorators` package uses standard decorators. (A project that needs the flag for another library can keep it, as [Using NexusDI with experimentalDecorators](/legacy-decorators/) shows.) The package's type declarations reference TypeScript's `esnext.disposable` library, which adds `Symbol.asyncDispose` and `AsyncDisposable` to your program, so `await using` compiles with `lib: ["es2022"]` and you add no entry for it.

Create a `tsconfig.json` with the following configuration:

```json no-run
{
  "compilerOptions": {
    "target": "es2022",
    "module": "nodenext",
    "strict": true,
    "noEmit": true,
    "lib": ["es2022"],
    "types": ["node"]
  }
}
```

You can now type-check your project with `npx tsc` and run files directly using `npx tsx <file>.ts`.

## Your First Application

The simplest way to start a container is using `Nexus.create`. This function takes a list of classes, analyzes how they depend on each other, and instantiates them in the correct order.

## Experience Static Validation

To see the power of NexusDI, let's intentionally break the wiring.

If a class depends on a token that the container wasn't given, `Nexus.create` will reject the startup process with a `NEXUS_BLUEPRINT_INVALID` error. This prevents your app from starting in a broken state.

**Try it:** Delete `FusionReactor` from the array passed to `Nexus.create` in `ship.ts` and run it again.

The run stops with an uncaught `NEXUS_BLUEPRINT_INVALID` error that lists `NEXUS_MISSING_PROVIDER`. `Nexus.create` checks the whole graph before it builds anything, and its `errors` array holds one error for each problem. This program breaks the ship the same way and reads the `errors` array of the rejection:


The one error inside is [NEXUS_MISSING_PROVIDER](/errors/NEXUS_MISSING_PROVIDER/). Core writes a short message: the code with the error's fields as `key=value` pairs, then a link to the code's page. The `module=root` field names the module the array became: `Nexus.create` compiles a list of classes as an unnamed root module.

Fix the ship: put `FusionReactor` back in the array and run `ship.ts` again. The status line prints.

## Improving Error Messages with DevTools

While core provides concise error codes, the `@nexusdi/devtools` plugin transforms these into human-readable messages with suggested fixes. It also adds the graph and trace tools that [Introspection and Tracing](/introspection/) teaches.

Install the devtools plugin at the same version as core:

```bash
npm install -D @nexusdi/devtools@next
```
