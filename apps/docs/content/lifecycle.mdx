# Lifecycle and Disposal

Managing the lifecycle of a service—especially those that hold external resources like database pools, file handles, or network sockets—is critical for application stability.

If resources aren't closed in the correct order, you risk leaking connections, hanging test processes, or crashing during a rolling deployment. NexusDI automates this through a strict lifecycle and disposal pipeline.

## The Startup Phase: `onInit`

NexusDI doesn't just instantiate classes; it ensures they are fully initialized before they are used.

Any singleton class can implement an optional `onInit` method. NexusDI calls this method after all singletons are built, but **before** the container is marked as ready. Crucially, these are called in dependency order: if Service A depends on Service B, Service B's `onInit` is guaranteed to finish before Service A's starts.

This ensures that no service ever runs against a dependency that isn't yet ready.

## The Shutdown Phase: `AsyncDisposable`

To prevent resource leaks, NexusDI treats the container as an `AsyncDisposable`. When the container is disposed, it shuts down every instance it owns.

**The Gold Rule of Disposal:** Instances are disposed in the **exact reverse order** of their creation.


By following this order, NexusDI guarantees that a service is stopped _before_ the dependencies it relies on are closed.

## Robust Error Handling during Disposal

A single failing disposer should not stop other resources from being cleaned up. If multiple disposers throw errors, NexusDI collects them all into a `SuppressedError` chain. This ensures that every single socket and pool is attempted to be closed, and you receive a complete list of every failure that occurred.

## Ownership and Disposal

NexusDI only disposes of what it actually created.

- **Factory Results:** If a `useFactory` provider returns a disposable object, NexusDI owns that object and will dispose of it.
- **Static Values:** If you use `useValue` to provide an existing object, NexusDI assumes you own that object and will **not** attempt to dispose of it.

## Transient Disposal in Scopes

Singletons are disposed when the container is disposed. However, **transients** (which are created on every `get()`) have no permanent owner.

To prevent memory leaks, you should resolve disposable transients within a **Scope**. The scope takes ownership of every transient it creates and disposes of them when the scope itself is destroyed.
