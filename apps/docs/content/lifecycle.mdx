# Lifecycle and Disposal

Managing the lifecycle of a service is critical for application stability. This holds most for services with external resources such as database pools, file handles, or network sockets.

If resources aren't closed in the correct order, you risk leaking connections, hanging test processes, or crashing during a rolling deployment. NexusDI automates this through a strict lifecycle and disposal pipeline.

## Why NexusDI Manages Lifecycle and Disposal

A service that holds a database pool or a file handle has to close it on every exit path, and in an order that keeps each service's dependencies open while it shuts down. Four situations show what goes wrong without that.

- **Rolling deploys:** On SIGTERM, Kubernetes gives a pod 30 seconds by default (`terminationGracePeriodSeconds`) and then sends SIGKILL. A pool that nobody closed cuts in-flight queries off, and its connections stay open on the database server until the server times them out. A rolling deploy that repeats this can reach the database's connection limit.
- **Test runs:** An open server or pool keeps the process alive. Jest prints "Jest did not exit one second after the test run has completed", and Vitest reports "close timed out" because something prevents the main process from exiting. A resource that one test leaves open is still there in the next test.
- **Dev servers:** Each reload that builds a new container without disposing the old one leaves a second pool open beside the first.
- **Out-of-order shutdown:** The database pool closes first, and the service that flushes its buffer on shutdown then fails its last writes.

Each rule on this page prevents one of those problems:

- `onInit` runs in dependency order and finishes before the first `get()`, so no service runs against a dependency that is not ready.
- Disposal runs in reverse creation order, so a service stops before the dependencies it uses and never runs after they close.
- Every disposer runs and the failures are chained, so one pool that fails to close does not leave the other sockets open, and the error lists every failure.
- A scope owns the transients it builds, so a per-request resource closes when its request ends.
- The container disposes what a factory returns and leaves a `useValue` alone, so it closes only what it created.

## The Startup Phase: `onInit`

NexusDI doesn't just instantiate classes; it ensures they are fully initialized before they are used.

Any singleton class can implement an optional `onInit` method. NexusDI calls this method after all singletons are built, but **before** the container is marked as ready. Crucially, these are called in dependency order: if Service A depends on Service B, Service B's `onInit` is guaranteed to finish before Service A's starts.

## The Shutdown Phase: `AsyncDisposable`

To prevent resource leaks, NexusDI treats the container as an `AsyncDisposable`. When the container is disposed, it shuts down every instance it owns. `await using ship = await Nexus.create(...)` disposes the container when the block ends, and `ship[Symbol.asyncDispose]()` disposes it by hand.

**The Gold Rule of Disposal:** Instances are disposed in the **exact reverse order** of their creation.

## Robust Error Handling during Disposal

A single failing disposer should not stop other resources from being cleaned up. If multiple disposers throw errors, NexusDI collects them all into a `SuppressedError` chain. This ensures that every single socket and pool is attempted to be closed, and you receive a complete list of every failure that occurred. The chain is built the way `DisposableStack` builds one.

## Ownership and Disposal

NexusDI only disposes of what it actually created.

- **Factory Results:** If a `useFactory` provider returns a disposable object, NexusDI owns that object and will dispose of it.
- **Static Values:** If you use `useValue` to provide an existing object, NexusDI assumes you own that object and will **not** attempt to dispose of it.

## Transient Disposal in Scopes

Singletons are disposed when the container is disposed. However, **transients** (which are created on every `get()`) have no permanent owner.

To prevent memory leaks, you should resolve disposable transients within a **Scope**. The scope takes ownership of every transient it creates and disposes of them when the scope itself is destroyed. A transient resolved from the root container is never disposed, and NexusDI reports it as an `untracked` trace event, which `trace()` from `@nexusdi/devtools` receives.

Move the line back out of the block and the program prints the leak again.

## Rules

These are the guarantees the container keeps, for reference.

- `onInit` runs on singletons only. NexusDI never calls it on a `useValue` object, and a scoped or transient class does its setup in its constructor or in a factory.
- NexusDI awaits an `onInit` that returns a promise, and `Nexus.create` resolves only after every `onInit` has finished.
- An `onInit` that throws rejects `Nexus.create` with `NEXUS_PROVIDER_FAILED`, the thrown error as its `cause`, and the `onInit` methods of later levels do not run.
- NexusDI calls `Symbol.asyncDispose` or `Symbol.dispose` on every instance it built, once per instance.
- A second call to `ship[Symbol.asyncDispose]()` returns the first call's promise, so two signal handlers can both call it.
- In the `SuppressedError` chain, `error` holds the last failure and `suppressed` holds the chain before it. On a runtime without `SuppressedError`, NexusDI uses its own error class with the same name and fields.
- A scope disposes the transients it built in reverse creation order when the scope is disposed.
