# Upgrading to 0.4

NexusDI 0.4 introduces a fundamental shift in how the container works: it moves from a "lazy, optimistic" model to a "static, validated" model. NexusDI now validates the entire module graph before the first instance is ever created, so wiring errors surface at startup.

Because of this shift, the 0.4 API is significantly different from 0.3. `set()`, `DynamicModule`, symbol tokens, parameter decorators and `createChildContainer()` have no 0.4 form. This guide provides a sequential path to migrate your project: work through the steps in order, and run `npx tsc` after each one, because it lists the 0.3 code that remains. Each step shows the 0.3 code, which does not compile against 0.4, and the 0.4 code that replaces it.

The 0.4 release candidates publish no codemod, so every step is an edit you make by hand. The [changelog of `@nexusdi/core`](https://github.com/NexusDI/core/blob/main/libs/core/CHANGELOG.md) lists every change, and the [0.3 support policy](/support-policy/) says how long 0.3 receives fixes.

## 1. Installation and Tooling

First, update your dependencies. 0.4 moves optional features (like decorators and testing) into their own packages to keep the core lean. Install from the `next` tag during the release candidate ([Trying the 0.4 Release Candidate](/release-candidate/)):

```bash
npm install @nexusdi/core@next
npm install -D @nexusdi/testing@next @nexusdi/errors@next @nexusdi/devtools@next
```

Each package holds one feature:

- **`@nexusdi/decorators`:** The decorators of a project that keeps them: `@Injectable` and `@Inject` for providers, `@Module` for modules.
- **`@nexusdi/testing`:** The testing container.
- **`@nexusdi/errors` and `@nexusdi/devtools`:** Word every error in full.
- **`@nexusdi/node`:** `nodeScopes()`, which binds a scope to one Node request.

### TypeScript Update

NexusDI 0.4 requires TypeScript 5.4+ and Node 22.12+, and it is published as ES modules only. A CommonJS project on Node 22.12 or later can `require()` it.

0.4 does not read compiler-emitted metadata, so you can remove `experimentalDecorators` and `emitDecoratorMetadata` from your `tsconfig.json`. A project that needs the flag for another library can keep it: `static deps` and `provide()` work with the flag on. Only `@nexusdi/decorators` needs it off, because it uses standard TC39 decorators. See [Using NexusDI with experimentalDecorators](/legacy-decorators/). For a project with no other use of the flags, the compiler options end up like this:

```json no-run
{
  "compilerOptions": {
    "target": "es2022",
    "module": "nodenext",
    "strict": true
  }
}
```

## 2. Replacing Symbol Tokens

0.3 allowed the use of Symbols or Strings as tokens. 0.4 requires a `Token<T>` for any value that isn't a class. A `Token<T>` carries the type of what it names and a required description, which errors and the graph show. `TokenType<T>` becomes `InjectionToken<T>`, which names a `Token` or a class.

**0.3 (Legacy):**

```ts anti-example
const NAV_CHARTS = Symbol('NavCharts');
container.set(NAV_CHARTS, { useValue: charts });
```

`Token<T>` provides both the runtime identity and the TypeScript type, making your dependencies type-safe.

**Try it:** Save the region as `tokens.ts` and run `npx tsx tokens.ts`. It prints `course to Kepler-442b` and `NavCharts`. Change the token to `const NAV_CHARTS = Symbol('NavCharts');` and `npx tsc` reports TS2769 on the `provide(` call and on the `get` call, because a symbol is not an injection token. `npx tsx tokens.ts` then stops with `NEXUS_BLUEPRINT_INVALID`, which holds `NEXUS_INVALID_TOKEN` with the field `received=the symbol Symbol(NavCharts)`. Change the line back to the `Token`.

## 3. Moving to `static deps`

The `@Service` and `@Inject` parameter decorators are replaced by a `static deps` array on the class. This makes dependencies explicit and verifiable: TypeScript checks the tuple against the constructor. `@Optional(X)` becomes `optional(X)` in the tuple.

**0.3 (Legacy):**

```ts anti-example
@Service()
class QuantumComputer {
  constructor(
    @Inject(REACTOR) private reactor: IReactorCore,
    @Optional(SUBSPACE_LINK) private link?: ISubspaceLink,
  ) {}
}
```

**0.4 (Current):**


If you prefer decorators, you can use `@Injectable({ deps: [...] })` from the `@nexusdi/decorators` package ([Writing Providers with Decorators](/decorators/)).

**Try it:** Save the region as `services.ts` and run `npx tsx services.ts`. It prints `Reactor output 1.21 GW, no link.` Swap the two entries of `static deps` and `npx tsc` reports TS2769 on the `provide(COMPUTER, ...)` call, because the tuple no longer matches the constructor. Swap them back.

### Plain-Field Injection

0.3 also injected a plain field marked `@Inject`. 0.4 has no plain-field injection:

```ts anti-example
@Service()
class QuantumComputer {
  @Inject(REACTOR) reactor!: IReactorCore;
}
```

Move that dependency into `static deps` as a constructor parameter. A project that keeps decorators can write `@Inject(REACTOR) accessor reactor!: IReactorCore;` with `@Inject` from `@nexusdi/decorators`, which accepts `accessor` fields only. The container sets an `accessor` field after the constructor returns and before `onInit`.

## 4. Redefining Modules

`DynamicModule` and `@Module` classes are replaced by the `defineModule()` function. This allows for better type checking and a clearer distinction between the module definition and its configuration.

`defineModule({ name, providers, imports, exports })` declares a module. A configurable module names an options token with `options`, and the importer passes the options with `forRoot(value)` or `forRootAsync({ useFactory, deps })`. `Mod.config(value)` becomes `Mod.forRoot(value)`, and `Mod.configAsync(fn)` becomes `Mod.forRootAsync({ useFactory: fn })`.

**0.3 (Legacy):**

```ts anti-example
@Module({ providers: [SubspaceRelay] })
class Comms extends DynamicModule<CommsOptions> {
  protected readonly configToken = COMMS_OPTIONS;
}
container.set(Comms.config({ frequency: 1420 }));
```

**0.4 (Current):**

```ts file=examples/meridian/src/pages/upgrade.md region=modules

```

**Try it:** Save the region as `modules.ts` and run `npx tsx modules.ts`. It prints `1420`. Replace `Comms.forRoot({ frequency: 1420 })` with `Comms.forRootAsync({ useFactory: () => ({ frequency: 1421 }) })` and it prints `1421`. Replace it with the bare `Comms` and `Nexus.create` rejects with `NEXUS_BLUEPRINT_INVALID`, which holds `NEXUS_MODULE_OPTIONS_MISSING` for `module=Comms`, because the module declares an options token and no importer supplied the options. Put the `forRoot` call back.

### The Changed Meaning of `forRoot`

The 0.3 static `DynamicModule.forRoot(config)` took a module config and returned a runtime module class. A 0.4 `forRoot(options)` takes the options of one configurable module, which is a different meaning under the same name, so check each 0.3 `forRoot` call site. `DynamicModule.forRoot({ providers })` becomes `defineModule({ name, providers })`.

### Module Encapsulation and `exports`

0.4 enforces module encapsulation, and this is the change most likely to stop a provider from resolving after the upgrade. A module sees its own providers, the exports of the modules it imports and the exports of every global module. 0.3 read no `exports`, so a 0.3 graph that worked through one flat map fails until each module exports what its importers use:


**Try it:** Save the region as `exports.ts` and run `npx tsx exports.ts`. It prints `[ 'NEXUS_MISSING_PROVIDER' ]`: `Tactical` imports `Engineering`, and `Engineering` keeps `REACTOR` private. Add `exports: [REACTOR],` to the `Engineering` module and run it again. `Nexus.create` resolves, so `error` holds the ship and no error, and the program prints `[]`. Take the line out again to see the code return.

## 5. Bootstrapping the Container

The `new Nexus()` and `set()` pattern is replaced by a single, atomic `Nexus.create()` call. This is where the static graph validation happens. Its root is a module, or an array of providers (a plain `{ providers, imports, exports }` object also works). The container is sealed once `create` resolves. A provider registered after startup becomes a module that `ship.load()` adds ([Adding Modules After Startup](/load/)).

**0.3 (Legacy):**

```ts anti-example
const container = new Nexus();
container.set(REACTOR, { useClass: FusionReactor });
container.set(QuantumComputer);
const computer = container.get(QuantumComputer);
```

**0.4 (Current):**


**Try it:** Save the region as `bootstrap.ts` and run `npx tsx bootstrap.ts`. It prints `Reactor output 1.21 GW.` Delete the `provide(REACTOR, ...)` line and run it again. The run stops with an uncaught `NEXUS_BLUEPRINT_INVALID` that lists `NEXUS_MISSING_PROVIDER` with `token=ReactorCore requester=ShipComputer module=root`: the check runs before any class is built. Put the line back.

## 6. Lifetimes and Scopes

- **Scopes:** `createChildContainer()` is replaced by `await ship.createScope({ request })`. A provider with `lifetime: 'scoped'` is built once per scope.
- **Transients:** `singleton: false` is now `lifetime: 'transient'`. 0.3 ignored that flag and cached every instance.
- **Eager Loading:** 0.3 built everything lazily. 0.4 builds all singletons at startup. Use `eager: false` to restore lazy initialization for expensive providers.

`REQUEST` resolves to the request the scope was created with. The project declares that request's shape once, by augmenting `NexusRequest` in a `.d.ts` file ([Scopes and the REQUEST Token](/scopes/)):

```ts no-run
// request.d.ts
import '@nexusdi/core';

declare module '@nexusdi/core' {
  interface NexusRequest {
    mission: { id: string; target: string };
  }
}
```

**0.3 (Legacy):**

```ts anti-example
const child = container.createChildContainer();
child.set(MISSION, { useValue: { id: 'survey-7', target: 'Kepler-442b' } });
```

**0.4 (Current):**


**Try it:** Save `request.d.ts` and the region as `scopes.ts` in one folder, and run `npx tsx scopes.ts`. It prints `Kepler-442b`. Without `request.d.ts`, `npx tsc` reports TS2339 on `request.mission`, because `NexusRequest` has no `mission`. ## 8. Error Codes

Every 0.4 error extends `NexusError` and carries a stable `code`. Core's own message is one line: the code with the error's fields, and a link to the code's page. Register `errors()` from `@nexusdi/errors`, or `devtools()`, for the full message with its fix. Code that matched 0.3 message text compares `error.code` in 0.4.

The 0.3 error classes map to 0.4 classes:

- `ContainerException` becomes `NexusError`.
- `NoProvider` becomes `MissingProviderError` or `NotVisibleError`.
- `InvalidToken` becomes `InvalidTokenError`, and `InvalidProvider` becomes `InvalidProviderError`.
- `InvalidModule` becomes `InvalidModuleError`.

**0.3 (Legacy):**

```ts anti-example
try {
  container.get(NAV_CHARTS);
} catch (error) {
  if (error instanceof NoProvider) recover();
}
```

**0.4 (Current):**


It prints `true`, `NEXUS_MISSING_PROVIDER` and the full first line, `[NEXUS_MISSING_PROVIDER] ShipComputer (module root) depends on NavCharts, but no provider of NavCharts is visible in root.` Delete the `plugins: [errors()],` option and run it again. The last line becomes core's one-line message, `[NEXUS_MISSING_PROVIDER] token=NavCharts requester=ShipComputer module=root.` followed by the link to the code's page. ## Summary of API Changes

These 0.3 exports and members map to 0.4 as follows. The last six rows have no step above.

| 0.3 Concept                                                                           | 0.4 Replacement                                                                                                                                                                                                           |
| :------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `container.set()`                                                                     | `Nexus.create()` / `provide()`                                                                                                                                                                                            |
| `DynamicModule`                                                                       | `defineModule()`                                                                                                                                                                                                          |
| `createChildContainer()`                                                              | `createScope()`                                                                                                                                                                                                           |
| `@Service`, `@Provider`                                                               | `static deps` with `provide()`, or `@Injectable` from `@nexusdi/decorators`                                                                                                                                               |
| Symbol tokens                                                                         | `Token<T>`                                                                                                                                                                                                                |
| `container.resolve(Class)`                                                            | `provide(Class, { lifetime: 'transient' })` and `ship.get(Class)`. `ship.resolve(deps)` takes a deps tuple or map, and `resolve(Class)` throws `NEXUS_INVALID_TOKEN`.                                                     |
| `container.list()`, `container.clear()`                                               | `list()` is gone: register `devtools()` in `Nexus.create`'s `plugins`, and `graph(ship)` from `@nexusdi/devtools` reports the graph. `clear()` is gone: dispose the ship with `await using` or `[Symbol.asyncDispose]()`. |
| `isToken`, `isService`, `isModuleClass` and the other guards                          | No 0.4 form. Core exports `isNexusError` and `isForeign`.                                                                                                                                                                 |
| `getMetadata`, `setMetadata`, `METADATA_KEYS`, `SYMBOL_METADATA`                      | No 0.4 form: core keeps no public metadata store.                                                                                                                                                                         |
| `import Nexus from '@nexusdi/core'`                                                   | The named export `import { Nexus } from '@nexusdi/core'`. 0.4 has no default export.                                                                                                                                      |
| `Token.create(id)`, `Token.createUnique()`, `token.equals(other)`, `token.toSymbol()` | `new Token<T>(description)` makes each token, `===` compares two, and `toSymbol()` is gone.                                                                                                                               |
| `IContainer`, `ModuleProvider`                                                        | The `Nexus` type, and `ProviderEntry`.                                                                                                                                                                                    |

## Behaviour That Changes Without a Compile Error

Some changes compile in a 0.3 project and behave differently under 0.4. `npx tsc` does not list these, so check each one by hand:

1. A constructor parameter with no `@Inject` was `undefined` in 0.3, because 0.3 read emitted parameter types that nothing wrote. In 0.4 `static deps` lists every parameter, and each one is injected.
2. Every singleton is built at `create`. `eager: false` restores first-use timing.
3. 0.3 never called `onInit`. 0.4 calls it inside `create`, after every singleton is built.
4. `has()` answers for visibility: it returns `false` for a token another module keeps private, and for a module class.
5. Two `forRoot()` calls build two module instances. Call `forRoot()` once and import the result everywhere.
6. One token provided in two modules builds two singletons, one for each module.
7. 0.3 disposed nothing. 0.4 disposes every instance it owns, a factory's result included, when the container is disposed.
8. Every error message starts with its code in brackets, such as `[NEXUS_MISSING_PROVIDER]`.
9. `@Optional` still threw `NoProvider` in 0.3 when no provider existed. `optional()` in 0.4 resolves to `undefined`.

