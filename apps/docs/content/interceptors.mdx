# Method Interceptors

In any complex application, you'll find logic that needs to run across many different services, such as logging every call, measuring performance, or validating inputs. If you write this logic inside every method, your codebase becomes cluttered with boilerplate.

**Interceptors** solve this by allowing you to "wrap" your service methods with cross-cutting logic. An interceptor can observe a call, change the arguments, cache the result, or even skip the method entirely.

## How Interceptors Work

An interceptor is a provider that implements the `Interceptor` interface and declares its deps like any class provider. Its core logic lives in the `intercept(call, next)` method:

- **`call`**: A `CallContext` holding the service instance, the provider, the method name, the arguments, the `async` flag and the current scope.
- **`next`**: A function that triggers the next interceptor in the chain, eventually calling the actual service method.

To use them, you first install the interceptors package:

```bash
npm install @nexusdi/interceptors@next
```

### Registering the Plugin

`interceptors({ register })` from `@nexusdi/interceptors` is a plugin that you pass to `Nexus.create`. `register` lists each interceptor under a token with `interceptor(token, { useClass })`, and `imports` names the modules the interceptors' own deps come from. ### Chain Order

The chain of a method runs the global entries first, then the bindings, then the class list, then the method list. A token that appears twice runs once, at its outermost position. In a list, the first interceptor is the outermost.

## Controlling the Execution Flow

Interceptors give you full control over the method call:

- **Modify Arguments:** Pass different arguments to `next(args)` to run the rest of the chain with a new input.
- **Short-circuit:** Return a value without calling `next()` to skip the method entirely (perfect for caching). An interceptor that calls `next()` twice runs the method twice.
- **Observe Results:** Use the `tap()` helper to run logic after the method completes without altering the result.

### Observing with `tap()`

`tap(next, { value, error })` runs `next()`, calls `value` with the result or `error` with the failure, and returns or rethrows the original. It handles a plain return, a returned promise, a rejected promise and a synchronous throw alike, so a logging interceptor needs no branch for async methods.

```

A method declared `async` turns a synchronous throw from any interceptor into a rejected promise, so the caller's `.catch` sees it.

## The Proxy Pattern

When you `get()` a service that has interceptors, NexusDI returns a **Proxy**. The container stores the proxy, so a call through `get()` or through an injected dependency runs the chain.

It is important to understand that:

1. Calls made through the proxy (e.g., `computer.status()`) are intercepted.
2. Calls made via `this` inside the class (e.g., `this.status()`) **bypass the proxy** and are not intercepted.
3. A method runs with `this` set to the service itself, so private fields such as `#serial` work.
4. `instanceof` holds for the proxy, and `get(T) === this` inside the class is false, because `this` is the service itself and `get()` returns its proxy.

```

**Try it:** Save the region as `identity.ts` and run `npx tsx identity.ts`. It prints `true`, `false`, `online QC-7` and `[ 'isSelf', 'selfTest' ]`. Add `computer.status();` before the `selfTest` line and run it again: the log is `[ 'isSelf', 'status', 'selfTest' ]`, because that call goes through the proxy. Remove the line again.

If you need an internal call to be intercepted, call the method through the token from outside the class, or move the method to another service and call it through that service's proxy. Do not inject the class's own token into the class: a class that depends on itself is a cycle, and `Nexus.create` rejects it.

## Interceptor Lifetimes

Interceptors are always **Singletons**. Each interceptor is built once per container. A scoped or transient interceptor makes `create` reject with `NEXUS_BLUEPRINT_INVALID`, which holds `NEXUS_INTERCEPTOR_LIFETIME` and core's [NEXUS_LIFETIME_VIOLATION](/errors/NEXUS_LIFETIME_VIOLATION/) for the singleton registry that would capture it. If an interceptor needs request-specific data, it reads it from `call.scope` or `call.instance`.

## Error Text

The errors `create` reports through the plugin's checks, and the bad-argument fault a wrapped method raises after setup, carry a one-line message with a link to their page. The full text and fix lines live in `interceptorsText` at `@nexusdi/interceptors/text`. Pass it to `errors()`, as the lifetime region does:

```ts no-run
import { errors } from '@nexusdi/errors';
import { interceptors } from '@nexusdi/interceptors';
import { interceptorsText } from '@nexusdi/interceptors/text';

const plugins = [errors({ text: [interceptorsText] }), interceptors(options)];
```

[Error Text Packs](/error-text/) covers the packs of every package.

## Rules

- [NEXUS_INTERCEPTOR_NOT_READY](/errors/NEXUS_INTERCEPTOR_NOT_READY/) carries its own full text, and `errors()` packs do not change it. A method called after its container is disposed throws it. So does one called from a constructor before its interceptors are built, which `create` reports as [NEXUS_PROVIDER_FAILED](/errors/NEXUS_PROVIDER_FAILED/) with that code as its `cause`.
- Call `interceptors()` once per container. A plugin object in use by a running container makes a second `create` reject with `NEXUS_BLUEPRINT_INVALID`, whose `errors` list holds [NEXUS_INTERCEPTORS_SHARED](/errors/NEXUS_INTERCEPTORS_SHARED/).
