# Rendering React Router on the Server

A React Router app that renders on the server runs loaders, actions and components for each request, and the request-scoped services they share need one scope per request. The scope has to stay open after the loaders return, because React Router streams deferred data and the rendered HTML after that. It has to end when the response body ends or the client leaves.

`@nexusdi/react-router` gives each request that scope from one root middleware, and disposes it once, when the body stream ends, errors or is cancelled, or when `request.signal` aborts. Loaders and actions resolve typed dependencies with `di.inject`, and the server entry hands the same scope to the components through `NexusProvider` from `@nexusdi/react`. [Scopes and the REQUEST Token](/scopes/) covers scopes, and [Using Services in React Components](/react/) covers the components.

The examples on this page call the middleware and the loaders the way React Router calls them, with no server, and `examples/bridge-console` is a full app wired the same way. The unit they demonstrate is a running server, so this page has no ship console.

## Install

The adapter installs beside core from the `next` tag, because 0.4 is a release candidate and the adapter pins the exact core release candidate:

```bash
npm install @nexusdi/react-router@next @nexusdi/core@next react-router
```

It works with React Router 8 on Node 22.22 or later, and with React Router 7.9 or later on Node 22.12 or later when `future.v8_middleware` is `true` in `react-router.config.ts`. It needs TypeScript 5.4 or later.

`app/nexus.server.ts` builds the server container and calls `nexus(ship, { request })`, which maps React Router's `request` and `params` to your `NexusRequest`. `app/root.tsx` exports `middleware = [di.middleware]`, so every document request, `.data` request and resource route passes through it:

The `request` option reads `x-mission-id` into the scope's `MISSION`, and the loader records the entry in the scoped `FLIGHT_LOG`, under that mission. A loader that `di.inject` wraps resolves its record from the request's scope, which the adapter creates on the first loader that asks. Loaders of one navigation start together and share that one scope. `request.mission` type-checks once your app augments `NexusRequest`, as [Scoping Node.js HTTP Requests](/node-request-scopes/) shows.

In the dev server, `nexus.server.ts` also disposes the container when Vite replaces the module, with `import.meta.hot?.dispose(() => ship[Symbol.asyncDispose]())`. Without it, each edit leaks a container. To see the scope's source, call `loader({ params, context })` without the middleware: it throws `[@nexusdi/react-router] no scope on this request: register di.middleware before this route`.

When using the function form `nexus(() => Nexus.create(Meridian))`, the module holds no container, so `nexus.server.ts` disposes `di` when Vite replaces the module:

```ts no-run
import.meta.hot?.dispose(() => di[Symbol.asyncDispose]());
```

`di[Symbol.asyncDispose]()` disposes the container the adapter built.

## Protecting Routes with Injected Middleware

Route guards often require request-scoped dependencies, such as an authentication or access-control service, to determine if a user can access a page. Because a guard must be able to terminate a request before the route's loaders execute, it requires a mechanism that supports a middleware chain. While `di.inject` wraps loaders or actions, it lacks a `next` callback and cannot function as a guard.

**`di.injectMiddleware(deps, fn)`** resolves dependencies from the request scope and passes them to a provided function. It returns a route middleware compatible with the `export const middleware = [...]` array in React Router.

**Implementation details:**

- **Type Inference:** Type the middleware array as `Route.MiddlewareFunction[]` from the route's generated types, or as `MiddlewareFunction<Response>[]`. TypeScript then infers the `args` within the injected function, removing the need for manual annotations. A data-mode route object for `createStaticHandler` or `createBrowserRouter` takes `di.middleware` and `di.injectMiddleware` with no cast, and `di.load(module)` too, and there `next()` resolves `unknown`, as React Router types it. Declare a middleware outside the route object as `const guard: MiddlewareFunction = di.injectMiddleware(...)`, so TypeScript knows which mode it runs in.
- **Request Flow:** To stop the request and prevent the loader from running, return a `Response`. To allow the request to proceed, return `next()`. In a browser router (`createBrowserRouter`) a guard stops the navigation by throwing a `Response` or `redirect()`.
- **Error Handling:** An unhandled exception within the function reaches React Router. If the function returns without calling `next`, React Router invokes `next` automatically.
- **Resolution Failures:** If the requested dependencies cannot be resolved, the middleware throws a `Response` with status 500 or 503, maintaining consistency with loader behavior.

## Hand the Scope to the Server Render

`app/entry.server.tsx` reads the scope from the router context with `loadContext.get(NEXUS_SCOPE)?.scope()` and passes it to `NexusProvider` as `scope`, so a component that calls `useService` during the server render reads the request's scoped services. In React Router's `handleRequest(request, status, headers, routerContext, loadContext)`, with `ship` from `nexus.server.ts`, `NEXUS_SCOPE` from `@nexusdi/react-router`, `renderToPipeableStream` from `react-dom/server`, `ServerRouter` from `react-router`, and `options` the stream options of React Router's default `entry.server.tsx`:

```tsx no-run
const scope = await loadContext.get(NEXUS_SCOPE)?.scope();
const { pipe } = renderToPipeableStream(
  <NexusProvider container={ship} scope={scope}>
    <ServerRouter context={routerContext} url={request.url} />
  </NexusProvider>,
  options,
);
```

React Router renders a request that no route matches without the root middleware, so on a 404 `loadContext.get(NEXUS_SCOPE)` returns `null`, and the page renders with the container and no scope. `app/entry.client.tsx` awaits the browser's own container, built in `app/ship.client.ts`, before `hydrateRoot`, so the hydration render reads services at once and matches the server HTML. Bind every token a component reads in render in both containers, the server's and the client's.

## When the Scope Is Disposed

The adapter wraps the response body and disposes the scope when the body stream ends, errors or is cancelled, or when `request.signal` aborts. A deferred value that an `<Await>` renders streams inside that body, so it reads the scope before disposal. A response with no body, a `HEAD` request and a 204 or 304 dispose as soon as the middleware chain returns. In a browser data router, `next()` resolves the loaders' results. `di.middleware` disposes the scope when the chain returns, and hands the results to React Router unchanged. A loader that returns a promise unawaited, for `<Await>`, must resolve its services before it returns, since the scope is gone when that promise settles.

## Errors

The adapter catches a NexusDI error from creating the scope or resolving a record, and logs it once through `log`. It then throws a `Response` whose body is the status text: 500, or 503 while the container shuts down:

## Ambient Scope

`nodeScopes()` from `@nexusdi/node` gives code deep in a service the request's scope without a parameter. Pass it as the `scopes` option, and the root middleware runs the rest of the request inside it, so `scopes.current()` returns the request's scope in loaders and the services they call. With `scopes` set, the middleware creates the scope at once. [Scoping Node.js HTTP Requests](/node-request-scopes/) explains how `nodeScopes()` keeps concurrent requests apart.
