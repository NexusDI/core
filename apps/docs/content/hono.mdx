# Scoping Hono Requests

A Hono handler that uses request-scoped services needs a scope per request, and the scope has to stay open until the response is done. Hono's `stream()` and `streamSSE()` return the response before the body is written. A scope disposed when the handler returns is gone while the stream still reads from it, and a scope disposed when the stream ends leaks when the client aborts.

`@nexusdi/hono` gives each request one scope and disposes it once, when the response body ends or the client leaves. Its middleware creates the scope the first time a handler asks for a dependency, so a request that resolves nothing opens no scope. [Scopes and the REQUEST Token](/scopes/) covers scopes themselves, and the [Hono documentation](https://hono.dev/docs/) covers Hono.

The examples on this page run through Hono's in-process `app.request()`, so the tests behind them open no port. The unit they demonstrate is a running server, so this page has no ship console.

## Install

The adapter installs beside core from the `next` tag, because 0.4 is a release candidate and the adapter pins the exact core release candidate:

```bash
npm install @nexusdi/hono@next @nexusdi/core@next hono
```

It works with `hono` 4.3.3 or later, on Node 22.12 or later with TypeScript 5.4 or later. It also runs on Bun, Deno, Cloudflare Workers and Vercel Edge.

## Create the Scope per Request

`nexus(ship, options)` from `@nexusdi/hono` takes your container and a `request` function that maps Hono's context to your `NexusRequest`. Register `di.middleware` on the app, then chain the routes on it, because Hono types `c.var.nexus` only on routes chained after the middleware. An app that registers routes in separate statements declares `new Hono<NexusEnv>()`, with `NexusEnv` imported from `@nexusdi/hono`.


The `request` function reads the `x-mission-id` header into the `mission` field of `NexusRequest`, which the `MISSION` provider reads through `REQUEST`. The scoped `FLIGHT_LOG` records each entry under that mission, and each request gets a log of its own. Map to domain values such as a mission or a user id, and keep Hono's `c` out of `NexusRequest`, so your services stay free of Hono.

`request` is required when your `NexusRequest` has a required field, as `mission` is here. [Scoping Node.js HTTP Requests](/node-request-scopes/) shows the `declare module '@nexusdi/core'` augmentation that adds the field.

To try it, save the region as `bridge.ts` and run `npx tsx bridge.ts`. It prints the course and one log entry, `survey-7: plotting Kepler-442b`. Delete `.use(di.middleware)` and run it again: Hono logs `[@nexusdi/hono] no scope on this request: register di.middleware before this route`, the reply is `500 Internal Server Error`, and `res.json()` throws. Put the middleware back.

## Handlers with `inject`

`di.inject({ name: TOKEN }, handler)` resolves the record from the request's scope and passes it to the handler as the first argument, with Hono's context second. The record's types follow the tokens, so `charts` is an `INavCharts` and `log` is an `IFlightLog`. `optional(TOKEN)`, `lazy(TOKEN)` and `all(MULTI)` work in the record as they do in `static deps`.

A handler that `inject` wraps reads `c.req.param('to')` as `string | undefined`. Hono types a path's params only for a handler written inline after the path, so the `bridge` region narrows the value with `c.req.param('to') ?? ''`.

`inject` checks the record against the container when you define the route. A token that no module provides throws at startup, and the adapter logs one line per failing entry through the `log` option:

```ts file=examples/meridian/src/pages/hono.md region=missing

```

The thrown error is a `BlueprintError` holding [NEXUS_MISSING_PROVIDER](/errors/NEXUS_MISSING_PROVIDER/). With a live container, a wrong token fails when the app starts. With the function form of the Workers section below, the check runs on the first request, which gets a 500. Code that is not a route handler reads the scope with `await di.scope(c)`, which rejects when `di.middleware` has not run on the request.

## When the Scope Is Disposed

The middleware disposes the request's scope once, at the first of four signals: the response body ends, the body errors, the consumer cancels the body, or `c.req.raw.signal` aborts. A response with no body, a `HEAD` request and a 204 or 304 dispose as soon as the handler returns. A request that resolves nothing creates no scope, so it disposes nothing.

The adapter wraps the response body in a pass-through stream to see the first three signals, and keeps the status and headers. `@hono/node-server` aborts the request's signal when the socket closes before the response finishes. A WebSocket upgrade returns a 101 with no body, so its scope is disposed when the upgrade completes. A WebSocket handler must not hold scoped instances, because they are disposed while the socket is still open.

On Cloudflare Workers the adapter hands the disposal to `c.executionCtx.waitUntil`, so async disposers finish after the response. On Node, Bun and Deno no execution context exists, and the disposal runs in the process.

## Errors

The adapter catches a NexusDI error from creating the scope or resolving the record, and throws Hono's `HTTPException` with status 500, or 503 while the container shuts down. The exception's message is the status text, and its `cause` is a `NexusHttpError` whose own `cause` is the NexusDI error, so your `app.onError` reads `error.cause.cause.code`. Hono's default error handler sends the status text as the body, which carries no error code and no token name.

```ts file=examples/meridian/src/pages/hono.md region=errors

```

The `MISSION` factory throws, the container reports [NEXUS_PROVIDER_FAILED](/errors/NEXUS_PROVIDER_FAILED/), and the client gets `500 Internal Server Error`. The adapter logs the error once through `log`. The default `log` writes the code, the error's fields and its message with `console.error`, and Hono's default handler logs nothing, so one failed request writes one line.

The log line holds the message exactly as core or a plugin wrote it. A plugin's error text, a third-party `construct` hook's included, reaches your log verbatim, so request data that a plugin puts in its message reaches the log too. The response body carries only the status text. Register `errors()` from `@nexusdi/errors` in development to get the full error text in that line ([Error Text Packs](/error-text/)).

## Ambient Scope

`nodeScopes()` from `@nexusdi/node` gives code deep in a service the request's scope without a parameter. Pass it as the `scopes` option, and the middleware runs the rest of the request inside it:

```ts file=examples/meridian/src/pages/hono.md region=ambient

```

`currentMission()` takes no argument and reads the scope from `scopes.current()`. With `scopes` set, the middleware creates the scope at once, because `current()` is synchronous and has no way to wait for a first use. `nodeScopes()` runs on Node, Bun, Deno and Workers through each runtime's `node:async_hooks`, and Workers needs the `nodejs_compat` flag for it. [Scoping Node.js HTTP Requests](/node-request-scopes/) explains how `nodeScopes()` keeps concurrent requests apart.

## Shutdown

Your Node entry stops the server first and disposes the container after, because the container serves every request until the server closes. `createBridge(ship)` below stands for a function that returns the `bridge` app of the first region, built on the container it receives:

```ts no-run
import { Nexus } from '@nexusdi/core';
import { errors } from '@nexusdi/errors';
import { serve } from '@hono/node-server';
import { once } from 'node:events';

const dev = process.env.NODE_ENV !== 'production';

const ship = await Nexus.create(Meridian, {
  plugins: dev ? [errors()] : [], // the full error text in development logs
});
const server = serve(createBridge(ship));
process.once('SIGTERM', () => server.close());
await once(server, 'close');
await ship[Symbol.asyncDispose](); // after the last request has finished
```

An app that disposes the container before its server stops answers the remaining requests with a 503.

## Run on Workers and Vercel Edge

An edge isolate evaluates your module once and serves many requests, so the container belongs to the isolate and no request builds one. Pass `nexus` a function that returns `Nexus.create(...)`: the adapter calls it on the first request and keeps the promise. A request whose build rejects gets a 503, and the next request builds again. Workers refuses I/O at module scope, which is why a graph whose factory downloads data needs this form there.

```ts no-run
// src/worker.ts, on Cloudflare Workers
export default createBridge(() => Nexus.create(Meridian));
```

The Worker's `wrangler.jsonc` sets a compatibility date and two flags. `nodejs_compat` gives `nodeScopes()` its `node:async_hooks`, and `enable_request_signal` makes `request.signal` abort when the client disconnects:

```jsonc no-run
{
  "main": "src/worker.ts",
  "compatibility_date": "2026-09-01",
  "compatibility_flags": ["nodejs_compat", "enable_request_signal"],
}
```

On Vercel Edge, export a function that passes Vercel's context to `app.fetch`. `hono/vercel`'s `handle(app)` and `@hono/vercel` 1.0.1 call `app.fetch(request)` with no execution context, so the adapter finds no `waitUntil` and a disposer that is still running after the response can be cut off:

```ts no-run
const app = createBridge(() => Nexus.create(Meridian));

type VercelContext = { waitUntil(promise: Promise<unknown>): void };

export default (request: Request, context: VercelContext) =>
  app.fetch(request, {}, context);
```

A singleton must not hold an I/O object such as a socket or a stream, because Workers refuses I/O on an object that another request created, and every request shares a singleton. Data a factory fetched is fine, and a database client that opens a connection is `scoped`. An isolate gets no shutdown signal, so an edge entry disposes no container.
