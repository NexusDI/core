# Writing NexusDI Plugins

NexusDI is designed to be extended. Whether you need to add custom logging, integrate with an external monitoring tool, or implement a specialized provider lookup, you can do so by writing a plugin.

The first-party packages `@nexusdi/errors`, `@nexusdi/devtools`, `@nexusdi/testing`, `@nexusdi/federation` and `@nexusdi/interceptors` use only the API on this page, so a third-party plugin can do what they do.

## The Extension Principle

To ensure that the ecosystem remains stable and maintainable, all NexusDI plugins follow the **Extension Principle**. This principle ensures that packages integrate through public contribution points and never reach into internal state. A package that does not own a new error, event, graph note or package needs no change when one is added.

**Key Rules for Plugin Authors:**

1. **Own your vocabulary:** Never rely on internal strings or hidden fields of other packages. A package reads another package's codes, event types and ids only through what that package exports, and never copies them into a table or a regex. You may compare `event.type` with `===` or a `switch` when the compiler checks it against the union the owner exports, such as `TraceEvent` from `@nexusdi/core`. Give the `switch` a `default` branch, since other packages add event types of their own.
2. **Open Types:** Use augmentable interfaces (like `NexusErrorByCode`) so other plugins can add their own types. A set that other packages extend is open in its type. `NexusErrorByCode` and `TraceEventByType` are interfaces a package augments, text packs and graph annotators are arguments the application passes, and code that branches on such a set handles a member it does not know.
3. **Public Hooks:** Only integrate via official plugin hooks or the `PluginContext`. The public, versioned contribution points are a plugin hook, a `PluginContext` member, a view field and an options argument.
4. **No Logic Duplication:** If two plugins need the same logic, the owner of that logic should export a helper.
5. **One-Way Optional Dependencies:** An optional dependency points one way, and the application writes the wiring line. A package names an optional package only in a type import or from a subpath the application opts into, such as `./text`, does not look for a missing package at run time, and never looks a plugin up by name.

## The Plugin Object

A plugin is a plain JavaScript object that declares its `name` and the `apiVersion` it was written against. The version is `NEXUS_PLUGIN_API` from `@nexusdi/core`. It then implements one or more optional hooks. Core reads the hooks once, when `Nexus.create` registers the plugin.

```ts no-run
const myPlugin = {
  name: 'my-plugin',
  apiVersion: NEXUS_PLUGIN_API,
  // Hooks go here...
};
```

### Common Hooks

Every hook is optional:

| Hook               | Purpose                                                                                                                    |
| :----------------- | :------------------------------------------------------------------------------------------------------------------------- |
| `modules`          | Adds modules to the root's imports, compiled like any import.                                                              |
| `onInit`           | `false` skips `onInit` at `create` and `load`.                                                                             |
| `tokenKey`         | Maps a token to the key every lookup uses; one key finds one provider.                                                     |
| `compile.module`   | Replaces a module definition before the compiler validates it.                                                             |
| `compile.provider` | Replaces or removes a provider before the compiler validates it.                                                           |
| `compile.check`    | Validate the graph and report custom errors before the container starts.                                                   |
| `construct`        | Wrap or observe instances as they are created. It may return a wrapper to store.                                           |
| `observe`          | Listen to every trace event emitted by the container.                                                                      |
| `formatError`      | Provide custom human-readable text for specific error codes.                                                               |
| `setup`            | Perform one-time initialization after singletons are built. It runs once, in plugin order, and receives a `PluginContext`. |
| `dispose`          | Runs at container disposal, after every root-owned instance, in reverse plugin order, for plugins whose `setup` finished.  |

## Reporting Custom Errors

If your plugin finds a problem with the module graph during `compile.check`, you can report it as a formal NexusDI error. The call is `compile.check(view, report)`. `Nexus.create` adds the error to the `NEXUS_BLUEPRINT_INVALID` it throws.

1. **Define the Error:** Use `errorBase()` to create a stable error class with a code and a link to your documentation. The call is `errorBase(code, name, docsBase)`. The third argument is the base URL of your docs, and the one-line message links to it followed by the code. An error built with a `cause` adds the cause after `Cause:`. Add the code to `NexusErrorByCode`, so `isNexusError` narrows it and a text pack can name it.
2. **Provide the Text:** Create a text pack that maps the error code to a human-readable message. Type it with `satisfies ErrorTextPack` and publish it at the package's `./text` subpath. The application passes the pack to `errors({ text })`.
3. **Report the Error:** Call `report()`, the second parameter of your `compile.check` hook.

## Emitting Custom Trace Events

You can add your own events to the container's trace, which allows other plugins (and the `@nexusdi/devtools` plugin) to observe your plugin's behavior.

By augmenting the `TraceEventByType` interface, you can add type-safe events that you can emit from the `PluginContext`. Use keys of the form `<package>/<event>`. Emit with `context.emit(make)` from the `PluginContext` your `setup` hook receives. Every `observe` hook receives the event, and `make` runs only when an observer exists.

## Graph Annotation

If your package analyzes the graph, it can add "notes" to specific providers. Annotators are not a plugin hook: the application passes `GraphAnnotator` functions to `devtools({ annotate })`, and `graph()` lists the notes on each provider. An annotator reads the container's `BlueprintView` and returns notes, each a provider id and a label. It matches the shape with no import from `@nexusdi/devtools`, so a package publishes one from a subpath and keeps devtools out of its dependencies.

## Versioning and Compatibility

Every plugin declares in `apiVersion` the plugin API it was written for. `Nexus.create` checks it before it compiles the graph.

**The API Version**. `NEXUS_PLUGIN_API` is 1 in every 0.4 release. Core raises this version only when a change breaks a plugin written for the current version. These raises occur in minor releases (or major releases from 1.0 onwards). Non-breaking additions keep the version: a new hook, a new optional member of a hook, a new `PluginContext` member, a new `ErrorTextKit` member, a new view field, a new `GraphNote` field and a new `TraceEventByType` key.

**Supported Versions**. `SUPPORTED_PLUGIN_APIS` lists every version the core accepts in ascending order, always including the current `NEXUS_PLUGIN_API`. A version remains accepted from the minor release that introduces it through at least the following minor.

**Try it:**

1. Save the region as `version.ts` and run `npx tsx version.ts`. It prints `1`, `[ 1 ]`, `true` and `true`.
2. Add `SUPPORTED_PLUGIN_APIS.push(2);` at the end. `npx tsc --noEmit` flags it with `Property 'push' does not exist on type 'readonly number[]'.`, and `npx tsx version.ts` throws `TypeError: Cannot add property 1, object is not extensible`, because core froze the list.
3. Remove the line and the first output returns.

A version raise appears in the first release candidate (rc) of a minor release or not at all in that minor, so plugin authors get the rc window to publish a compatible build. Core never raises the version in two consecutive minors and never modifies the supported list in a patch or in any rc after the first rc of a minor. If a version raise allows older plugins to continue working unchanged, core lists both versions. Core does not provide shims for versions it cannot serve.

Plugin API 1: `@nexusdi/core` 0.4.0 and later.

Issue [#289](https://github.com/NexusDI/core/issues/289) tracks a release check of the version rule.

**Version Mismatches**. If a plugin's `apiVersion` is missing, not a number or not in the supported list, `Nexus.create` rejects and `check()` throws `NEXUS_BLUEPRINT_INVALID`, which holds a [NEXUS_PLUGIN_VERSION](/errors/NEXUS_PLUGIN_VERSION/) for the plugin. The error names the plugin, the declared version and the supported list. Core registers none of that plugin's hooks, so its `formatError`, `setup` and every other hook never run.

[Guarantees for Plugin and Adapter Authors](/extension-contract/) states what stays stable across a version and what may change.

**Distribution**. Declare `@nexusdi/core` as a peer dependency and add the `nexusdi-plugin` keyword to your `package.json` to make the package discoverable. [NexusDI Plugins](/plugins/) shows the application side.
