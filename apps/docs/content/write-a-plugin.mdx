# Writing NexusDI Plugins

NexusDI is designed to be extended. Whether you need to add custom logging, integrate with an external monitoring tool, or implement a specialized provider lookup, you can do so by writing a plugin.

## The Extension Principle

To ensure that the ecosystem remains stable and maintainable, all NexusDI plugins follow the **Extension Principle**. This principle ensures that packages integrate through public contribution points and never reach into internal state.

**Key Rules for Plugin Authors:**

1. **Own your vocabulary:** Never rely on internal strings or hidden fields of other packages.
2. **Open Types:** Use augmentable interfaces (like `NexusErrorByCode`) so other plugins can add their own types.
3. **Public Hooks:** Only integrate via official plugin hooks or the `PluginContext`.
4. **No Logic Duplication:** If two plugins need the same logic, the owner of that logic should export a helper.

## The Plugin Object

A plugin is a plain JavaScript object that declares its `name` and the `apiVersion` it was written against. It then implements one or more optional hooks.

```ts no-run
const myPlugin = {
  name: 'my-plugin',
  apiVersion: NEXUS_PLUGIN_API,
  // Hooks go here...
};
```

### Common Hooks

| Hook            | Purpose                                                                  |
| :-------------- | :----------------------------------------------------------------------- |
| `compile.check` | Validate the graph and report custom errors before the container starts. |
| `construct`     | Wrap or observe instances as they are created.                           |
| `observe`       | Listen to every trace event emitted by the container.                    |
| `formatError`   | Provide custom human-readable text for specific error codes.             |
| `setup`         | Perform one-time initialization after singletons are built.              |

## Reporting Custom Errors

If your plugin finds a problem with the module graph during `compile.check`, you can report it as a formal NexusDI error.

1. **Define the Error:** Use `errorBase()` to create a stable error class with a code and a link to your documentation.
2. **Provide the Text:** Create a text pack that maps the error code to a human-readable message.
3. **Report the Error:** Call `report()`, the second parameter of your `compile.check` hook.

## Versioning and Compatibility

To prevent crashes, NexusDI checks the `apiVersion` of every plugin. If the core API changes in a way that breaks a plugin, the version is incremented. Core accepts every plugin API version it still supports. If a plugin's `apiVersion` is not one of them, `Nexus.create` rejects the startup process with a `NEXUS_PLUGIN_VERSION` error.
