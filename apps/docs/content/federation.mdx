# How do I share tokens between a shell and its remotes?

Define the shared tokens in a contract with `defineContract()` from `@nexusdi/federation`, and register `federation()` in the shell's container. Then list `@nexusdi/core` as a shared singleton in the Module Federation `shared` setting of the shell and of every remote.

A micro-frontend app splits into a shell and remotes. The shell holds the container and loads each remote at runtime, and each remote is a bundle built and served apart from the shell. The shell provides the services every remote needs, such as the star charts behind `NAV_CHARTS`, and a remote's section depends on them.

```bash
npm install @nexusdi/federation@next @nexusdi/core@next
```

## Two Bundles Hold Two Copies of a `Token`

A `Token` is compared by identity: two `new Token()` calls make two tokens, even with the same description. The shell and a remote each bundle their own copy of the package that declares `NAV_CHARTS`, so the remote's `NAV_CHARTS` is a different object from the shell's. Below, `SectorRoutes` in the remote's `Cartography` section depends on the remote's copy, and the shell provides its own. `ship.load(Cartography)` rejects with [NEXUS_BLUEPRINT_INVALID](/errors/NEXUS_BLUEPRINT_INVALID/), whose `errors` list holds [NEXUS_MISSING_PROVIDER](/errors/NEXUS_MISSING_PROVIDER/).


**Try it:** Save the region as `copies.ts` and run `npx tsx copies.ts`. It prints `['NEXUS_MISSING_PROVIDER']`. Change `static deps = [REMOTE_NAV_CHARTS]` to `static deps = [NAV_CHARTS]` and run it again: one bundle with one token loads the section, and the region prints `[]`. Change it back.

## Declare Shared Tokens in a Contract with `defineContract()`

A contract gives every copy of a token the same name and a version. `defineContract({ key, version })` returns a token maker, and `meridian.token<INavCharts>('NavCharts')` makes a `Token<INavCharts>` described `meridian/NavCharts`, the contract key and the token name joined by a slash. Each token also carries a contract mark, `{ key, name, version }`, and `federation()` reads it from every copy.

```ts file=examples/meridian/src/pages/federation.md region=contract

```

**Try it:** Save the region as `contract.ts` and run `npx tsx contract.ts`. It prints `meridian/NavCharts`. Change `'2.4.0'` to `'v2'` and run it again: `defineContract()` throws `TypeError: defineContract({ key: 'meridian' }) needs a version such as 2.3.0, and got 'v2'.` Change it back.

The contract lives in its own package, which the shell and every remote depend on. Keep the contract with the shell's team. The shell provides every contract token, so the team that binds the providers decides what each token promises and when the version moves. A remote depends on the contract tokens and never provides one.

## Bind Each Copy to the Shell's Provider with `federation()`

`federation()` binds every copy of a contract token to one provider. The plugin matches tokens by contract key and token name, so the remote's `meridian/NavCharts` resolves to the provider the shell registered for its own `meridian/NavCharts`. Register it in the shell's `Nexus.create`. A remote registers no plugin, since the shell's container builds every section a remote hands it.

The shell provides the contract tokens from a contract module, `Tactical` here, marked [`global: true`](/modules/). A remote cannot import the shell's `Tactical` object, so a section that [`load()`](/load/) adds sees `NAV_CHARTS` only through the exports of a global module.

```ts file=examples/meridian/src/pages/federation.md region=load-section

```

**Try it:** Save the region as `section.ts` and run `npx tsx section.ts`. It prints `Kepler-442b: heading 42`. Change `Nexus.create(Meridian, { plugins: [federation()] })` to `Nexus.create(Meridian)` and run it again: `load()` rejects with `NEXUS_BLUEPRINT_INVALID`, whose `errors` list holds `NEXUS_MISSING_PROVIDER` for `meridian/NavCharts`. Put the plugin back and the region prints `Kepler-442b: heading 42` again.

Delete `global: true,` from `Tactical` and run the region once more. `Cartography` no longer sees the exports of `Tactical`, and `load()` rejects with the same error. Put the line back.

## Check Contract Versions with `NEXUS_CONTRACT_VERSION`

`federation()` compares the version on each contract token a provider depends on with the version on the token the shell provided. It runs when `Nexus.create` or `load()` compiles the graph, before any constructor runs. A remote built against a newer version than the shell provides fails, since it may call a member the shell's provider does not have. The rule follows npm's `^` range, except at 0.0.x, where a newer shell patch also satisfies. The comparison ignores a prerelease tag:

- The majors must match.
- From major 1 on, the remote's minor may be older than the shell's or the same.
- With the same minor, the remote's patch must be no newer than the shell's.
- At major 0, the minors must match, because a minor is a breaking change there.

A mismatch rejects the load with [NEXUS_CONTRACT_VERSION](/errors/NEXUS_CONTRACT_VERSION/) inside `NEXUS_BLUEPRINT_INVALID`. Register the `errors()` plugin from `@nexusdi/errors` (`npm install @nexusdi/errors@next`) with `{ text: [federationText] }`, and the error carries its full text and a fix. `federationText` comes from `@nexusdi/federation/text`. Here the remote was built against 2.4.0 and the shell provides 2.3.0:

```ts file=examples/meridian/src/pages/federation.md region=drift

```

**Try it:** Save the region as `drift.ts` and run `npx tsx drift.ts`. It prints `[NEXUS_CONTRACT_VERSION] meridian/NavCharts is needed at 2.4.0, and the provider has 2.3.0.` Change the remote's version to `'2.2.0'` and run it again. The shell's 2.3.0 satisfies an older minor, so the load resolves. The region prints `undefined`. Change it to `'3.0.0'` and the error returns for a new major. Change it back to `'2.4.0'`.

Move the contract's minor when the shell adds a token or a member to a token's interface. Move its major when a token's interface changes in a way an older remote cannot read.

## Share One `@nexusdi/core` Between the Bundles

`federation()` binds the copies of a contract token, and every bundle must load the same copy of `@nexusdi/core`. Each copy of core brands the definitions it makes, and it rejects a definition that another copy made. A remote that bundles its own core hands the shell a `Cartography` from another copy, and `load()` rejects with [NEXUS_CORE_NOT_SHARED](/errors/NEXUS_CORE_NOT_SHARED/).

The shell and every remote list `@nexusdi/core` in the `shared` setting of Module Federation, with `singleton: true` and `requiredVersion` set to core's exact version, since every `@nexusdi` package peers on that version. A remote whose components call [`useService`](/react/) shares `@nexusdi/react` the same way, so that it reads the shell's `NexusProvider`. Each `rspack.config.ts` passes the object to its `ModuleFederationPlugin`:

```ts file=examples/meridian/src/pages/federation.md region=shared

```

**Try it:** Run `npm install react`, save the region as `shared.ts` and run `npx tsx shared.ts`. It prints `true` twice. Change `requiredVersion: core` on the `@nexusdi/core` line to `requiredVersion: react` and run it again: the second line is `false`. Change it back.

The federation demo builds this object once, in [`meridianShared()`](https://github.com/NexusDI/core/blob/release/0.4/examples/federation-contracts/src/shared.ts). Its unshared build calls `meridianShared({ core: false })`, which drops the `@nexusdi/core` entry.

The contracts package has no entry in `shared`, so each bundle holds its own copy, and `federation()` binds the copies by key. `@nexusdi/federation` and `@nexusdi/decorators` have no entry in `shared` either. A second copy of `@nexusdi/federation` reads the contract marks every copy writes under a registered `Symbol.for()` key, and a second copy of `@nexusdi/decorators` writes what its decorators declare through the shared core.

## The Full Federation Demo

The federation demo runs this page's setup across real rspack bundles, with an end-to-end suite in Chromium. Six folders hold it:

- [`examples/federation-shell`](https://github.com/NexusDI/core/tree/release/0.4/examples/federation-shell): the shell, whose root `Meridian` imports the global `Tactical`, with `federation()` and `errors({ text: [federationText] })` in its container `ship`.
- [`examples/federation-cartography`](https://github.com/NexusDI/core/tree/release/0.4/examples/federation-cartography): the `cartography` remote, which exposes the section `CartographyStation` and its component `CartographyPanel`. Its drift build raises `NEXUS_CONTRACT_VERSION`, and its unshared build raises `NEXUS_CORE_NOT_SHARED`.
- [`examples/federation-command`](https://github.com/NexusDI/core/tree/release/0.4/examples/federation-command): the `command` remote, whose section `CommandStation` is written with `@nexusdi/decorators`.
- [`examples/federation-engineering`](https://github.com/NexusDI/core/tree/release/0.4/examples/federation-engineering): the `engineering` remote, which exposes the section `EngineeringStation` and its component `EngineeringPanel`. The panel shows the reactor and coolant gauges and the power budget.
- [`examples/federation-life-support`](https://github.com/NexusDI/core/tree/release/0.4/examples/federation-life-support): the `life-support` remote, which exposes the section `LifeSupportStation` and its component `LifeSupportPanel`. The panel shows the compartment air and sends atmosphere commands.
- [`examples/federation-contracts`](https://github.com/NexusDI/core/tree/release/0.4/examples/federation-contracts): the `meridian` contract and `meridianShared()`.
