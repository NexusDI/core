# Scoping Node.js HTTP Requests

In a web server, you often need a "request scope": a set of dependencies that are created when a request arrives and disposed when its handler settles.

The `@nexusdi/node` package provides `nodeScopes()`, which leverages Node's `AsyncLocalStorage` to bind a NexusDI scope to the current asynchronous execution context. This allows you to access the request's scope deep within your call chain without having to pass the scope object manually through every function. [Scopes and the REQUEST Token](/scopes/) covers the scopes themselves, and the [Node documentation for `node:http`](https://nodejs.org/api/http.html) covers the server.

Install the package from the `next` tag:

```bash
npm install @nexusdi/node@next
```

## Running Handlers in a Scope

`nodeScopes()` returns an object with two methods over one `AsyncLocalStorage`: `run(scope, fn)` and `current()`. To use request scopes, you create a scope for each request with `ship.createScope()` and run your handler with `scopes.run(scope, fn)`. `run()` makes that scope the current scope of everything that happens inside the function.


`dispatch(req)` creates one scope per request with the request's mission and runs the handler inside it. `logArrival()` takes no scope argument: it reads the scope from `scopes.current()` and resolves the scoped `FLIGHT_LOG`.

`dispatch` returns `await scopes.run(...)`. The `await` keeps the scope open until the handler finishes. Without it, `await using` disposes the scope first, and the handler's next `get()` throws [NEXUS_DISPOSED](/errors/NEXUS_DISPOSED/).

**Try it:**

1. Save the region as `dispatch.ts` and run `npx tsx dispatch.ts`. It prints `survey-7: arrived`.
2. Change `return await scopes.run(` to `return scopes.run(` and run it again. The handler throws `NEXUS_DISPOSED`, because the scope closed before `logArrival()` called `get()`.
3. Put the `await` back and run it again. It prints `survey-7: arrived`.

### The `REQUEST` Token

`REQUEST` resolves to the object you pass to `createScope({ request })`. Any scoped provider can inject it to read request-specific data (like user IDs or headers) directly.

To get full type safety, augment the `NexusRequest` interface. The `dispatch` region relies on this declaration:

```ts no-run
declare module '@nexusdi/core' {
  interface NexusRequest {
    mission: { id: string; target: string };
  }
}
```

## Accessing the Current Scope

If you are in a function that was called inside a `run()` block, you can retrieve the current scope using `scopes.current()`. If `current()` is called outside of a `run()` block, it returns `undefined`. A function that needs a scope checks for it and fails with its own message, as `logArrival()` does above.

## Concurrency and Isolation

Because `nodeScopes()` uses `AsyncLocalStorage`, it is completely safe for concurrent requests. Each `run()` starts its own async context, so `scopes.current()` always returns the scope associated with the async chain of the current request.

The `nodeScopes()` object registers with no container. Create it once per process and share it between every container and every handler.

## Integrating with `node:http`

Integrating NexusDI scopes into a standard Node.js server is straightforward. The server reads the mission from the request and calls `dispatch` from the first region, which creates a scope for every incoming request and runs the handler in it. The reply goes back as the response body.

A server keeps its container for the life of the process, so declare it with `const ship`. With `await using ship` at the top level of a module, the container is disposed as soon as the module finishes loading, and the first request throws [NEXUS_DISPOSED](/errors/NEXUS_DISPOSED/).

```ts no-run
import { createServer } from 'node:http';

createServer(async (req, res) => {
  const url = new URL(req.url ?? '/', 'http://localhost');
  const id = url.searchParams.get('mission') ?? 'survey-7';
  const reply = await dispatch({ mission: { id, target: 'Kepler-442b' } });
  res.end(reply);
}).listen(3000);
```

By doing this, every request gets its own isolated set of scoped providers, which are automatically disposed of when the handler settles.

**Try it:** In `dispatch.ts`, change `await using ship` to `const ship`, add the server lines at the end, and run it. The terminal prints `survey-7: arrived` once, from the region's own call, and the process keeps running. Open `http://localhost:3000/?mission=survey-9`. The page shows `survey-9: arrived`. Stop the server with Ctrl-C. To see the failure, change `const ship` back to `await using ship` and restart the server: the first request throws `NEXUS_DISPOSED` in the terminal and the process exits without a reply. Change it to `const ship` again to fix it.
