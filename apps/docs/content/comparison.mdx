# NexusDI vs Other Containers

When choosing a dependency injection container, the primary trade-offs are typically bundle size, startup performance, and the ability to detect wiring mistakes.

NexusDI is compared here against four other TypeScript containers using a standardized benchmark harness. Every figure on this page is derived from actual measurements of the same eight-provider graph, rendered from the harness's results files at build time. [Understanding Benchmark Measurements](/benchmark-method/) states the method behind each one.

## Performance and Footprint

The performance table below compares bundle size, cold-start time, and resolution speed.

- **Bundle Size:** The minified and gzipped esbuild bundle size.
- **Startup Time:** Cold start of a fresh Node process.
- **Resolve Speed:** Time for a single transient resolution on a ready container.
- **Build Time:** The library's fastest passing build of a 200-class graph under a toolchain its documentation names.

## Toolchain Flexibility

Many DI libraries rely on `emitDecoratorMetadata`, which requires specific compiler flags that not every toolchain supports. In the matrix below, the metadata-based variants fail to compile under Node's type stripping, and tsyringe's fails at runtime under esbuild. Every variant passes under Bun and Deno.

NexusDI avoids this by using `static deps`. Because `static deps` needs no compiler-emitted metadata, it passes under every toolchain in the matrix. The `@nexusdi/decorators` variant uses standard decorators, which plain Vite and Node's type stripping cannot compile.

A cell that does not pass keeps its first error line in a tooltip and links the toolchain's own page when that page documents the limitation. InversifyJS's [getting-started page](https://inversify.io/docs/introduction/getting-started/) and tsyringe's [README](https://github.com/microsoft/tsyringe#readme) set `experimentalDecorators` and `emitDecoratorMetadata` for their decorated setups. [awilix](https://github.com/jeffijoe/awilix#readme) and [needle-di](https://needle-di.io) document setups that use no decorator metadata (inversify 8.2.3, tsyringe 4.10.0, awilix 13.0.5, needle-di 1.2.1; read 2026-09-30).

## Wiring-Mistake Detection

Most containers are "optimistic". They assume the graph is correct and only fail at runtime when a missing dependency is requested. This can lead to crashes in production on rarely-used code paths.

NexusDI is "pessimistic." It validates the entire module graph during the `Nexus.create` phase. If a dependency is missing, `Nexus.create` reports it before any constructor runs, and one error lists every problem it found ([Errors](/errors/)).

## Lifecycle and Disposal Comparison

Managing resources (like database pools) is critical. NexusDI implements a strict reverse-creation order for disposal and uses `SuppressedError` to ensure every resource is closed, even if some failures occur. [Lifecycle and Disposal](/lifecycle/) explains why each row matters.

This section comes from reading each library's source and documentation, and the harness does not measure it. A cell says what the library does without extra plugins unless it names one.

|                                                     | NexusDI                                | InversifyJS                                               | tsyringe                                         | awilix                  | needle-di | TypeDI                      | NestJS                                    |
| --------------------------------------------------- | -------------------------------------- | --------------------------------------------------------- | ------------------------------------------------ | ----------------------- | --------- | --------------------------- | ----------------------------------------- |
| Startup hook awaited in dependency order            | Yes, `onInit` before `create` resolves | Per instance on first resolve, awaited through `getAsync` | No hook                                          | No hook                 | No hook   | No hook                     | Yes, `onModuleInit`                       |
| Container disposal                                  | `Symbol.asyncDispose`                  | `unbindAllAsync()`                                        | `dispose()`                                      | `dispose()`             | None      | `reset()` calls `destroy()` | `app.close()`                             |
| Supports `Symbol.dispose` and `Symbol.asyncDispose` | Both                                   | Both, with `@inversifyjs/plugin-dispose`                  | No                                               | No                      | No        | No                          | No                                        |
| Disposal order                                      | Reverse creation                       | Unspecified, plugin runs fewest dependents first          | Creation order, so dependencies first            | All at once             | n/a       | Registration order          | Reverse of startup                        |
| All disposer failures reported                      | Yes, `SuppressedError` chain           | No, first error                                           | No, first error                                  | No, first error         | n/a       | No, errors ignored          | Logged, not thrown                        |
| Keeps going after a failure                         | Yes                                    | Plugin stops at the first                                 | Async failures only, a sync throw skips the rest | Yes                     | n/a       | Yes                         | Yes                                       |
| Scopes own transients                               | Yes                                    | No                                                        | Yes, by the container that resolved it           | No                      | n/a       | No                          | No, request-scoped providers get no hooks |
| Disposes factory results                            | Yes                                    | Only with `onDeactivation`                                | No                                               | Yes, with `.disposer()` | n/a       | Yes                         | Yes                                       |
| Leaves `useValue` objects alone                     | Yes                                    | Yes, unless `onDeactivation` is set                       | Yes                                              | Yes                     | n/a       | Yes                         | No, hooks run on them                     |

NestJS has the most complete startup story of the six. It awaits hooks module by module and by dependency depth inside a module, runs shutdown in the reverse order and logs every failure. Its hooks are provider methods, and a Nest application is not an `AsyncDisposable`. tsyringe disposes every disposable instance it builds, transients included. awilix awaits any promise a `.disposer()` returns, and a container disposes only its own cache, never its scopes. InversifyJS has `@postConstruct` and `@preDestroy`, and with its dispose plugin it supports `await using`. needle-di and TypeDI document no startup hook and no awaited disposal.

Versions read on 2026-10-03: inversify 8.2.3 (with @inversifyjs/plugin-dispose 0.4.7), tsyringe 4.10.0, awilix 13.0.5, needle-di 1.2.1, TypeDI 0.10.0, @nestjs/core 12.1.2. Sources: the published packages' code, [InversifyJS container API](https://inversify.io/docs/api/container/), [tsyringe disposable instances](https://github.com/microsoft/tsyringe#disposable-instances), [awilix disposing](https://github.com/jeffijoe/awilix#disposing), [needle-di docs](https://needle-di.io/llms-full.txt) and [NestJS lifecycle events](https://docs.nestjs.com/fundamentals/lifecycle-events). The research notes are in `specs/2026-10-03-lifecycle-comparison-research.md` in the repository.

## Containers Left Out

TypeDI is left out of the measurements: its last release, 0.10.0, was published on 2021-01-15 ([npm](https://www.npmjs.com/package/typedi)). NestJS is a framework with its own container, so it is left out too.

## Conclusion

If you are building a large-scale application where reliability, startup speed, and toolchain flexibility are priorities, NexusDI's static validation and lightweight core make it a strong choice. For those already using the NestJS framework, its built-in container already wires your services, and NexusDI would add a second container beside it ([When to skip NexusDI](/#when-to-skip-nexusdi)).

## Break and Fix a Benchmark Figure

Every figure on this page comes from the harness, and a guard keeps it that way. The `<Figure>` component renders one result inline in a sentence, and the `doc-benchmark-figures` guard fails on a path the results do not hold.

**Try it:** In `apps/docs/content/index.mdx`, change the figure's path from `size.nexusdi.plain.esbuild.gzip` to `size.nexusdi.plain.esbuild.brotli`, and run the guard:

```sh
npx nx test @nexusdi/repo-checks -- doc-benchmark-figures
```

The guard fails and names the key the results lack. Type a size with its unit into a sentence on the same page, and the guard fails on that sentence too, because a figure in prose comes only from the harness. Restore the path and delete the sentence, and the guard passes.
