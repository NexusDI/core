# NexusDI vs Other Containers

When choosing a dependency injection container, the primary trade-offs are typically bundle size, startup performance, and the ability to detect wiring mistakes.

NexusDI is compared here against four other TypeScript containers using a standardized benchmark harness. Every figure on this page is derived from actual measurements of the same eight-provider graph.

## Toolchain Flexibility

Many DI libraries rely on `emitDecoratorMetadata`, which requires specific compiler flags that not every toolchain supports. In the matrix below, the metadata-based variants fail to compile under Node's type stripping, and tsyringe's fails at runtime under esbuild. Every variant passes under Bun and Deno.

NexusDI avoids this by using `static deps`. Because `static deps` needs no compiler-emitted metadata, it passes under every toolchain in the matrix. The `@nexusdi/decorators` variant uses standard decorators, which plain Vite and Node's type stripping cannot compile.

## Wiring-Mistake Detection

Most containers are "optimistic". They assume the graph is correct and only fail at runtime when a missing dependency is requested. This can lead to crashes in production on rarely-used code paths.

NexusDI is "pessimistic." It validates the entire module graph during the `Nexus.create` phase. If a dependency is missing, `Nexus.create` reports it before any constructor runs.

## Lifecycle and Disposal Comparison

Managing resources (like database pools) is critical. NexusDI implements a strict reverse-creation order for disposal and uses `SuppressedError` to ensure every resource is closed, even if some failures occur.

| Feature                           | NexusDI | InversifyJS                    | tsyringe | awilix             | needle-di | TypeDI | NestJS |
| :-------------------------------- | :------ | :----------------------------- | :------- | :----------------- | :-------- | :----- | :----- |
| **Dependency-ordered `onInit`**   | Yes     | Per instance, on first resolve | No       | No                 | No        | No     | Yes    |
| **Reverse-order Disposal**        | Yes     | No                             | No       | No                 | n/a       | No     | Yes    |
| **Reports all disposal failures** | Yes     | No                             | No       | No                 | n/a       | No     | Logged |
| **Scopes own transients**         | Yes     | No                             | Yes      | No                 | n/a       | No     | No     |
| **Disposes factory results**      | Yes     | Partial                        | No       | With `.disposer()` | n/a       | Yes    | Yes    |

Versions read on 2026-10-03: inversify 8.2.3 (with @inversifyjs/plugin-dispose 0.4.7), tsyringe 4.10.0, awilix 13.0.5, needle-di 1.2.1, TypeDI 0.10.0, @nestjs/core 12.1.2. The harness does not measure this table: it is read from each library's source and documentation, and the notes are in `specs/2026-10-03-lifecycle-comparison-research.md`.

## Conclusion

If you are building a large-scale application where reliability, startup speed, and toolchain flexibility are priorities, NexusDI's static validation and lightweight core make it a strong choice. For those already using the NestJS framework, its built-in container already wires your services, and NexusDI would add a second container beside it.
