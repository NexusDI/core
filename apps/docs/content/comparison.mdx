# NexusDI compared with InversifyJS, tsyringe, awilix and needle-di

NexusDI is compared here with four dependency injection containers for TypeScript, each built from the same eight-provider graph by the benchmark harness in `benchmarks/`. Every figure and outcome on this page renders from the harness's results files at build time, and [How NexusDI's benchmarks are measured](/benchmark-method/) states the method behind each one.

## Performance of NexusDI and the four containers

The performance table shows each library in the variant its own documentation teaches. Bundle size is the esbuild bundle, minified and gzipped, and startup is a cold start of a fresh Node process. Resolve is one transient resolve on a ready container, and build time is the library's fastest passing build of a 200-class graph under a toolchain its documentation names. Focus or hover a figure for its spread and, on another library's row, the paired ratio to NexusDI with its interval. A ratio below 1 means NexusDI took less time, and an interval that contains 1 is no measured difference.

## Why NexusDI needs no compiler flags

A NexusDI class lists its dependencies as tokens in `static deps`, and TypeScript checks that list against the constructor. The container reads the list at run time, so no build step has to emit decorator metadata, and the NexusDI `plain` row of the toolchain matrix above shows the result under each toolchain. InversifyJS's [getting-started page](https://inversify.io/docs/introduction/getting-started/) and tsyringe's [README](https://github.com/microsoft/tsyringe#readme) set `experimentalDecorators` and `emitDecoratorMetadata` for their decorated setups, and their `decorated` rows show which toolchains build those setups. [awilix](https://github.com/jeffijoe/awilix#readme) and [needle-di](https://needle-di.io) document setups that use no decorator metadata (inversify 8.2.3, tsyringe 4.10.0, awilix 13.0.5, needle-di 1.2.1; read 2026-09-30).

## TypeDI and NestJS compared with NexusDI

TypeDI is left out of the measurements: its last release, 0.10.0, was published on 2021-01-15 ([npm](https://www.npmjs.com/package/typedi)). NestJS is a framework with its own container, and [When to skip NexusDI](/#when-to-skip-nexusdi) explains why NexusDI would add a second container beside it.

## Lifecycle and disposal in NexusDI and six other containers

This section comes from reading each library's source and documentation, and the harness does not measure it. [Lifecycle and disposal](/lifecycle/) explains why each row matters. A cell says what the library does without extra plugins unless it names one.

| | NexusDI | InversifyJS | tsyringe | awilix | needle-di | TypeDI | NestJS |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Startup hook awaited in dependency order | Yes, `onInit` before `create` resolves | Per instance on first resolve, awaited through `getAsync` | No hook | No hook | No hook | No hook | Yes, `onModuleInit` |
| Container disposal | `Symbol.asyncDispose` | `unbindAllAsync()` | `dispose()` | `dispose()` | None | `reset()` calls `destroy()` | `app.close()` |
| Supports `Symbol.dispose` and `Symbol.asyncDispose` | Both | Both, with `@inversifyjs/plugin-dispose` | No | No | No | No | No |
| Disposal order | Reverse creation | Unspecified, plugin runs fewest dependents first | Creation order, so dependencies first | All at once | n/a | Registration order | Reverse of startup |
| All disposer failures reported | Yes, `SuppressedError` chain | No, first error | No, first error | No, first error | n/a | No, errors ignored | Logged, not thrown |
| Keeps going after a failure | Yes | Plugin stops at the first | Async failures only, a sync throw skips the rest | Yes | n/a | Yes | Yes |
| Scopes own transients | Yes | No | Yes, by the container that resolved it | No | n/a | No | No, request-scoped providers get no hooks |
| Disposes factory results | Yes | Only with `onDeactivation` | No | Yes, with `.disposer()` | n/a | Yes | Yes |
| Leaves `useValue` objects alone | Yes | Yes, unless `onDeactivation` is set | Yes | Yes | n/a | Yes | No, hooks run on them |

NestJS has the most complete startup story of the six. It awaits hooks module by module and by dependency depth inside a module, runs shutdown in the reverse order and logs every failure. Its hooks are provider methods, and a Nest application is not an `AsyncDisposable`. tsyringe disposes every disposable instance it builds, transients included. awilix awaits any promise a `.disposer()` returns, and a container disposes only its own cache, never its scopes. InversifyJS has `@postConstruct` and `@preDestroy`, and with its dispose plugin it supports `await using`. needle-di and TypeDI document no startup hook and no awaited disposal.

Versions read on 2026-10-03: inversify 8.2.3 (with @inversifyjs/plugin-dispose 0.4.7), tsyringe 4.10.0, awilix 13.0.5, needle-di 1.2.1, TypeDI 0.10.0, @nestjs/core 12.1.2. Sources: the published packages' code, [InversifyJS container API](https://inversify.io/docs/api/container/), [tsyringe disposable instances](https://github.com/microsoft/tsyringe#disposable-instances), [awilix disposing](https://github.com/jeffijoe/awilix#disposing), [needle-di docs](https://needle-di.io/llms-full.txt) and [NestJS lifecycle events](https://docs.nestjs.com/fundamentals/lifecycle-events). The research notes are in `specs/2026-10-03-lifecycle-comparison-research.md` in the repository.

## Break and fix a NexusDI benchmark figure

The `<Figure>` component renders one result inline in a sentence, and the `doc-benchmark-figures` guard fails on a path the results do not hold. In `apps/docs/content/index.mdx`, change the figure's path from `size.nexusdi.plain.esbuild.gzip` to `size.nexusdi.plain.esbuild.brotli`, and run the guard:

```sh
npx nx test @nexusdi/repo-checks -- doc-benchmark-figures
```

The guard fails and names the key the results lack. Type a size with its unit into a sentence on the same page, and the guard fails on that sentence too, because a figure in prose comes only from the harness. Restore the path and delete the sentence, and the guard passes.
