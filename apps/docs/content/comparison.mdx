# NexusDI vs Other Containers

When choosing a dependency injection container, the primary trade-offs are typically bundle size, startup performance, and the ability to detect wiring mistakes.

NexusDI is compared here against four other TypeScript containers using a standardized benchmark harness. Every figure on this page is derived from actual measurements of the same eight-provider graph.

## Toolchain Flexibility

Many DI libraries rely on `emitDecoratorMetadata`, which requires specific compiler flags and often breaks when using modern toolchains like Vite, Bun, or Deno.

NexusDI avoids this by using `static deps`. Because it doesn't require compiler-emitted metadata, it works out-of-the-box with any modern TypeScript toolchain.

## Wiring-Mistake Detection

Most containers are "optimistic"—they assume the graph is correct and only fail at runtime when a missing dependency is requested. This can lead to crashes in production on rarely-used code paths.

NexusDI is "pessimistic." It validates the entire module graph during the `Nexus.create` phase. If a dependency is missing, it is reported immediately, ensuring your application never starts in a broken state.

## Lifecycle and Disposal Comparison

Managing resources (like database pools) is critical. NexusDI implements a strict reverse-creation order for disposal and uses `SuppressedError` to ensure every resource is closed, even if some failures occur.

## Conclusion

If you are building a large-scale application where reliability, startup speed, and toolchain flexibility are priorities, NexusDI's static validation and lightweight core make it a strong choice. For those already using the NestJS framework, its built-in container is highly capable, though NexusDI can be used alongside it for specific low-level needs.
