# Modules

As your application grows, putting every provider into a single global list becomes unmanageable. You lose the ability to encapsulate logic, and it becomes difficult to track where dependencies are coming from.

**Modules** solve this by grouping related providers into bounded contexts. A module defines its own internal set of providers and explicitly chooses which ones to share with the rest of the application.

## Encapsulation and Visibility

The primary purpose of a module is to control visibility. `defineModule({ name, providers, imports, exports })` declares one, and from this page on `Nexus.create` takes the program's root module. A module sees its own providers and the exports of the modules it imports, and nothing else.

- **Private Providers:** By default, everything provided inside a module is private. Only other providers within the same module can use them.
- **Public Exports:** To make a provider available to other modules, you must list its token in the `exports` array.

```

`Engineering` provides a power router and a computer, both built on a reactor, and exports only `COMPUTER`. `Meridian` imports `Engineering`, so the root container resolves `COMPUTER`. `POWER_ROUTER` stays private: `has()` answers `false` for it, and `get(POWER_ROUTER, { module: Engineering })` resolves it as code inside `Engineering` would.

`has(token)` answers whether `get(token)` would find a visible provider, and never builds anything. The `{ module }` option of `get()` and `has()` resolves as if the call came from inside that module, which suits tests and debugging sessions.

**Try it:** Save the program as `modules.ts` and run `npx tsx modules.ts`. It prints `ShipComputer online on 0.605 GW.`, then `false`, then `0.605`. Add `POWER_ROUTER` to the `exports` of `Engineering` and run it again. `routerVisible` prints `true`, and the other two lines stay the same. Remove it again and `routerVisible` prints `false`.

This pattern prevents "leaky abstractions." For example, a `DatabaseModule` might provide a `ConnectionPool` internally, but only export a `Repository` to the rest of the app. The rest of the app doesn't need to know the pool exists, and they cannot accidentally depend on it.

## Module Integration

Modules interact through `imports`. If Module A imports Module B, Module A can see everything that Module B exports.

### Global Modules

Some providers are truly universal (like configuration or logging) and are needed by almost every module. You can mark a module as `global: true`.

```

A global module's exports are visible to every module in the graph automatically, provided the global module is included in the graph at least once. `Tactical` above names no import, and its drone still reaches the reactor `Engineering` exports.

A global module suits a provider that most modules need and no module owns, such as configuration. Every other provider belongs behind an explicit import, because the import is what shows a reader where a dependency comes from.

**Try it:** Run the program and it prints `12.1`. Remove `global: true` from `Engineering` and run it again. `create` rejects with `NEXUS_BLUEPRINT_INVALID`, and its `errors` list holds one `NEXUS_MISSING_PROVIDER` for `ReactorCore`, requested by `SurveyDrone` in `Tactical`. Put `global: true` back and it prints `12.1` again.

## Swapping Implementations

Because modules are defined by the tokens they export and not by the classes they use, you can swap an entire module for another as long as the exported tokens remain the same.

This is incredibly powerful for testing. You can replace `Engineering` with a `SimulatorEngineering` module that exports the same `COMPUTER` token but binds `REACTOR` to a `SimulatedReactor` behind it.

A swap works only when the replacement exports every token the original did. A missing export passes `create` when no provider depends on the token, and fails only at `get()` with `NEXUS_NOT_VISIBLE`.

**Try it:** Run the program. It prints `Reactor output 1.21 GW.` and then `Reactor output 0 GW.`. Remove `COMPUTER` from the `exports` of `SimulatorEngineering` and run it again. `create` still resolves, because no provider depends on `COMPUTER` and the dependency check has nothing to report. Only `get(COMPUTER)` for the simulator ship throws `NEXUS_NOT_VISIBLE`, because `Meridian` can no longer see its computer. The first line still prints. Restore the export and both lines print again.
