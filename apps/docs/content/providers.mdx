# Providers

Once you have defined **Tokens** to identify your dependencies, you need to tell NexusDI how to actually create the values associated with those tokens. This is the role of a **Provider**.

A provider is essentially a recipe. When the container encounters a token it needs to resolve, it looks up the assigned provider to determine if it should instantiate a class, return a static value, or run a factory function.

## The Default: Class Providers

The most common way to provide a dependency is by using a class. `provide(COMPUTER, { useClass: QuantumComputer })` binds the class to the token, and `provide()`'s other options pick the other forms: `useValue`, `useFactory` and `useExisting`.

To make a class "injectable," you define its constructor dependencies in a `static deps` array. This allows NexusDI to know exactly what to inject without needing runtime reflection.

By declaring `static deps`, TypeScript can verify that the tokens you've listed actually match the types expected by the constructor. `static deps` lists the tokens in parameter order, and `provide()` reads it, so the provider needs no `deps` option.

## Advanced Provider Types

Sometimes a simple class instantiation isn't enough. NexusDI provides several other ways to resolve tokens.

### Factory Providers (`useFactory`)

Factories are used when the creation logic is complex or requires asynchronous setup. A factory is a function that returns the value for the token. ## Handling Constructor Defaults

If your class has no `static deps`, NexusDI counts its constructor parameters with `cls.length`. That count stops at the first parameter with a default or a rest parameter. A class whose parameters all have defaults counts zero and builds with its defaults. A rest parameter follows the same rule as a default: `constructor(...rest: X[])` counts zero and builds with an empty `rest`. `constructor(a: X, b = 1)` still counts one and fails with `NEXUS_MISSING_DEPS`.
