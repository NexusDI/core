# NexusDI Plugins

The core of NexusDI is designed to be lean. To keep the bundle size small while providing powerful features, optional functionality is delivered via **Plugins**.

Plugins allow you to hook into the container's lifecycle, modify how errors are reported, or add entirely new capabilities like graph introspection and method interception. A NexusDI plugin is a plain object with a `name` and the plugin API version it was written for (`apiVersion`), and it sets the hooks it uses as functions on that object. Each first-party package exports a function that returns one.

## Registering Plugins

Plugins are passed to the container during creation in the `plugins` array. The order of this array matters: plugins are executed in the order they are listed. The call is `Nexus.create(root, { plugins })`.

`errors()` from `@nexusdi/errors` gives NexusDI errors their full message with a fix line. Install it at the same version as `@nexusdi/core`:

```bash
npm install @nexusdi/errors@next
```

## Official First-Party Plugins

NexusDI provides several official plugins to enhance your development experience:

| Package                 | Plugin           | Purpose                                                                           |
| :---------------------- | :--------------- | :-------------------------------------------------------------------------------- |
| `@nexusdi/errors`       | `errors()`       | Replaces short error codes with full human-readable messages and fix suggestions. |
| `@nexusdi/devtools`     | `devtools()`     | Enables the `graph()` and `trace` tools for debugging your dependency tree.       |
| `@nexusdi/interceptors` | `interceptors()` | Enables method interception for cross-cutting concerns.                           |
| `@nexusdi/federation`   | `federation()`   | Gives one provider for every copy of a contract token, across bundles.            |
| `@nexusdi/testing`      | none to register | `createTestingContainer()` registers its own plugin ahead of yours.               |

The application writes the line that registers each one. `errors({ text })` takes the text packs you pass. `devtools({ text, annotate, trace })` includes the errors engine. `interceptors(options)` takes the options of [Method Interceptors](/interceptors/). `createTestingContainer()` is covered in [Testing and Overrides](/testing/).

Every package must be at the version of `@nexusdi/core`. Each one declares an exact peer dependency on core, so a package manager reports a mismatch at install.

## Plugin Execution Order

Some plugins provide similar functionality. For example, both `errors()` and a custom internal plugin might want to format error messages.

NexusDI handles this using a "first-win" strategy for `formatError` and `tokenKey`: the first plugin in the array that returns a result wins, and later plugins are not asked. Other hooks, such as `observe`, `construct`, `compile.check` and `setup`, run for every plugin in array order. This application plugin words one code, and `errors()` after it words the rest:

Swap the entries back and the bridge console's line returns.

## Plugin Validation

To ensure stability, `Nexus.create` validates all plugins before the graph is compiled. It will reject the startup process if:

- Two plugins share the same `name`.
- A plugin was written for an incompatible `apiVersion`.
- A plugin object is invalid, such as one with no `name`.

These faults reject as `NEXUS_PLUGIN_INVALID` and `NEXUS_PLUGIN_VERSION`. `Nexus.create` reports each fault as an error inside `NEXUS_BLUEPRINT_INVALID`.


**Try it:** Register `errors()` twice in the `plugins.ts` of the first region and run it. The container rejects, and the file prints `[NEXUS_PLUGIN_INVALID] nexus:errors has the name of an earlier plugin; each plugin needs its own name.` The plugin check runs before the graph compiles, so the missing provider is not reported. Remove the second `errors()` and the full missing-provider message returns.

A plugin written for another plugin API version fails with [NEXUS_PLUGIN_VERSION](/errors/NEXUS_PLUGIN_VERSION/). `NEXUS_PLUGIN_API` is the version this `@nexusdi/core` supports:

```ts file=examples/meridian/src/pages/plugins.md region=version

```

**Try it:** Set `apiVersion` to `NEXUS_PLUGIN_API` and run the region. The plugin is valid, so `Nexus.create` resolves, and the file prints `1` and then `undefined`, because there is no error to read. Set it back to `2` and the `NEXUS_PLUGIN_VERSION` message returns.

Later, a hook that throws rejects with `NEXUS_PLUGIN_FAILED`, and two plugins that rewrite the same module or provider reject with `NEXUS_PLUGIN_CONFLICT`. See [NEXUS_PLUGIN_FAILED](/errors/NEXUS_PLUGIN_FAILED/) and [NEXUS_PLUGIN_CONFLICT](/errors/NEXUS_PLUGIN_CONFLICT/).

This ensures that your plugin configuration is proven correct before your application starts processing data. To write a plugin of your own, read [Writing NexusDI Plugins](/write-a-plugin/).
