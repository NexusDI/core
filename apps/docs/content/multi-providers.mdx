# Multi-Providers

In most cases, one token maps to one provider. However, some features require a collection of contributions from across the application, such as a list of all available diagnostics, a set of validation rules, or a collection of plugin handlers.

**Multi-Providers** allow multiple modules to contribute to a single token, which is then resolved as an array of all contributions the reader can see.

## The `MultiToken`

To create a multi-provider, use the `MultiToken` class. This tells NexusDI that this token is designed to collect multiple values and not resolve to a single one.

```ts file=examples/meridian/src/pages/multi-providers.md region=multi-token

```

Any number of modules can call `provide(DIAGNOSTICS, ...)` to add their own contribution to the list. A contribution is either a class, as `ReactorDiagnostic` is above, or a value, as the hull check is. A contribution that needs deps uses a factory. `ship.get(DIAGNOSTICS)` returns the contributions as an array. The walk is the depth-first pass `Nexus.create` makes over the module graph. `all()` lists the contributions in the order the walk first meets their modules, starting at the root and following each module's `imports` in order, and within a module in `providers` order.

**Try it:** Save the region as `diagnostics.ts` and run `npx tsx diagnostics.ts`. It prints `[ 'reactor', 'hull' ]`. Add a third `provide(DIAGNOSTICS, { useValue: { system: 'shields', check: () => false } })` after the hull one and run it again: it prints `[ 'reactor', 'hull', 'shields' ]`. Delete that line and the array loses `shields` again. Then add `const DRONE_COUNT = new Token<number>('DroneCount');` (import `Token`), `provide(DRONE_COUNT, { useValue: 3 })` and `provide(DIAGNOSTICS, { useFactory: (n: number) => ({ system: 'drone' + n, check: () => true }), deps: [DRONE_COUNT] })` to the list: the array gains `drone3`.

## Consuming Contributions with `all()`

Because a `MultiToken` represents a collection, you cannot use it as a standard dependency. Instead, you must use the `all()` modifier in your `static deps` list. `lazy(all(TOKEN))` composes `all()` with `lazy()`, and it is the one other form a multi-token takes (see [Contributors That Call the Collector](#contributors-that-call-the-collector)). `lazy(TOKEN)`, `optional(TOKEN)`, `optional(all(TOKEN))` and the bare `MultiToken` are invalid: each makes `Nexus.create` reject with `NEXUS_BLUEPRINT_INVALID`, wrapping `NEXUS_INVALID_PROVIDER`.

```ts file=examples/meridian/src/pages/multi-providers.md region=panel

```

`all(TOKEN)` tells NexusDI to resolve every visible contribution to that token and pass them to the constructor as an array. Here `Engineering` contributes the reactor diagnostic and `Tactical` the hull check, each module exports `DIAGNOSTICS`, and `StatusBoard` in `Meridian` reads both. The same panel takes `optional(SUBSPACE_LINK)`, which resolves to `undefined` while no module provides a link.

  hullDiagnostic -->|all| DiagnosticsPanel

Add a `Comms` module that provides and exports `SUBSPACE_LINK` with a `useValue` whose `send(report)` returns `'sent: ' + report`, import it into `Meridian`, and run it again: the panel prints `sent: reactor green, hull green`. Take `Comms` out of `Meridian`'s imports and the panel prints `reactor green, hull green` again.

### Contributors That Call the Collector

Cyclic dependencies often occur when a collector, such as an event bus, interacts with contributors that must call back into that same collector. For example, a handler might react to a bulletin by publishing a new one. In this scenario, the handler depends on the bus, while the bus depends on every handler via `all()`. This creates a provider cycle that causes `Nexus.create` to reject the configuration with `NEXUS_BLUEPRINT_INVALID`, whose `errors` list holds `NEXUS_CIRCULAR_DEPENDENCY`. To avoid this without requiring every third-party handler to manually use `lazy(EVENT_BUS)`, the bus itself can resolve the cycle.

`lazy(all(HANDLERS))` allows the bus to break the cycle. The bus receives a thunk that returns the handlers, while each handler maintains a standard dependency on the bus.

```ts file=examples/meridian/src/pages/multi-providers.md region=lazy-all

```

**SubspaceBus** accepts `lazy(all(HANDLERS))` and executes the thunk inside the `publish()` method after `Nexus.create` has completed. **AlertHandler** depends on `EVENT_BUS` and publishes a second bulletin upon hearing `hull breach`. Consequently, `LogHandler` processes the nested `all hands` bulletin before the `hull breach` bulletin. [Collectors Their Contributors Call](/lazy/#collectors-their-contributors-call) describes the thunk and the errors it throws.

**Try it:** Save the region as `bus.ts` and run it. It prints `[ 'all hands', 'hull breach' ]`. Change `SubspaceBus`'s deps to `[all(HANDLERS)] as const`, its parameter to `IHandler[]` and the loop to `for (const each of this.handlers)`, and run it again: `Nexus.create` rejects, and the region below shows what you see. ## Publishing Contributions

A library that defines an extension point cannot import the modules that extend it. A health library owns the `HEALTH_CHECKS` token and a `HealthService` that runs every check, and each application module that wants a check imports the library and contributes to the token. The module publishes its contributions by exporting the token.

```ts file=examples/meridian/src/pages/multi-providers.md region=publish

```

`HealthService` sits in `HealthModule` and takes `all(HEALTH_CHECKS)`. `Engineering` and `Tactical` import `HealthModule`, bind a check each with `useClass`, and export `HEALTH_CHECKS`. `HealthModule` imports neither of them, and `HealthService` still runs both checks. `DeckReport` is a second collector in another module, and it counts the same two.

For a `MultiToken` and a module, the container applies two rules. A module publishes its own contributions to the token when its `exports` names the token, and publishes none otherwise. A re-export, as in `exports: [OtherModule]`, publishes nothing of the token, because each module publishes its own contributions. The module's view of the token holds its own contributions plus everything that every module publishes.

What a reader of `all()` sees:

- Private contributions stay private. If a module does not export a contribution, it remains visible only within that module (or by a root `get()` if that module is the root). For a non-root module to keep such a contribution, it must provide its own reader via `all()` or `lazy(all())`. Otherwise, NexusDI detects a contribution that no provider reads and rejects with `NEXUS_UNREAD_CONTRIBUTION`.
- Two collectors of one token in two modules see one list, apart from each one's own private contributions. A plugin module's exported contributions (`NexusPlugin.modules`) are in that list, as any other module's are.

`exports: [DIAGNOSTICS]` in a module with no contribution of its own is legal and does nothing. The contributions of its imports reach every collector without it, and the export raises no `NEXUS_INVALID_EXPORT`.

**Try it:** Save the region as `health.ts` and run it. It prints `reactor green, hull red` and then `2`. Delete `exports: [HEALTH_CHECKS],` from `Tactical` and run it again: `Nexus.create` rejects with `NEXUS_BLUEPRINT_INVALID`, and its `errors` list holds `NEXUS_UNREAD_CONTRIBUTION` for `HullCheck` in `Tactical`, because no provider in `Tactical` reads `HEALTH_CHECKS`. Put the line back and it prints `reactor green, hull red` and `2` again.

The next region contributes to a token without exporting it, and no provider in the module reads the token.

```ts file=examples/meridian/src/pages/multi-providers.md region=unexported

```

`Tactical` contributes the hull check, has no `exports` and has no provider of its own, so nothing can read the contribution. The panel in `Meridian` sees only what `Engineering` exports. `Nexus.create` rejects with `NEXUS_BLUEPRINT_INVALID`, and the first entry of its `errors` list is `NEXUS_UNREAD_CONTRIBUTION`. There are three fixes, in this order: collect the contribution in `Tactical` with a provider that takes `all(DIAGNOSTICS)`, add `DIAGNOSTICS` to the `exports` of `Tactical` to publish it to every collector, or remove the contribution. [NEXUS_UNREAD_CONTRIBUTION](/errors/NEXUS_UNREAD_CONTRIBUTION/) lists the conditions and the lookups that do not count as readers.

**Try it:** Save the region as `private.ts` and run it. It prints `NEXUS_BLUEPRINT_INVALID` and then `NEXUS_UNREAD_CONTRIBUTION`. Add `exports: [DIAGNOSTICS]` to `Tactical` and run it again: `Nexus.create` succeeds, and the region prints `null` twice because there is no error to read. Remove `exports` from `Tactical` and the error returns.

### The Order of the List

The list follows the walk, and the walk visits a module once, where it first meets it. Here `Meridian` imports `Hangar` before `Engineering`, and `Hangar` imports `Engineering` itself, so the walk meets `Engineering` inside `Hangar`:

```

`Hangar` contributes `shuttle` and comes first. `Engineering` follows with `reactor` and `coolant` in `providers` order, and `Tactical` adds `hull` last. A private contribution of the collector's own module sorts into the list by the same order.
