# Multi-Providers

In most cases, one token maps to one provider. However, some features require a collection of contributions from across the application—such as a list of all available diagnostics, a set of validation rules, or a collection of plugin handlers.

**Multi-Providers** allow multiple modules to contribute to a single token, which is then resolved as an array of all visible contributions.

## The `MultiToken`

To create a multi-provider, use the `MultiToken` class. This tells NexusDI that this token is designed to collect multiple values rather than resolving to a single one.

```ts file=examples/meridian/src/pages/multi-providers.md region=multi-token
```

Any number of modules can call `provide(DIAGNOSTICS, ...)` to add their own contribution to the list.

## Consuming Contributions with `all()`

Because a `MultiToken` represents a collection, you cannot use it as a standard dependency. Instead, you must use the `all()` modifier in your `static deps` list.

```ts file=examples/meridian/src/pages/multi-providers.md region=panel
```

`all(TOKEN)` tells NexusDI to resolve every visible contribution to that token and pass them to the constructor as an array.

## Visibility and Encapsulation

Multi-providers follow the same visibility rules as standard providers:

1. **Local Contributions:** A module always sees its own contributions.
2. **Imported Contributions:** A module sees contributions from any imported module that explicitly exports the `MultiToken`.
3. **Private Contributions:** If a module contributes to a `MultiToken` but does not export it, that contribution remains private to the module.

This allows you to have "internal" diagnostics that only the module itself can see, while sharing "public" diagnostics with the rest of the application.
