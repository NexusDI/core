# Multi-Providers

In most cases, one token maps to one provider. However, some features require a collection of contributions from across the application, such as a list of all available diagnostics or a collection of plugin handlers.

## Extension Points in Libraries

A library that runs every health check or every event handler cannot know these contributors in advance. The contributors live in the application's modules, and the library cannot import those modules because they already import the library.

To solve this, the library defines a token that acts as an extension point. The library's collector reads the entire list of contributions, while the application modules add to that list without needing to know the collector exists.

**Multi-Providers** allow NexusDI to implement these extension points. Many modules contribute to a single token, and a collector resolves them as an array of all visible contributions.

## The `MultiToken`

To create a multi-provider, use the `MultiToken` class. The class tells NexusDI that the token collects multiple values.


Any number of modules can call `provide(DIAGNOSTICS, ...)` to add a contribution. A contribution can be a class (like `ReactorDiagnostic` above) or a value (like the hull check). A contribution with dependencies takes them through its class's `static deps` or a factory's `deps`.

When you call `ship.get(DIAGNOSTICS)`, NexusDI returns the contributions as an array. The walk is the depth-first pass `Nexus.create` makes over the module graph. `all()` lists the contributions in the order the walk first meets their modules, starting at the root and following each module's `imports` in order, and within a module in `providers` order.

**Try it:** Save the region as `diagnostics.ts` and run `npx tsx diagnostics.ts`. It prints `[ 'reactor', 'hull' ]`. Add a third `provide(DIAGNOSTICS, { useValue: { system: 'shields', check: () => false } })` after the hull one and run it again: it prints `[ 'reactor', 'hull', 'shields' ]`. Delete that line and the array loses `shields` again. Then add `const DRONE_COUNT = new Token<number>('DroneCount');` (import `Token`), `provide(DRONE_COUNT, { useValue: 3 })` and `provide(DIAGNOSTICS, { useFactory: (n: number) => ({ system: 'drone' + n, check: () => true }), deps: [DRONE_COUNT] })` to the list: the array gains `drone3`.

## Consuming Contributions with `all()`

Because a `MultiToken` represents a collection, you cannot use it as a standard dependency. You must use the `all()` modifier in the dependency list.

Valid forms for multi-tokens include `all(TOKEN)` and `lazy(all(TOKEN))`. `lazy(TOKEN)`, `optional(TOKEN)`, `optional(all(TOKEN))` and a bare `MultiToken` are invalid. Each makes `Nexus.create` reject with `NEXUS_BLUEPRINT_INVALID`, wrapping a `NEXUS_INVALID_PROVIDER` error.

```ts file=examples/meridian/src/pages/multi-providers.md region=panel

```

`all(TOKEN)` tells NexusDI to resolve every visible contribution to that token and pass them to the constructor as an array. In the example above, `Engineering` contributes the reactor diagnostic and `Tactical` contributes the hull check, each module exports `DIAGNOSTICS`, and `StatusBoard` in `Meridian` reads both. The same panel takes `optional(SUBSPACE_LINK)`, which resolves to `undefined` while no module provides a link.

```mermaid caption="Engineering and Tactical each contribute to DIAGNOSTICS, and StatusBoard in Meridian reads both through all()."
  hullDiagnostic -->|all| StatusBoard
```

**Try it:** Save the region as `panel.ts` and run it. It prints `reactor green, hull green`. Add a `Comms` module that provides and exports `SUBSPACE_LINK` with a `useValue` whose `send(report)` returns `'sent: ' + report`, import it into `Meridian`, and run it again: the panel prints `sent: reactor green, hull green`. Take `Comms` out of `Meridian`'s imports and the panel prints `reactor green, hull green` again.

## Publishing Contributions

A library defining an extension point cannot import the modules that extend it. For example, a health library owns the `HEALTH_CHECKS` token and a `HealthService` that runs every check. Application modules import the health library, contribute their own checks to the token, and publish those contributions by exporting the token.

```ts file=examples/meridian/src/pages/multi-providers.md region=publish

```

`HealthService` sits in `HealthModule` and takes `all(HEALTH_CHECKS)`. `Engineering` and `Tactical` import `HealthModule`, bind a check each with `useClass`, and export `HEALTH_CHECKS`. Even though `HealthModule` imports neither of them, `HealthService` still runs both checks. `DeckReport` is a second collector in another module, and it counts the same two.

NexusDI applies two rules for `MultiToken` and modules:

1. **Publishing:** A module publishes its own contributions to the token only if its `exports` list names that token.
2. **Re-exports:** A re-export (e.g., `exports: [OtherModule]`) does not publish the token's contributions, as each module must publish its own.

A collector reads its own module's contributions plus everything published by other modules.

**Try it:** Save the region as `health.ts` and run it. It prints `reactor green, hull red` and then `2`. Delete `exports: [HEALTH_CHECKS],` from `Tactical` and run it again: `Nexus.create` rejects with `NEXUS_BLUEPRINT_INVALID`, and its `errors` list holds `NEXUS_UNREAD_CONTRIBUTION` for `HullCheck` in `Tactical`, because no provider in `Tactical` reads `HEALTH_CHECKS`. Put the line back and it prints `reactor green, hull red` and `2` again.

### Multiple Collectors

Multiple collectors of the same token across different modules see the same list, apart from each one's own private contributions. In the region above, `HealthService` and `DeckReport` are in different modules, yet both read `reactor` and `hull`. A plugin can add modules to the container through `NexusPlugin.modules`. Those modules' exported contributions are in the list, after the root's own imports.

### Inert Exports

Exporting a token from a module that provides no contribution to it is legal. The contributions from its imports still reach the collector, and the export does not trigger a `NEXUS_INVALID_EXPORT`. A re-export of a module is just as inert. In the region below, `Bridge` has no contribution of its own and exports both the token and `Engineering`. The root still receives the one contribution that `Engineering` publishes.


**Try it:** Save the region as `bridge.ts` and run it. It prints `[ 'reactor' ]`. Delete the `exports` line from `Bridge` and run it again: it prints `[ 'reactor' ]`, because `Engineering` publishes the contribution on its own.

### Resolution Order

The list follows the module walk. A module is visited once, where it is first encountered. In the example below, `Meridian` imports `Hangar` before `Engineering`, and `Hangar` also imports `Engineering`, so the walk meets `Engineering` inside `Hangar`.

```ts file=examples/meridian/src/pages/multi-providers.md region=order

```

`Hangar` contributes `shuttle` and appears first. `Engineering` follows with `reactor` and `coolant` (in `providers` order), and `Tactical` adds `hull` last. Private contributions from the collector's own module are sorted into the list using the same logic.

## Private Contributions

If a module contributes to a token but does not export it, that contribution remains private. It is visible only within that module. A root `get()` also sees it when that module is the root.

For a non-root module to keep a private contribution, it must provide its own reader via `all()` or `lazy(all())`. Otherwise, NexusDI detects a contribution that no provider reads and rejects with `NEXUS_UNREAD_CONTRIBUTION`.

```ts file=examples/meridian/src/pages/multi-providers.md region=unexported

```

In this example, `Tactical` contributes a hull check but has no `exports`, and no provider in `Tactical` reads `DIAGNOSTICS`. Nothing can read the contribution, so `Nexus.create` rejects with `NEXUS_BLUEPRINT_INVALID`, and the first entry of its `errors` list is `NEXUS_UNREAD_CONTRIBUTION`.

There are three fixes, in order of preference:

1. Collect the contribution in `Tactical` with a provider using `all(DIAGNOSTICS)`.
2. Add `DIAGNOSTICS` to the `exports` of `Tactical` to publish it.
3. Remove the contribution.

The compiler raises this error when: the module is not the root, it does not export the token, and no provider in the module binds the token via `all()` or `lazy(all())`. (A token that a test or plugin pins to one contribution is exempt.) `get(TOKEN, { module })` can see private contributions, but they do not count as readers because the compiler cannot guarantee these calls will execute. [NEXUS_UNREAD_CONTRIBUTION](/errors/NEXUS_UNREAD_CONTRIBUTION/) lists the conditions and the lookups that do not count as readers.

**Try it:** Save the region as `private.ts` and run it. It prints `NEXUS_BLUEPRINT_INVALID` and then `NEXUS_UNREAD_CONTRIBUTION`. Add `exports: [DIAGNOSTICS]` to `Tactical` and run it again: `Nexus.create` succeeds, and the region prints `null` twice because there is no error to read. Remove `exports` from `Tactical` and the error returns.

## Contributors That Call the Collector

Cyclic dependencies often arise when a collector (like an event bus) interacts with contributors that must call back into that same collector. If a handler depends on the bus, and the bus depends on all handlers via `all()`, a provider cycle is created. This causes `Nexus.create` to reject with `NEXUS_BLUEPRINT_INVALID` and `NEXUS_CIRCULAR_DEPENDENCY`.

To resolve this without forcing every handler to use `lazy()`, the bus can resolve the cycle using `lazy(all(TOKEN))`. This provides the bus with a thunk that returns the handlers, while handlers maintain a standard dependency on the bus.

```ts file=examples/meridian/src/pages/multi-providers.md region=lazy-all

```

`SubspaceBus` takes `lazy(all(HANDLERS))` and calls the thunk inside `publish()`, after `Nexus.create` has finished. `AlertHandler` depends on `EVENT_BUS` and publishes a new bulletin when it handles `hull breach`. Consequently, `LogHandler` processes the nested `all hands` bulletin before the `hull breach` bulletin.

**Try it:** Save the region as `bus.ts` and run it. It prints `[ 'all hands', 'hull breach' ]`. Change `SubspaceBus`'s deps to `[all(HANDLERS)] as const`, its parameter to `IHandler[]` and the loop to `for (const each of this.handlers)`, and run it again: `Nexus.create` rejects, and the region below shows what you see. The region registers `errors()` from `@nexusdi/errors` (`npm install @nexusdi/errors@next`), which adds a `Fix:` line under each error message. Change them back when you are done.

```ts file=examples/meridian/src/pages/multi-providers.md region=lazy-all-cycle

```

Save this region as `bus-cycle.ts` and run it. It prints `NEXUS_BLUEPRINT_INVALID`, `NEXUS_CIRCULAR_DEPENDENCY`, `all -> required` and `true`. The error's `kinds` field lists how each step of the cycle depends on the next: the bus reaches `AlertHandler` through `all()`, and `AlertHandler` reaches the bus through a required dependency. `true` confirms that the `Fix:` line suggests `lazy(all(Handlers))`.

The thunk is all or nothing, and it throws `NEXUS_NOT_READY` or `NEXUS_DISPOSED` when a contribution is not live. [Collectors Their Contributors Call](/lazy/#collectors-their-contributors-call) describes the thunk and these two errors.
